    Ampliación avanzada: clúster multi‑nodo + Transforms (agregados) para dashboards rápidos

    Curso de Especialización en IA y Big Data

    Este documento amplía la práctica anterior (CSV → RAW/REF → enrich → covid_enriched) con dos líneas “Big Data”:

    1) Despliegue de un clúster multi‑nodo (roles, replicas, rendimiento, tolerancia a fallos).
    2) Transforms para generar índices agregados (diario/mensual) y acelerar visualizaciones en Kibana.

    1) Ampliación 1: Montar un clúster multi‑nodo (roles y arquitectura)

    1.1 Objetivos didácticos

    • Entender roles de nodo (master, data, ingest, transform, coordinating).
    • Ver el efecto de replicas y shards.
    • Practicar resiliencia: caída de un nodo, reubicación de shards.
    • Medir rendimiento: búsquedas y agregaciones con 1 vs varios nodos.

    1.2 Arquitectura recomendada para el aula (mínima y clara)

    Opción A (simple y eficaz): 3 nodos iguales + 1 Kibana - es01, es02, es03: master,data,ingest,transform - kibana: interfaz

    Opción B (más “real”): separar ingest/transform - 3 nodos master/data: es01, es02, es03 con roles master,data - 1 nodo es_ingest: roles ingest,transform,coordinating_only (sin data) - Kibana apunta al coordinador o a un LB

    Para clase, Opción A suele ser la mejor: menos piezas, y ya permite HA.

    1.3 Docker Compose de ejemplo (Opción A: 3 nodos + Kibana)

    Ajusta RAM/CPU según tu equipo. Para alumnos con portátil, 3 nodos con heap de 1 GB puede ir justo; 768 MB también puede funcionar.

    1.3.1 Verificación del clúster

    GET _cluster/health?pretty
GET _cat/nodes?v
GET _cat/shards?v

    1.4 Shards y replicas para la práctica

    Con 3 nodos, ya tiene sentido usar replicas:

    • Índices RAW: number_of_replicas: 1 (tolerancia a fallos).
    • Índice final covid_enriched: number_of_shards: 3, number_of_replicas: 1.

    Ejemplo (ajusta antes de reindexar, idealmente con template): 

    PUT covid_enriched/_settings
{
  "index": {
    "number_of_replicas": 1
  }
}

    Nota: number_of_shards solo se fija al crear el índice. Para decidirlo, piensa: - dataset histórico grande: 3–6 shards - laboratorio: 1–3 shards

    1.5 Actividades evaluables (multi‑nodo)

    1) Caída controlada: parar es02, comprobar que el clúster sigue “yellow/green” y que Kibana funciona.
    2) Activar replicas=1 y observar reasignación de shards.
    3) Medir tiempo de una query de agregación grande con 1 nodo vs 3 nodos (mismo dataset).
    4) Ajustar slices=auto en reindex y comparar tiempos.

    2) Ampliación 2: Transforms para índices agregados (dashboards rápidos)

    2.1 ¿Qué es un Transform?

    Un Transform crea (y mantiene) un índice derivado con datos agregados o pivotados a partir de otro índice.

    En esta práctica: - origen: covid_enriched - destino: índices agregados tipo: - covid_agg_daily (diario) - covid_agg_monthly (mensual)

    Ventaja: - Dashboards con miles de puntos en lugar de millones de documentos. - Menos carga en CPU/heap al hacer visualizaciones.

    2.2 Preparación: índice origen y campos

    Se asume que covid_enriched ya tiene: - @timestamp (date) - provincia.code, provincia.nombre, provincia.ccaa - sexo, grupo_edad - métricas: num_casos, num_hosp, num_uci, num_def

    Comprobación rápida: 

    GET covid_enriched/_search?size=1

    3) Transform 1: agregado DIARIO por provincia/sexo/edad

    3.1 Crear Transform (API)

    Este Transform crea un documento por: - día (@timestamp agrupado por día) - provincia (provincia.code) - sexo - grupo_edad

    Y agrega: - suma de casos, hospitalizaciones, UCI y fallecimientos.

    PUT _transform/covid_daily_by_prov_sex_age
{
  "source": {
    "index": "covid_enriched"
  },
  "dest": {
    "index": "covid_agg_daily"
  },
  "pivot": {
    "group_by": {
      "day": {
        "date_histogram": {
          "field": "@timestamp",
          "fixed_interval": "1d"
        }
      },
      "provincia_code": { "terms": { "field": "provincia.code" } },
      "provincia_nombre": { "terms": { "field": "provincia.nombre" } },
      "ccaa": { "terms": { "field": "provincia.ccaa" } },
      "sexo": { "terms": { "field": "sexo" } },
      "grupo_edad": { "terms": { "field": "grupo_edad" } }
    },
    "aggregations": {
      "sum_casos": { "sum": { "field": "num_casos" } },
      "sum_hosp":  { "sum": { "field": "num_hosp" } },
      "sum_uci":   { "sum": { "field": "num_uci" } },
      "sum_def":   { "sum": { "field": "num_def" } }
    }
  },
  "description": "Agregado diario por provincia/sexo/edad desde covid_enriched"
}

    3.2 Arrancar Transform

    POST _transform/covid_daily_by_prov_sex_age/_start

    3.3 Monitorizar

    GET _transform/covid_daily_by_prov_sex_age/_stats
GET covid_agg_daily/_count

    3.4 Ver un documento del índice agregado

    GET covid_agg_daily/_search?size=1

    4) Transform 2: agregado MENSUAL (más ligero aún)

    Ideal para dashboards de overview.

    PUT _transform/covid_monthly_by_prov
{
  "source": {
    "index": "covid_enriched"
  },
  "dest": {
    "index": "covid_agg_monthly"
  },
  "pivot": {
    "group_by": {
      "month": {
        "date_histogram": {
          "field": "@timestamp",
          "calendar_interval": "1M"
        }
      },
      "provincia_code": { "terms": { "field": "provincia.code" } },
      "provincia_nombre": { "terms": { "field": "provincia.nombre" } },
      "ccaa": { "terms": { "field": "provincia.ccaa" } }
    },
    "aggregations": {
      "sum_casos": { "sum": { "field": "num_casos" } },
      "sum_hosp":  { "sum": { "field": "num_hosp" } },
      "sum_uci":   { "sum": { "field": "num_uci" } },
      "sum_def":   { "sum": { "field": "num_def" } }
    }
  },
  "description": "Agregado mensual por provincia desde covid_enriched"
}

POST _transform/covid_monthly_by_prov/_start

    5) (Opcional) Transform continuo

    Para un dataset que se actualiza (no solo histórico), se usa sync. Ejemplo: agregados diarios que se mantienen “al día”, con un pequeño retraso (delay):

    PUT _transform/covid_daily_continuous
{
  "source": { "index": "covid_enriched" },
  "dest": { "index": "covid_agg_daily_cont" },
  "sync": {
    "time": {
      "field": "@timestamp",
      "delay": "60m"
    }
  },
  "pivot": {
    "group_by": {
      "day": { "date_histogram": { "field": "@timestamp", "fixed_interval": "1d" } },
      "provincia_code": { "terms": { "field": "provincia.code" } }
    },
    "aggregations": {
      "sum_casos": { "sum": { "field": "num_casos" } }
    }
  }
}
POST _transform/covid_daily_continuous/_start

    6) Kibana: crear Data Views para los índices agregados

    Crea Data Views: - covid_agg_daily - covid_agg_monthly

    Time field: - day o month (según el Transform) o usar el campo de fecha creado en el group_by.

    En Lens: - Y: sum_casos (ya es un campo del índice agregado) - X: day o month

    7) Comparativa de rendimiento (actividad)

    7.1 Experimento

    1) Crea una visualización equivalente: - desde covid_enriched (millones de docs) - desde covid_agg_daily o covid_agg_monthly (mucho menos)

    2) Compara: - tiempo de carga del panel - uso de CPU/memoria del clúster - latencia de agregaciones

    7.2 Métrica rápida (a ojo)

    • covid_enriched: agregaciones “pesadas”
    • covid_agg_monthly: casi instantáneo para dashboards generales

    8) Mejores prácticas (para que Transform vaya fino)

    • Destino con replicas=1 en clúster multi-nodo.
    • Elegir intervalos razonables:
    • 1d para análisis detallado
    • 1M para overview
    • Si se usa continuo: delay suficiente para evitar re-procesar datos “recién llegados”.
    • Si el índice origen es muy grande: crear un Transform por fases (por años) o aplicar filtros por rango temporal en source.query.

    9) Propuestas de evaluación (Transforms)

    1) Crear covid_agg_daily y demostrar que el total de casos agregados coincide con el original (comparación de sumas globales).
    2) Crear un dashboard “overview” mensual con covid_agg_monthly.
    3) Añadir dimensión alarma.cod al daily Transform y analizar efecto en los gráficos.
    4) Proponer una estrategia ILM para covid_agg_daily (retener 2 años en hot, pasar a warm, etc.).

    10) Check rápido de consistencia (sumas)

    Ejemplo: comparar suma total de casos entre origen y agregado mensual.

    Origen: 

    GET covid_enriched/_search
{
  "size": 0,
  "aggs": {
    "total": { "sum": { "field": "num_casos" } }
  }
}

    Agregado mensual: 

    GET covid_agg_monthly/_search
{
  "size": 0,
  "aggs": {
    "total": { "sum": { "field": "sum_casos" } }
  }
}

    Deben ser muy cercanos (si no hay filtros y el Transform terminó).
