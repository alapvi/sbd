    Caso de uso

    Objetivo de la práctica

    Cargar CSV directamente en Elasticsearch desde Kibana y hacer todas las transformaciones dentro del stack Elastic hasta obtener un índice final listo para análisis:

    • Índices RAW (CSV “tal cual”):

    • covid_raw

    • prov_raw

    • trams_raw

    • Índices REF (limpios para enrich):

    • prov_ref
    • trams_ref
    • Índice final (curado):
    • covid_enriched

    El índice final covid_enriched debe incluir:

    • @timestamp (date)
    • provincia.* enriquecido (nombre, CCAA, ISO3166-2)
    • alarma.cod (integer) y alarma.desc
    • métricas num_* como integers
    • trazabilidad opcional: fecha_raw, ingest_error

    Importación de CSV y creación de índices RAW

    Importación con Data Visualizer

    Kibana: - Machine Learning → Data Visualizer → Upload file - Subir cada CSV y asignar:

    CSV Índice RAW
    Serie COVID covid_raw
    Provincias prov_raw
    Tramos alarma trams_raw

    Si Kibana muestra timeout, comprueba igualmente en Index Management: la importación puede haber terminado.

    Verificación

    GET _cat/indices/covid_raw,prov_raw,trams_raw?v

    Ver un documento de muestra

    GET covid_raw/_search?size=1
GET prov_raw/_search?size=1
GET trams_raw/_search?size=1

    Crear índices REF (limpios) para enrich

    ¿Por qué REF?

    • Evita depender de nombres de columnas con espacios/acentos (p.ej. “Código 3166-2”).
    • Tipos claros (keyword, integer) para enrich.
    • Proceso reproducible: RAW intactos + REF limpios.

    Construcción de prov_ref

    Crear índice

    DELETE prov_ref

PUT prov_ref
{
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "provincia_code": { "type": "keyword" },
      "iso3166_2":      { "type": "keyword" },
      "nombre":         { "type": "keyword" },
      "ccaa":           { "type": "keyword" }
    }
  }
}

    ¿Qué es un mapping?

    En Elasticsearch/OpenSearch, el mapping es el “esquema” de tus documentos: define qué campos existen, su tipo y cómo se indexan para búsquedas, filtros y agregaciones.

    mappings.dynamic: "strict"
    "dynamic": "strict"

    Con strict, solo se aceptan campos definidos en properties:

    • ✅ Documento con campos conocidos → se indexa.
    • ❌ Documento con un campo extra no declarado → se rechaza con un error tipo strict_dynamic_mapping_exception.

    Esto es típico en índices de referencia/maestros, donde interesa garantizar estructura fija.

    properties: campos permitidos
    ccaa (keyword)
    • Qué representa: la Comunidad Autónoma (CCAA) asociada a la provincia.
    • Tipo: keyword (valor exacto; no se analiza).
    • Uso típico: filtros, agregaciones y ordenación.

    Ejemplos: "Andalucía", "Cataluña" (o un código interno, según tu modelo).

    iso3166_2 (keyword)
    • Qué representa: un código ISO 3166-2 (subdivisión administrativa).
    • Tipo: keyword (identificador exacto).
    • Uso típico: filtros exactos y agregaciones.

    Ejemplo de formato: "ES-XX" (el sufijo depende de la subdivisión que estés codificando).

    Nota: el mapping no valida que sea ISO “real”; solo define el tipo del campo.

    nombre (keyword)
    • Qué representa: el nombre de la provincia.
    • Tipo: keyword (ideal para coincidencia exacta y agregaciones).

    Ejemplos: "Sevilla", "A Coruña", "Illes Balears".

    Si necesitas búsqueda por texto (parcial, relevancia, etc.), conviene añadir un multifield:

    "nombre": {
  "type": "keyword",
  "fields": {
    "text": { "type": "text" }
  }
}

    Así usarías nombre para exactos y nombre.text para full‑text.

    provincia_code (keyword)
    • Qué representa: un código identificador de provincia (oficial o interno).
    • Tipo: keyword (perfecto para IDs).
    • Uso típico: joins lógicos en la app, filtros, agregaciones.

    Ejemplos: "41", "28", "08" (si guardas códigos numéricos como string).

    Ejemplo de documento válido

    {
  "ccaa": "Andalucía",
  "iso3166_2": "ES-AN",
  "nombre": "Sevilla",
  "provincia_code": "41"
}

    Ejemplo de documento inválido (por dynamic: strict)

    {
  "ccaa": "Andalucía",
  "iso3166_2": "ES-AN",
  "nombre": "Sevilla",
  "provincia_code": "41",
  "poblacion": 1950000
}

    ➡️ poblacion no está en properties, así que el documento fallaría al indexar.

    Consultas típicas (campos keyword)

    Filtrar por provincia (exacto)
    {
  "query": { "term": { "nombre": "Sevilla" } }
}
    Filtrar por varias provincias
    {
  "query": { "terms": { "provincia_code": ["41", "28", "08"] } }
}
    Agregar por CCAA
    {
  "size": 0,
  "aggs": {
    "por_ccaa": { "terms": { "field": "ccaa" } }
  }
}

    Pipeline prov_ref_pipeline

    PUT _ingest/pipeline/prov_ref_pipeline
{
  "processors": [
    {
      "script": {
        "lang": "painless",
        "source": """
          def iso = ctx['Código 3166-2'];
          def nombre = ctx['Nombre de la subdivisión'];
          def ccaa = ctx['Subdivisión superior'];

          String isoStr = iso == null ? null : iso.toString();
          String code = null;

          if (isoStr != null) {
            if (isoStr.startsWith('ES-') && isoStr.length() > 3) code = isoStr.substring(3);
            else code = isoStr;
          }

          if (code != null) ctx.provincia_code = code;
          if (isoStr != null) ctx.iso3166_2 = isoStr;
          if (nombre != null) ctx.nombre = nombre.toString();
          if (ccaa != null) ctx.ccaa = ccaa.toString();
        """
      }
    },
    {
      "remove": {
        "field": [
          "Código 3166-2",
          "Categoría de la subdivisión",
          "Nombre de la subdivisión",
          "Código del idioma",
          "Subdivisión superior"
        ],
        "ignore_missing": true
      }
    }
  ]
}

    ¿Para qué sirve este pipeline?

    Su objetivo es transformar documentos “en bruto” (por ejemplo, importados desde un CSV con cabeceras en español, espacios y acentos) hacia el modelo final del índice prov_ref, que espera campos “limpios” como:

    • provincia_code
    • iso3166_2
    • nombre
    • ccaa

    Y, después, elimina los campos originales para dejar un _source final consistente.

    Esto encaja especialmente bien con un índice con dynamic: "strict", porque evita que queden campos inesperados.

    Processor 1 — script (Painless)

    1. Lectura de campos de entrada

    def iso = ctx['Código 3166-2'];
def nombre = ctx['Nombre de la subdivisión'];
def ccaa = ctx['Subdivisión superior'];
    • ctx es el documento que entra al pipeline (equivalente a su _source).
    • Se leen tres campos “raw” típicos de una importación:
    Campo de entrada Significado esperado
    Código 3166-2 Código ISO 3166-2, p. ej. ES-SE
    Nombre de la subdivisión Nombre de provincia/subdivisión, p. ej. Sevilla
    Subdivisión superior Subdivisión superior (p. ej. CCAA), Andalucía

    2. Normalización a string (isoStr) y creación de code

    String isoStr = iso == null ? null : iso.toString();
String code = null;
    • isoStr asegura que el valor de Código 3166-2 sea String.
    • Si iso es null, isoStr también será null.
    • code se inicializa a null. Luego se calculará a partir de isoStr.

    3. Lógica para generar provincia_code

    if (isoStr != null) {
  if (isoStr.startsWith('ES-') && isoStr.length() > 3) code = isoStr.substring(3);
  else code = isoStr;
}

    Esta parte es la clave del pipeline:

    • Si isoStr empieza por ES- y tiene algo después:
    • se elimina el prefijo ES- usando substring(3)
    • Si no cumple eso:
    • se usa isoStr tal cual

    Ejemplos:

    isoStr (entrada) Resultado code Motivo
    ES-SE SE Quita ES-
    ES-AN AN Quita ES-
    ES- ES- No tiene longitud > 3 (se deja igual)
    FR-75 FR-75 No empieza por ES-
    SE SE No empieza por ES-

    En la práctica, esto genera un identificador corto para España, y deja intactos códigos de otros formatos.

    4. Escritura de campos finales en el documento

    if (code != null) ctx.provincia_code = code;
if (isoStr != null) ctx.iso3166_2 = isoStr;
if (nombre != null) ctx.nombre = nombre.toString();
if (ccaa != null) ctx.ccaa = ccaa.toString();

    Crea (o sobrescribe) estos campos:

    Campo de salida Fuente Transformación
    provincia_code derivado de Código 3166-2 quita ES- si aplica
    iso3166_2 Código 3166-2 a string
    nombre Nombre de la subdivisión a string
    ccaa Subdivisión superior a string

    Además, se asignan solo si el valor no es null, lo que evita escribir nulos o fallar por campos ausentes.

    Processor 2 — remove

    {
  "remove": {
    "field": [
      "Código 3166-2",
      "Categoría de la subdivisión",
      "Nombre de la subdivisión",
      "Código del idioma",
      "Subdivisión superior"
    ],
    "ignore_missing": true
  }
}

    Elimina del documento los campos “raw” usados en la importación:

    • Código 3166-2
    • Categoría de la subdivisión
    • Nombre de la subdivisión
    • Código del idioma
    • Subdivisión superior

    Con ignore_missing: true el pipeline no falla si alguno de esos campos no viene en el documento.

    Resultado: el _source final queda limpio y alineado con tu mapping.

    Ejemplo completo: antes → después

    Entrada (documento raw)

    {
  "Código 3166-2": "ES-SE",
  "Categoría de la subdivisión": "province",
  "Nombre de la subdivisión": "Sevilla",
  "Código del idioma": "es",
  "Subdivisión superior": "Andalucía"
}

    Salida (documento final)

    {
  "provincia_code": "SE",
  "iso3166_2": "ES-SE",
  "nombre": "Sevilla",
  "ccaa": "Andalucía"
}

    Relación con dynamic: "strict"

    Si tu índice prov_ref tiene dynamic: "strict", cualquier campo no definido en el mapping provocará error al indexar.

    Este pipeline ayuda porque:

    1. Crea los campos esperados (provincia_code, iso3166_2, nombre, ccaa)
    2. Elimina los campos “extra” que vendrían del CSV

    De este modo, el documento final respeta el mapping estricto.

    Cómo probarlo con _simulate

    Puedes verificar el resultado exacto sin indexar documentos:

    POST _ingest/pipeline/prov_ref_pipeline/_simulate
{
  "docs": [
    {
      "_source": {
        "Código 3166-2": "ES-SE",
        "Categoría de la subdivisión": "province",
        "Nombre de la subdivisión": "Sevilla",
        "Código del idioma": "es",
        "Subdivisión superior": "Andalucía"
      }
    }
  ]
}

    Reindex prov_raw → prov_ref

    Para reindex grandes, mejor hacerlo asíncrono. Detalle más adelante. 

    POST _reindex
{
  "source": { "index": "prov_raw" },
  "dest":   { "index": "prov_ref", "pipeline": "prov_ref_pipeline" },
  "conflicts": "proceed"
}

    ¿Qué hace _reindex?

    _reindex copia documentos de un índice origen a un índice destino reindexando (es decir, volviendo a indexar) cada documento.

    En este caso:

    1. Lee documentos de prov_raw.
    2. Por cada documento, ejecuta el ingest pipeline prov_ref_pipeline.
    3. Indexa el documento transformado en prov_ref.
    4. Si hay conflictos de versión, los omite y continúa (por conflicts: proceed).

    Detalle de cada atributo

    1) source
    "source": { "index": "prov_raw" }
    • Indica de dónde se leen los documentos.
    • index: nombre del índice origen (prov_raw).
    • Al no especificarse más opciones, se reindexa todo el contenido del índice.

    Opcionalmente, source puede incluir query, _source, sort, slice, etc., para filtrar o paralelizar. Aquí no se usa nada de eso.

    2) dest
    "dest": { "index": "prov_ref", "pipeline": "prov_ref_pipeline" }
    • index: índice destino donde se escribirán los documentos (prov_ref).
    • pipeline: pipeline de ingestión que se ejecutará antes de indexar cada documento en prov_ref.

    En este caso, el pipeline prov_ref_pipeline: - transforma campos “raw” con espacios/acentos (ej. Código 3166-2, Nombre de la subdivisión, etc.) - crea campos finales (provincia_code, iso3166_2, nombre, ccaa) - elimina los campos originales

    Esto es muy útil si el mapping de prov_ref es estricto (dynamic: "strict"), porque evita que queden campos inesperados.

    3) conflicts
    "conflicts": "proceed"

    Controla qué hacer ante conflictos de versión durante el reindex.

    • abort (por defecto): el reindex se detiene en el primer conflicto.
    • proceed: el reindex continúa, y los documentos conflictivos se saltan.
    ¿Qué es exactamente un “conflict” aquí?

    En _reindex, conflicts se refiere a version conflicts (conflictos de versión) al escribir en el destino.

    Ejemplos típicos: - El documento a escribir en prov_ref entra en conflicto con una versión existente (según cómo se esté controlando la versión/op_type). - En algunos flujos, si se configura escritura tipo “create” (solo crear si no existe), los documentos ya existentes generarían conflictos.

    Importante: conflicts no ignora errores de ingestión o mapping. Por ejemplo: - excepciones del script del pipeline - strict_dynamic_mapping_exception por campos no permitidos - errores de parseo de tipos

    Esos aparecen como fallos (failures) y pueden detener la tarea si no se gestionan.

    ¿Qué devuelve la respuesta de _reindex?

    Al completarse, Elasticsearch/OpenSearch suele devolver contadores y, si aplica, fallos.

    Campos típicos:

    • total: documentos procesados desde el origen
    • created: documentos creados en el destino
    • updated: documentos actualizados en el destino
    • version_conflicts: cuántos se omitieron por conflictos de versión (si conflicts: proceed)
    • failures: lista de errores (pipeline/mapping/etc.)

    Interpretación clave:

    • Si version_conflicts > 0 y conflicts: proceed, el reindex termina igualmente, pero con menos documentos escritos.
    • Si failures contiene entradas, hay documentos que fallaron por causas distintas a “conflict”.

    Seguimiento de progreso y auditoría (recomendado)

    Para reindex grandes, es mejor ejecutarlo como tarea:

    1) Lanzar en modo asíncrono
    POST _reindex?wait_for_completion=false
{
  "source": { "index": "prov_raw" },
  "dest":   { "index": "prov_ref", "pipeline": "prov_ref_pipeline" },
  "conflicts": "proceed"
}

    Esto devuelve un task id.

    2) Consultar progreso
    GET _tasks/<task_id>

    Cuando termine, el resultado final suele aparecer en: - completed: true - dentro de response: contadores (created, updated, version_conflicts) y failures si los hubo.

    Seguimiento de errores “en serio”: índice de errores (dead‑letter)

    Si quieres que el proceso no se pare por errores de ingestión o mapping, y a la vez guardar trazabilidad, una estrategia habitual es:

    1. Añadir un bloque on_failure al pipeline.
    2. En caso de fallo, guardar el documento en un índice de errores (por ejemplo prov_ref_errors) junto con metadatos de la causa.
    Ejemplo de on_failure en pipeline
    PUT _ingest/pipeline/prov_ref_pipeline
{
  "processors": [
    ... tus processors ...
  ],
  "on_failure": [
    { "set": { "field": "ingest_error.message", "value": "{{ _ingest.on_failure_message }}" } },
    { "set": { "field": "ingest_error.processor_type", "value": "{{ _ingest.on_failure_processor_type }}" } },
    { "set": { "field": "ingest_error.processor_tag", "value": "{{ _ingest.on_failure_processor_tag }}" } },
    { "set": { "field": "ingest_error.pipeline", "value": "{{ _ingest.on_failure_pipeline }}" } },
    { "script": { "lang": "painless", "source": "ctx._index = 'prov_ref_errors';" } }
  ]
}

    Qué consigue esto - Documentos OK → prov_ref - Documentos con error → prov_ref_errors con detalle del fallo

    Recomendación: crea prov_ref_errors con un mapping más flexible (sin dynamic: strict) para evitar que el propio índice de errores provoque más fallos.

    Construcción de trams_ref

    Crear índice

    DELETE trams_ref

PUT trams_ref
{
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "cod":  { "type": "integer" },
      "desc": { "type": "keyword" }
    }
  }
}

    Pipeline trams_ref_pipeline

    PUT _ingest/pipeline/trams_ref_pipeline
{
  "processors": [
    {
      "script": {
        "lang": "painless",
        "source": """
          if (ctx.containsKey('cod') && ctx.cod != null) {
            def c = ctx.cod;
            if (c instanceof Number) {
              ctx.cod = ((Number)c).intValue();
            } else {
              ctx.cod = Integer.parseInt(c.toString().trim());
            }
          }
          if (ctx.containsKey('desc') && ctx.desc != null) {
            ctx.desc = ctx.desc.toString();
          }
        """
      }
    }
  ]
}

    Crear y ejecutar Enrich Policies

    Una enrich policy define una forma de hacer “lookups” (búsquedas tipo tabla de referencia) durante la ingestión de documentos mediante un ingest pipeline.

    En lugar de que tu aplicación tenga que:

    • consultar una tabla/índice de referencia aparte, o
    • hacer joins fuera de Elasticsearch,

    Elasticsearch puede añadir automáticamente campos “descriptivos” a los documentos que estás indexando.

    Provincias (por provincia_code)

    PUT /_enrich/policy/prov_by_code
{
  "match": {
    "indices": "prov_ref",
    "match_field": "provincia_code",
    "enrich_fields": ["iso3166_2", "nombre", "ccaa"]
  }
}

POST /_enrich/policy/prov_by_code/_execute

    ¿Qué significa cada atributo?

    prov_by_code (nombre de la policy)
    • Es el identificador de la policy.
    • Se usará más tarde en un processor enrich dentro de un pipeline:
    • policy_name: "prov_by_code"

    Bloque match

    Indica que es una policy de tipo match: se resuelve por coincidencia exacta (ideal para códigos/IDs, campos keyword).

    Existen otros tipos (según versión): range y geo_match, pero aquí no aplican.

    indices: "prov_ref"

    • El índice fuente (la “tabla de referencia”) desde el que se va a enriquecer.
    • En tu caso, prov_ref contiene la información de provincia (código, ISO, nombre, CCAA…).

    match_field: "provincia_code"

    • Campo clave en prov_ref que se usará para encontrar el registro.
    • Es el equivalente a una clave de JOIN (por ejemplo, provincia_code = "SE").
    • Normalmente se recomienda que sea keyword, porque el match es exacto.

    enrich_fields: ["iso3166_2", "nombre", "ccaa"]

    • Lista de campos que se copiarán desde prov_ref al documento que estás indexando cuando exista match.
    • Es decir: cuando el código coincida, trae:
    • iso3166_2
    • nombre
    • ccaa

    2) Ejecutar (materializar) la policy: POST .../_execute

    POST /_enrich/policy/prov_by_code/_execute

    ¿Por qué hace falta _execute?

    Crear la policy solo define “la receta”. Con _execute:

    • Elasticsearch construye un índice interno de enrich (un snapshot optimizado) a partir de prov_ref.
    • Ese índice interno suele tener un nombre del estilo:
    • .enrich-prov_by_code-...

    Ventaja: los enrich durante ingestión son rápidos porque consultan ese índice interno optimizado.

    Importante: no es “live”

    La enrich policy no se actualiza automáticamente si cambia prov_ref.

    • Si añades/modificas datos en prov_ref, debes volver a ejecutar:
    • POST /_enrich/policy/prov_by_code/_execute

    ¿Para qué sirve en la práctica?

    Sirve para que, al indexar documentos “de negocio” o “de eventos” que solo contienen un código, Elasticsearch complete automáticamente la información.

    Ejemplo:

    • Entra un documento con: provincia_code: "SE"
    • El enrich añade: nombre, ccaa, iso3166_2

    Esto evita:

    • duplicar tablas en la app,
    • hacer consultas extra por documento,
    • o mantener joins externos.

    Pipeline final covid_pipeline

    El pipeline convierte documentos COVID “raw” a un formato listo para analítica:

    1. Trazabilidad: guarda fecha_raw y elimina fecha.
    2. Time series: crea @timestamp desde fecha (a medianoche UTC).
    3. Normalización: limpia provincia_iso/provincia_code (trim + mayúsculas).
    4. Tipado: convierte num_casos, num_hosp, num_uci, num_def a int.
    5. Enrich de provincia: añade ISO/nombre/CCAA usando prov_by_code.
    6. Derivados:
    7. grupo_edad_orden para ordenar grupos de edad.
    8. alarma_cod según el rango de fecha.
    9. Enrich de tramo de alarma: añade descripción con tram_by_cod.
    10. Estructura final: crea objetos provincia y alarma, y elimina campos auxiliares.

    Creación

    DELETE _ingest/pipeline/covid_pipeline

PUT _ingest/pipeline/covid_pipeline
{
  "description": "COVID raw -> enriched (timestamp + enrich provincias + tramo alarma + tipos int)",
  "processors": [
    {
      "script": {
        "lang": "painless",
        "source": """
          // Guarda la fecha original por trazabilidad
          if (ctx.containsKey('fecha') && ctx.fecha != null) {
            ctx.fecha_raw = ctx.fecha.toString();
            ctx.fecha = ctx.fecha.toString().trim();
          }

          // Normaliza provincia
          if (ctx.containsKey('provincia_iso') && ctx.provincia_iso != null) {
            ctx.provincia_iso = ctx.provincia_iso.toString().trim().toUpperCase();
          }

          // Métricas -> int (acepta Number, string, string vacío)
          def nums = ['num_casos','num_hosp','num_uci','num_def'];
          for (def f : nums) {
            if (!ctx.containsKey(f) || ctx[f] == null) continue;
            def v = ctx[f];
            try {
              if (v instanceof Number) ctx[f] = ((Number)v).intValue();
              else {
                def s = v.toString().trim();
                ctx[f] = (s.length() == 0) ? 0 : Integer.parseInt(s);
              }
            } catch (Exception e) {
              ctx[f] = 0;
              ctx.ingest_error = 'metric_parse_failed';
            }
          }

          // @timestamp desde fecha: primeros 10 chars y valida con LocalDate.parse()
          if (ctx.containsKey('fecha') && ctx.fecha != null) {
            String s = ctx.fecha.toString().trim();
            String d = (s.length() >= 10) ? s.substring(0,10) : s;

            try {
              java.time.LocalDate.parse(d);
              ctx['@timestamp'] = d + 'T00:00:00.000Z';
            } catch (Exception e) {
              ctx.ingest_error = 'date_parse_failed';
            }
          } else {
            ctx.ingest_error = 'missing_fecha';
          }

          ctx.remove('fecha');
        """
      }
    },

    { "rename": { "field": "provincia_iso", "target_field": "provincia_code", "ignore_missing": true } },

    {
      "script": {
        "lang": "painless",
        "source": """
          if (ctx.containsKey('provincia_code') && ctx.provincia_code != null) {
            ctx.provincia_code = ctx.provincia_code.toString().trim().toUpperCase();
          }
        """
      }
    },

    { "enrich": { "policy_name": "prov_by_code", "field": "provincia_code", "target_field": "provincia" } },

    {
      "script": {
        "lang": "painless",
        "source": """
          if (ctx.provincia == null) ctx.provincia = new HashMap();
          if (ctx.containsKey('provincia_code') && ctx.provincia_code != null) {
            ctx.provincia.put('code', ctx.provincia_code.toString());
          }
          ctx.remove('provincia_code');

          // grupo_edad_orden
          if (ctx.grupo_edad != null) {
            def m = /^(\\d+)/.matcher(ctx.grupo_edad.toString());
            if (m.find()) ctx.grupo_edad_orden = Integer.parseInt(m.group(1));
          }

          // alarma_cod (ENTERO)
          int cod = 99;
          if (ctx.containsKey('@timestamp') && ctx['@timestamp'] != null) {
            String ts = ctx['@timestamp'].toString();
            String dp = ts.substring(0,10);
            def date = java.time.LocalDate.parse(dp);

            def d1  = java.time.LocalDate.parse('2020-03-14');
            def d2  = java.time.LocalDate.parse('2020-03-27');
            def d3  = java.time.LocalDate.parse('2020-04-10');
            def d4  = java.time.LocalDate.parse('2020-04-24');
            def d5  = java.time.LocalDate.parse('2020-05-08');
            def d6  = java.time.LocalDate.parse('2020-05-22');
            def d7  = java.time.LocalDate.parse('2020-06-05');
            def end = java.time.LocalDate.parse('2020-06-21');

            if (date.isBefore(d1) || date.isAfter(end)) cod = 99;
            else if (!date.isBefore(d7)) cod = 7;
            else if (!date.isBefore(d6)) cod = 6;
            else if (!date.isBefore(d5)) cod = 5;
            else if (!date.isBefore(d4)) cod = 4;
            else if (!date.isBefore(d3)) cod = 3;
            else if (!date.isBefore(d2)) cod = 2;
            else cod = 1;
          }
          ctx.alarma_cod = cod;
        """
      }
    },

    { "enrich": { "policy_name": "tram_by_cod", "field": "alarma_cod", "target_field": "alarma_meta" } },

    {
      "script": {
        "lang": "painless",
        "source": """
          if (ctx.alarma == null) ctx.alarma = new HashMap();

          int cod = (ctx.alarma_cod instanceof Number)
            ? ((Number)ctx.alarma_cod).intValue()
            : Integer.parseInt(ctx.alarma_cod.toString().trim());

          ctx.alarma.put('cod', cod);

          if (ctx.alarma_meta != null && ctx.alarma_meta.desc != null) {
            ctx.alarma.put('desc', ctx.alarma_meta.desc.toString());
          }

          ctx.remove('alarma_cod');
          ctx.remove('alarma_meta');
        """
      }
    }
  ]
}
