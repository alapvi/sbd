    Laboratorio 1: extracción de PostgreSQL y conversión a JSON

    Objetivos

    En este laboratorio se construirá un flujo ETL sencillo para extraer información desde PostgreSQL, convertir el resultado a formato JSON y almacenarlo en un fichero.

    Al finalizar serás capaz de:

    • Configurar una conexión JDBC mediante DBCPConnectionPool.
    • Extraer registros de PostgreSQL.
    • Convertir los resultados SQL a formato JSON.
    • Guardar el resultado mediante PutFile.
    • Comprobar el contenido generado.
    • Identificar los errores más habituales.

    1. Escenario

    Una empresa dispone de una tabla PostgreSQL denominada clientes. Se necesita extraer periódicamente su contenido y generar un fichero JSON que pueda ser consumido por otro sistema.

    La tabla contiene la siguiente información:

    Campo Descripción
    id Identificador del cliente
    nombre Nombre del cliente
    email Correo electrónico
    ciudad Ciudad de residencia

    El resultado se almacenará en:

    /datos/salida/clientes.json

    2. Arquitectura del laboratorio

    El flujo seguirá las tres fases propias de un proceso ETL:

    flowchart LR
    E["Extract<br/>PostgreSQL"]
    T["Transform<br/>Records a JSON"]
    L["Load<br/>Fichero JSON"]

    E --> T
    T --> L

    En Apache NiFi se implementará mediante:

    flowchart LR
    G["GenerateFlowFile"]
    SQL["ExecuteSQLRecord"]
    FILE["PutFile"]

    DBCP["DBCPConnectionPool"]
    WRITER["JsonRecordSetWriter"]
    DB[(PostgreSQL)]
    OUTPUT["clientes.json"]

    G --> SQL
    SQL --> FILE

    SQL -.-> DBCP
    SQL -.-> WRITER
    DBCP --> DB
    FILE --> OUTPUT

    3. Componentes utilizados

    Componente Función
    GenerateFlowFile Activa la ejecución del flujo
    ExecuteSQLRecord Ejecuta la consulta SQL
    DBCPConnectionPool Proporciona la conexión JDBC
    JsonRecordSetWriter Convierte las filas SQL a JSON
    PutFile Guarda el resultado en el sistema de archivos

    GenerateFlowFile únicamente actúa como disparador. Su contenido no se utilizará durante la consulta.

    4. Preparación de PostgreSQL

    El laboratorio utilizará la base de datos:

    clientes_db

    y la tabla:

    CREATE TABLE clientes (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    email VARCHAR(150) NOT NULL,
    ciudad VARCHAR(100)
);

    Añadir algunos registros:

    INSERT INTO clientes (nombre, email, ciudad)
VALUES
    ('Ana López', 'ana@empresa.com', 'Valencia'),
    ('Carlos Ruiz', 'carlos@empresa.com', 'Madrid'),
    ('Laura Pérez', 'laura@empresa.com', 'Sevilla');

    Comprobar el contenido:

    SELECT *
FROM clientes
ORDER BY id;

    Resultado esperado:

     id |    nombre    |        email         |  ciudad
----+--------------+----------------------+----------
  1 | Ana López    | ana@empresa.com      | Valencia
  2 | Carlos Ruiz  | carlos@empresa.com   | Madrid
  3 | Laura Pérez  | laura@empresa.com    | Sevilla

    5. Preparación del directorio de salida

    Si NiFi se ejecuta mediante Docker, debe existir un volumen que permita acceder a los ficheros desde el host.

    Añadir al servicio NiFi:

    volumes:
  - /opt/nifi/datos:/datos

    Crear el directorio en el host:

    mkdir -p /opt/nifi/datos/salida

    Asignar permisos para el laboratorio:

    chmod -R 777 /opt/nifi/datos

    La correspondencia será:

    Host:        /opt/nifi/datos
Contenedor:  /datos

    Por tanto, PutFile escribirá dentro del contenedor en:

    /datos/salida

    y el fichero podrá consultarse desde el host en:

    /opt/nifi/datos/salida

    6. Crear DBCPConnectionPool

    Dentro del Process Group del laboratorio, abrir:

    Configure → Controller Services

    Añadir:

    DBCPConnectionPool

    Asignar el nombre:

    DBCP-POSTGRESQL-CLIENTES

    Configurar:

    Propiedad Valor
    Database Connection URL jdbc:postgresql://postgres:5432/clientes_db
    Database Driver Class Name org.postgresql.Driver
    Database Driver Location(s) /opt/nifi/drivers/postgresql.jar
    Database User nifi
    Password nifi123
    Max Total Connections 8
    Max Wait Time 5 sec
    Validation Query SELECT 1

    Guardar y habilitar el servicio.

    Note

    Si PostgreSQL se ejecuta en otro contenedor del mismo Docker Compose, debe utilizarse el nombre del servicio, por ejemplo `postgres`, y no `localhost`.

    7. Crear JsonRecordSetWriter

    Añadir otro Controller Service:

    JsonRecordSetWriter

    Asignar el nombre:

    JSON-WRITER-CLIENTES

    Configurar:

    Propiedad Valor
    Schema Write Strategy Do Not Write Schema
    Pretty Print JSON true

    Guardar y habilitar.

    Este servicio recibirá las filas obtenidas desde PostgreSQL y generará un documento JSON.

    8. Crear GenerateFlowFile

    Añadir un Processor:

    GenerateFlowFile

    Asignar el nombre:

    Iniciar exportación

    Configurar:

    Propiedad Valor
    Run Schedule 1 hour
    Custom Text exportar_clientes
    Batch Size 1

    Durante el laboratorio debe ejecutarse mediante:

    Run Once

    De esta forma se evita generar ficheros continuamente.

    9. Crear ExecuteSQLRecord

    Añadir:

    ExecuteSQLRecord

    Asignar el nombre:

    Extraer clientes

    Configurar:

    Propiedad Valor
    Database Connection Pooling Service DBCP-POSTGRESQL-CLIENTES
    Record Writer JSON-WRITER-CLIENTES
    SQL select query Consulta SQL

    Consulta:

    SELECT
    id,
    nombre,
    email,
    ciudad
FROM clientes
ORDER BY id;

    Este Processor:

    1. Obtiene una conexión de DBCPConnectionPool.
    2. Ejecuta la consulta.
    3. Convierte cada fila en un Record.
    4. Entrega los Records a JsonRecordSetWriter.
    5. Sustituye el contenido del FlowFile por el JSON generado.
    sequenceDiagram
    participant G as GenerateFlowFile
    participant S as ExecuteSQLRecord
    participant D as DBCPConnectionPool
    participant DB as PostgreSQL
    participant W as JsonRecordSetWriter

    G->>S: FlowFile de activación
    S->>D: Solicitar conexión
    D-->>S: Conexión JDBC
    S->>DB: Ejecutar SELECT
    DB-->>S: Filas de clientes
    S->>W: Enviar Records
    W-->>S: Documento JSON

    10. Preparar el nombre del fichero

    Añadir un Processor:

    UpdateAttribute

    Asignar el nombre:

    Definir nombre de salida

    Crear la propiedad dinámica:

    filename = clientes.json

    El flujo quedará:

    flowchart LR
    G["GenerateFlowFile"]
    SQL["ExecuteSQLRecord"]
    U["UpdateAttribute"]
    FILE["PutFile"]

    G --> SQL
    SQL --> U
    U --> FILE

    Para conservar un histórico puede utilizarse:

    filename = clientes_${now():format("yyyyMMdd_HHmmss")}.json

    Ejemplo:

    clientes_20260731_180500.json

    11. Crear PutFile

    Añadir:

    PutFile

    Asignar el nombre:

    Guardar clientes JSON

    Configurar:

    Propiedad Valor
    Directory /datos/salida
    Conflict Resolution Strategy replace
    Create Missing Directories true

    Conectar:

    GenerateFlowFile
        ↓
ExecuteSQLRecord
        ↓
UpdateAttribute
        ↓
PutFile

    Gestionar las relaciones:

    flowchart LR
    G["GenerateFlowFile"]
    SQL["ExecuteSQLRecord"]
    U["UpdateAttribute"]
    FILE["PutFile"]
    OK["LogAttribute<br/>success"]
    ERROR["LogAttribute<br/>failure"]

    G --> SQL
    SQL -->|success| U
    SQL -->|failure| ERROR
    U --> FILE
    FILE -->|success| OK
    FILE -->|failure| ERROR

    12. Ejecutar el flujo

    El orden recomendado es:

    1. Iniciar los LogAttribute.
    2. Iniciar PutFile.
    3. Iniciar UpdateAttribute.
    4. Iniciar ExecuteSQLRecord.
    5. Ejecutar GenerateFlowFile mediante Run Once.

    El FlowFile debe recorrer el flujo hasta la relación success.

    13. Comprobar el resultado

    Desde el host:

    ls -l /opt/nifi/datos/salida

    Debe aparecer:

    clientes.json

    Mostrar el contenido:

    cat /opt/nifi/datos/salida/clientes.json

    Resultado esperado:

    [
  {
    "id": 1,
    "nombre": "Ana López",
    "email": "ana@empresa.com",
    "ciudad": "Valencia"
  },
  {
    "id": 2,
    "nombre": "Carlos Ruiz",
    "email": "carlos@empresa.com",
    "ciudad": "Madrid"
  },
  {
    "id": 3,
    "nombre": "Laura Pérez",
    "email": "laura@empresa.com",
    "ciudad": "Sevilla"
  }
]

    También puede comprobarse desde el contenedor:

    docker exec nifi \
cat /datos/salida/clientes.json

    14. Comprobar el contenido antes de PutFile

    Para observar el FlowFile antes de guardarlo:

    1. Detener PutFile.
    2. Ejecutar nuevamente el flujo.
    3. Abrir la Queue anterior a PutFile.
    4. Seleccionar List Queue.
    5. Abrir el FlowFile.
    6. Seleccionar View Content.

    Esto permite comprobar que ExecuteSQLRecord y JsonRecordSetWriter han generado correctamente el JSON.

    15. Data Provenance

    Abrir Data Provenance y localizar el FlowFile generado.

    Podrán observarse eventos relacionados con:

    • Creación del FlowFile.
    • Modificación del contenido.
    • Escritura en el sistema de archivos.
    • Finalización del flujo.

    El detalle de Provenance permite consultar:

    • Atributos originales.
    • Atributos actualizados.
    • Tamaño del contenido.
    • Processor que realizó cada operación.
    • Duración.
    • Linaje del FlowFile.
    flowchart LR
    CREATE["CREATE<br/>GenerateFlowFile"]
    MODIFY["CONTENT_MODIFIED<br/>ExecuteSQLRecord"]
    ATTR["ATTRIBUTES_MODIFIED<br/>UpdateAttribute"]
    SEND["SEND<br/>PutFile"]

    CREATE --> MODIFY
    MODIFY --> ATTR
    ATTR --> SEND

    Los nombres exactos de los eventos pueden variar según la operación y la versión.

    16. Errores frecuentes

    El DBCPConnectionPool no se habilita

    Comprobar:

    • URL JDBC.
    • Driver.
    • Ruta del JAR.
    • Usuario.
    • Contraseña.
    • Estado de PostgreSQL.

    ClassNotFoundException

    Mensaje:

    ClassNotFoundException: org.postgresql.Driver

    Comprobar el driver:

    docker exec nifi \
ls -l /opt/nifi/drivers

    Connection refused

    Mensaje:

    Connection refused

    Comprobar PostgreSQL:

    docker ps

    Y la conectividad:

    docker exec nifi \
bash -c 'echo > /dev/tcp/postgres/5432'

    UnknownHostException

    Comprobar la resolución:

    docker exec nifi \
getent hosts postgres

    Ambos contenedores deben pertenecer a la misma red Docker.

    PutFile escribe dentro del contenedor

    Comprobar el montaje:

    docker inspect nifi \
--format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'

    Debe aparecer:

    /opt/nifi/datos -> /datos

    Permission denied

    Asignar permisos al directorio del host:

    chmod -R 777 /opt/nifi/datos

    En un entorno de producción deben utilizarse permisos y propietarios más restrictivos.

    El fichero ya existe

    Si la estrategia es fail, PutFile enviará el FlowFile por failure.

    Configurar:

    Conflict Resolution Strategy = replace

    o utilizar un nombre con fecha y hora.

    El JSON aparece vacío

    Comprobar directamente la consulta:

    SELECT
    id,
    nombre,
    email,
    ciudad
FROM clientes;

    Si no existen registros, el resultado puede ser:

    []

    17. Reto adicional

    Modificar la consulta para exportar únicamente los clientes de Valencia:

    SELECT
    id,
    nombre,
    email,
    ciudad
FROM clientes
WHERE ciudad = 'Valencia'
ORDER BY id;

    Nombre del fichero:

    clientes_valencia.json

    Resultado:

    [
  {
    "id": 1,
    "nombre": "Ana López",
    "email": "ana@empresa.com",
    "ciudad": "Valencia"
  }
]

    18. Reto avanzado

    Añadir información calculada directamente en la consulta:

    SELECT
    id,
    UPPER(nombre) AS nombre,
    LOWER(email) AS email,
    UPPER(ciudad) AS ciudad,
    CURRENT_TIMESTAMP AS fecha_exportacion
FROM clientes
ORDER BY id;

    Resultado aproximado:

    [
  {
    "id": 1,
    "nombre": "ANA LÓPEZ",
    "email": "ana@empresa.com",
    "ciudad": "VALENCIA",
    "fecha_exportacion": "2026-07-31T18:00:00"
  }
]

    En este caso, parte de la transformación se realiza directamente en PostgreSQL.

    Resumen

    En este laboratorio se ha construido un flujo ETL completo:

    flowchart LR
    EXTRACT["Extract<br/>PostgreSQL"]
    TRANSFORM["Transform<br/>SQL Records a JSON"]
    LOAD["Load<br/>PutFile"]

    EXTRACT --> TRANSFORM
    TRANSFORM --> LOAD

    Se han utilizado:

    • DBCPConnectionPool, para gestionar la conexión JDBC.
    • ExecuteSQLRecord, para extraer registros.
    • JsonRecordSetWriter, para generar JSON.
    • UpdateAttribute, para definir el nombre del fichero.
    • PutFile, para guardar el resultado.

    El flujo final es:

    GenerateFlowFile
        ↓
ExecuteSQLRecord
        ↓
UpdateAttribute
        ↓
PutFile

    Este patrón puede reutilizarse para:

    • Exportar datos periódicamente.
    • Generar ficheros de intercambio.
    • Crear copias para auditoría.
    • Alimentar aplicaciones externas.
    • Preparar datos para su envío a APIs, Kafka o almacenamiento en la nube.

    Laboratorio 2: consumo de API REST y carga en PostgreSQL

    Objetivos

    En este laboratorio se construirá un flujo ETL para consumir datos JSON desde una API REST, transformarlos al esquema relacional y cargarlos en PostgreSQL.

    Al finalizar serás capaz de:

    • Consultar una API HTTP con InvokeHTTP.
    • Convertir JSON en registros mediante JsonTreeReader.
    • Insertar registros en PostgreSQL con PutDatabaseRecord.
    • Manejar respuestas correctas y errores.
    • Verificar la carga en base de datos.

    1. Escenario

    Un servicio externo expone un endpoint con pedidos en formato JSON. Se necesita cargar estos pedidos en la tabla pedidos de PostgreSQL cada cierto tiempo.

    Endpoint de ejemplo:

    http://api-pedidos:8080/pedidos

    Ejemplo de respuesta JSON:

    [
  {
    "id_pedido": 1001,
    "cliente": "Ana López",
    "total": 59.90,
    "estado": "PAGADO"
  },
  {
    "id_pedido": 1002,
    "cliente": "Carlos Ruiz",
    "total": 120.50,
    "estado": "PENDIENTE"
  }
]

    2. Arquitectura del laboratorio

    flowchart LR
    E["Extract<br/>API REST"]
    T["Transform<br/>JSON a Records"]
    L["Load<br/>PostgreSQL"]

    E --> T
    T --> L

    Implementación en NiFi:

    flowchart LR
    G["GenerateFlowFile"]
    H["InvokeHTTP"]
    DBW["PutDatabaseRecord"]

    DBCP["DBCPConnectionPool"]
    READER["JsonTreeReader"]
    API[("API pedidos")]
    PG[("PostgreSQL")]

    G --> H
    H --> DBW
    H -->|failure| ERR["LogAttribute<br/>http_error"]

    H --> API
    DBW -.-> DBCP
    DBW -.-> READER
    DBCP --> PG
    DBW -->|success| OK["LogAttribute<br/>db_ok"]
    DBW -->|failure| ERRDB["LogAttribute<br/>db_error"]

    3. Preparación de PostgreSQL

    Crear tabla destino:

    CREATE TABLE pedidos (
    id_pedido INTEGER PRIMARY KEY,
    cliente VARCHAR(120) NOT NULL,
    total NUMERIC(10,2) NOT NULL,
    estado VARCHAR(30) NOT NULL,
    fecha_carga TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

    4. Configurar Controller Services

    DBCPConnectionPool

    Nombre recomendado:

    DBCP-POSTGRESQL-PEDIDOS

    Valores clave:

    Propiedad Valor
    Database Connection URL jdbc:postgresql://postgres:5432/clientes_db
    Database Driver Class Name org.postgresql.Driver
    Database Driver Location(s) /opt/nifi/drivers/postgresql.jar
    Database User nifi
    Password nifi123

    JsonTreeReader

    Nombre recomendado:

    JSON-READER-PEDIDOS

    Valores clave:

    Propiedad Valor
    Schema Access Strategy Infer Schema
    Date Format yyyy-MM-dd
    Timestamp Format yyyy-MM-dd'T'HH:mm:ss

    Guardar y habilitar ambos servicios.

    5. Crear los Processors

    GenerateFlowFile

    Usar como disparador del flujo:

    Propiedad Valor
    Run Schedule 15 min
    Batch Size 1
    Custom Text run_api

    InvokeHTTP

    Nombre:

    Consumir API pedidos

    Configurar:

    Propiedad Valor
    HTTP Method GET
    Remote URL http://api-pedidos:8080/pedidos
    Follow Redirects true
    Content-Type application/json
    Read Timeout 30 sec
    Put Response Body In Attribute dejar vacío

    PutDatabaseRecord

    Nombre:

    Insertar pedidos

    Configurar:

    Propiedad Valor
    Record Reader JSON-READER-PEDIDOS
    Database Type PostgreSQL
    Statement Type INSERT
    Table Name pedidos
    Catalog Name vacío
    Schema Name public
    Database Connection Pooling Service DBCP-POSTGRESQL-PEDIDOS

    6. Conexiones y relaciones

    Conectar en este orden:

    GenerateFlowFile
        ↓
InvokeHTTP
        ↓
PutDatabaseRecord

    Gestionar relaciones:

    • InvokeHTTP.success -> PutDatabaseRecord
    • InvokeHTTP.failure -> LogAttribute http_error
    • InvokeHTTP.retry -> LogAttribute http_retry
    • PutDatabaseRecord.success -> LogAttribute db_ok
    • PutDatabaseRecord.failure -> LogAttribute db_error

    7. Ejecución y validación

    1. Iniciar LogAttribute de errores y éxito.
    2. Iniciar PutDatabaseRecord.
    3. Iniciar InvokeHTTP.
    4. Ejecutar GenerateFlowFile con Run Once.

    Verificar en PostgreSQL:

    SELECT
    id_pedido,
    cliente,
    total,
    estado,
    fecha_carga
FROM pedidos
ORDER BY id_pedido;

    Si el endpoint devuelve dos pedidos como el ejemplo, deberían aparecer dos filas nuevas.

    8. Errores frecuentes

    HTTP 404 o 500

    Revisar:

    • URL del endpoint.
    • Puerto y red entre contenedores.
    • Estado de la API.

    JSON mal formado

    PutDatabaseRecord enviará por failure si el payload no es JSON válido o no coincide con el esquema inferido.

    Duplicado de clave primaria

    Si llega un id_pedido existente, PostgreSQL devolverá error por clave duplicada.

    Opciones:

    • Limpiar datos previos para pruebas.
    • Cambiar estrategia a UPDATE o UPSERT con otro patrón.

    9. Reto adicional

    Ampliar el flujo para cargar solo pedidos pagados.

    Pista: añadir QueryRecord entre InvokeHTTP y PutDatabaseRecord con una consulta similar a:

    SELECT * FROM FLOWFILE WHERE estado = 'PAGADO'

    Resumen

    Este laboratorio muestra el patrón inverso al laboratorio anterior:

    • Se extrae desde API REST en lugar de base de datos.
    • Se transforma JSON a Records.
    • Se carga en PostgreSQL en lugar de fichero.

    El diseño completo queda:

    flowchart LR
    A["GenerateFlowFile"] --> B["InvokeHTTP"]
    B -->|success| C["PutDatabaseRecord"]
    B -->|failure/retry| D["LogAttribute http_error"]
    C -->|success| E["LogAttribute db_ok"]
    C -->|failure| F["LogAttribute db_error"]
