    Capítulo 6. FlowFiles: el núcleo de Apache NiFi 2.x

    "Si los Processors representan las operaciones de un flujo de datos, los FlowFiles representan los propios datos que circulan por él. Comprender qué es un FlowFile y cómo evoluciona durante su recorrido es esencial para diseñar, mantener y depurar cualquier DataFlow en Apache NiFi."

    Objetivos

    Al finalizar este capítulo serás capaz de:

    • Comprender qué es un FlowFile.
    • Diferenciar claramente entre contenido y atributos.
    • Entender el ciclo de vida completo de un FlowFile.
    • Conocer cómo Apache NiFi almacena la información internamente.
    • Interpretar la relación entre los distintos repositorios.
    • Comprender por qué NiFi puede mover grandes volúmenes de información de forma eficiente.

    6.1 ¿Qué es un FlowFile?

    El FlowFile constituye la unidad fundamental de procesamiento en Apache NiFi.

    Cada vez que un dato entra en un flujo, NiFi lo encapsula dentro de un FlowFile. A partir de ese momento, todos los Processors trabajan sobre él hasta que el flujo finaliza.

    Un FlowFile puede representar prácticamente cualquier tipo de información:

    • un fichero CSV;
    • un documento JSON;
    • un XML;
    • una imagen;
    • un vídeo;
    • un mensaje MQTT;
    • un mensaje Kafka;
    • una respuesta de una API REST;
    • un correo electrónico;
    • cualquier secuencia de bytes.

    Es importante comprender que los Processors no intercambian directamente archivos ni mensajes, sino FlowFiles.

    flowchart LR
    A[Origen de datos] --> B[FlowFile]
    B --> C[Processor]
    C --> D[Processor]
    D --> E[Destino]

    Idea clave

    Todo lo que circula por Apache NiFi es un FlowFile.

    6.2 ¿Qué contiene un FlowFile?

    Una de las dudas más habituales cuando se comienza a trabajar con Apache NiFi consiste en pensar que un FlowFile es simplemente un archivo.

    Sin embargo, un FlowFile está formado por dos elementos completamente independientes:

    • Contenido (Content)
    • Atributos (Attributes)
    flowchart TB

    A[FlowFile]

    A --> B[Content]

    A --> C[Attributes]

    Esta separación constituye una de las características más importantes del diseño interno de Apache NiFi.

    El contenido (Content)

    El contenido representa la información que realmente queremos transportar.

    Por ejemplo:

    • un documento PDF;
    • un fichero CSV;
    • un JSON;
    • una imagen JPG;
    • un archivo ZIP.

    Si el FlowFile transporta un fichero CSV, el contenido será exactamente ese CSV.

    Si transporta una imagen, el contenido será la imagen.

    Si transporta un mensaje JSON, el contenido será dicho JSON.

    Ejemplo:

    {
  "sensor":"temperatura",
  "valor":22.7
}

    Ese JSON forma parte del Content.

    Los atributos (Attributes)

    Los atributos representan los metadatos asociados al contenido.

    Por ejemplo:

    Atributo Ejemplo
    filename datos.csv
    path /entrada
    uuid 0f8c...
    mime.type application/json
    fileSize 2048

    Los atributos permiten que los Processors tomen decisiones sin necesidad de leer completamente el contenido.

    Por ejemplo:

    • mover únicamente los PDF;
    • enviar solamente imágenes;
    • seleccionar archivos superiores a 100 MB;
    • cambiar nombres;
    • clasificar documentos.
    flowchart LR

A[FlowFile]

A --> B[Contenido]

A --> C[Atributos]

C --> D[filename]

C --> E[path]

C --> F[mime.type]

C --> G[uuid]

    6.3 ¿Dónde está realmente el contenido?

    Aquí aparece uno de los conceptos más importantes de Apache NiFi.

    Muchos usuarios piensan que el contenido se almacena dentro del propio FlowFile.

    No es así.

    El FlowFile únicamente mantiene una referencia al contenido.

    flowchart LR

FlowFile --> ContentRepository

    El contenido se encuentra almacenado dentro del Content Repository.

    El FlowFile únicamente conoce dónde localizarlo.

    Gracias a este diseño:

    • no es necesario copiar continuamente grandes archivos;
    • el consumo de memoria es reducido;
    • las operaciones son mucho más rápidas.

    Diseño eficiente

    Apache NiFi evita mover físicamente el contenido siempre que es posible. En muchas operaciones únicamente cambia la referencia al contenido almacenado en el repositorio.

    6.4 Anatomía interna de un FlowFile

    De forma simplificada, un FlowFile puede representarse mediante el siguiente esquema.

    classDiagram

class FlowFile{

UUID

Content Claim

Size

Attributes

Entry Date

Lineage

}

    Los elementos más importantes son:

    • UUID, identificador único.
    • Content Claim, referencia al contenido.
    • Size, tamaño.
    • Attributes, metadatos.
    • Entry Date, fecha de entrada.
    • Lineage, información utilizada para la trazabilidad.

    No todos estos elementos son visibles desde la interfaz gráfica, pero forman parte del modelo interno de Apache NiFi.

    6.5 El UUID

    Cada FlowFile posee un identificador único denominado UUID (Universally Unique Identifier).

    Ejemplo:

    5dc81498-a0d5-4b9b-a833-cfd0cfaa57d8

    Nunca existirán dos FlowFiles con el mismo UUID.

    Este identificador permite:

    • seguir el recorrido completo;
    • localizar un FlowFile concreto;
    • consultar Data Provenance;
    • relacionar eventos.

    Durante las tareas de depuración, el UUID constituye la referencia principal.

    flowchart LR

UUID --> Provenance

UUID --> Processor1

UUID --> Processor2

UUID --> Processor3

    6.6 El ciclo de vida de un FlowFile

    Todo FlowFile sigue un ciclo de vida similar.

    flowchart LR

A[Creación]

-->

B[Queue]

-->

C[Processor]

-->

D[Queue]

-->

E[Processor]

-->

F[Destino]

    En función del flujo diseñado, un FlowFile puede:

    • ser creado;
    • modificarse;
    • dividirse;
    • fusionarse;
    • duplicarse;
    • eliminarse.

    Cada una de estas operaciones queda registrada por Apache NiFi mediante Data Provenance.

    Observación

    Un mismo FlowFile puede atravesar decenas o incluso cientos de Processors antes de finalizar su recorrido.

    6.7 Los repositorios internos de Apache NiFi

    Una de las características que distingue a Apache NiFi de otras herramientas ETL es la forma en que almacena la información.

    Cuando un FlowFile circula por un flujo de datos, Apache NiFi no guarda toda la información en un único lugar. En su lugar, distribuye la información entre varios repositorios especializados.

    Esta arquitectura aporta importantes ventajas:

    • mejora el rendimiento;
    • reduce las operaciones de copia de datos;
    • facilita la recuperación ante fallos;
    • permite realizar auditorías completas del procesamiento.

    Los tres repositorios principales son:

    • FlowFile Repository
    • Content Repository
    • Provenance Repository
    flowchart TB

    FF[FlowFile]

    FF --> FFR[FlowFile Repository]

    FF --> CR[Content Repository]

    FF --> PR[Provenance Repository]

    Cada uno de ellos almacena un tipo de información diferente.

    6.8 FlowFile Repository

    El FlowFile Repository almacena la información necesaria para que Apache NiFi conozca el estado de cada FlowFile.

    No contiene el contenido del fichero.

    Contiene únicamente información de control.

    Entre otros datos almacena:

    • UUID
    • atributos
    • tamaño
    • referencia al contenido
    • estado actual
    • posición dentro del flujo

    Puede imaginarse como un índice.

    flowchart LR

A[FlowFile]

-->

B[FlowFile Repository]

B --> UUID

B --> Attributes

B --> ContentClaim

B --> Queue

    Gracias a este repositorio, si Apache NiFi se detiene inesperadamente, al reiniciarse puede reconstruir el estado del flujo.

    Persistencia

    El FlowFile Repository permite que NiFi continúe procesando los FlowFiles pendientes después de un reinicio inesperado.

    6.9 Content Repository

    El Content Repository almacena el contenido real de los FlowFiles.

    Aquí es donde se encuentran:

    • CSV
    • JSON
    • XML
    • imágenes
    • vídeos
    • documentos PDF
    • archivos ZIP
    • cualquier otro dato binario.

    Es importante entender que el FlowFile no contiene directamente estos datos.

    Únicamente mantiene una referencia al lugar donde están almacenados.

    flowchart LR

FlowFile

-->

ContentClaim

-->

ContentRepository

-->

Archivo

    Este diseño evita copiar continuamente grandes volúmenes de información.

    Supongamos un fichero de 5 GB.

    Si varios Processors necesitan trabajar sobre él, NiFi intentará reutilizar el mismo contenido siempre que sea posible.

    No se copiarán 5 GB en cada operación.

    Simplemente cambiarán las referencias.

    Content Claim

    La referencia utilizada por Apache NiFi para localizar el contenido recibe el nombre de Content Claim.

    Puede entenderse como un puntero.

    FlowFile
│
├── UUID
├── filename
├── path
└── Content Claim
        │
        ▼
Content Repository
        │
        ▼
archivo.csv

    Gracias al Content Claim:

    • varios FlowFiles pueden compartir temporalmente el mismo contenido;
    • las modificaciones son muy eficientes;
    • se reduce el uso del disco.

    Diseño Copy-on-Write

    Cuando un Processor modifica el contenido de un FlowFile, Apache NiFi no sobrescribe el archivo existente. En su lugar, crea un nuevo Content Claim y el FlowFile pasa a apuntar a ese nuevo contenido.

    6.10 ¿Qué ocurre cuando cambia el contenido?

    Supongamos el siguiente flujo.

    flowchart LR

A[GenerateFlowFile]

-->

B[ReplaceText]

-->

C[PutFile]

    Inicialmente:

    FlowFile
↓

Content Claim 1

↓

Contenido original

    Después de ejecutar ReplaceText:

    FlowFile
↓

Content Claim 2

↓

Nuevo contenido

    El contenido original permanece disponible hasta que Apache NiFi determina que ya no existe ningún FlowFile que lo utilice.

    Posteriormente será eliminado por las tareas internas de limpieza.

    Este comportamiento mejora la seguridad y evita inconsistencias.

    6.11 Provenance Repository

    El tercer repositorio fundamental es el Provenance Repository.

    Su misión consiste en almacenar el historial de cada FlowFile.

    Cada vez que ocurre un evento importante, Apache NiFi registra información como:

    • creación;
    • recepción;
    • envío;
    • modificación;
    • bifurcación;
    • unión;
    • eliminación.
    flowchart LR

CREATE

-->

ROUTE

-->

MODIFY

-->

SEND

-->

DROP

    Cada uno de estos eventos queda asociado al UUID del FlowFile.

    Gracias a ello es posible reconstruir completamente su recorrido.

    Información almacenada

    Un evento de Provenance puede contener información como:

    Campo Descripción
    Event ID Identificador del evento
    Event Type Tipo de operación
    Component Processor implicado
    UUID FlowFile
    Timestamp Fecha y hora
    Duration Tiempo empleado
    Attributes Antes y después del cambio

    Dependiendo de la configuración, también puede conservar una copia temporal del contenido.

    6.12 Relación entre los tres repositorios

    Los tres repositorios trabajan conjuntamente.

    flowchart TB

FlowFile

-->

FlowFileRepository

FlowFile

-->

ContentRepository

FlowFile

-->

ProvenanceRepository

FlowFileRepository --> Estado

ContentRepository --> Datos

ProvenanceRepository --> Historial

    Puede resumirse de la siguiente forma:

    Repositorio Almacena
    FlowFile Repository Estado del FlowFile
    Content Repository Contenido real
    Provenance Repository Historial del procesamiento

    6.13 ¿Por qué esta arquitectura es tan eficiente?

    Esta separación aporta numerosas ventajas.

    Evita copias innecesarias

    Si un archivo de 10 GB pasa por diez Processors, Apache NiFi no crea diez copias del archivo.

    Los distintos FlowFiles reutilizan el mismo Content Claim mientras el contenido no cambie.

    Reduce el uso de memoria

    Los Processors trabajan principalmente con referencias y atributos.

    No necesitan cargar continuamente grandes ficheros en memoria.

    Facilita la recuperación

    Ante un fallo eléctrico o un reinicio inesperado, Apache NiFi puede reconstruir el estado del flujo utilizando el FlowFile Repository.

    Permite auditoría completa

    Gracias al Provenance Repository es posible conocer:

    • quién creó un FlowFile;
    • qué Processors lo modificaron;
    • cuándo ocurrió cada cambio;
    • cuál fue su contenido;
    • dónde terminó.

    Esta característica convierte a Apache NiFi en una herramienta especialmente adecuada para entornos donde la trazabilidad es un requisito fundamental.

    Ideas clave

    Antes de continuar con el siguiente apartado conviene recordar cinco conceptos fundamentales:

    1. Un FlowFile no almacena directamente el contenido.
    2. El contenido reside en el Content Repository.
    3. El estado del FlowFile se almacena en el FlowFile Repository.
    4. El historial se registra en el Provenance Repository.
    5. Los Content Claims permiten reutilizar el contenido sin copiarlo continuamente.

    Estos conceptos serán esenciales para comprender el funcionamiento de los Processors que modifican atributos, transforman contenido o realizan operaciones de enrutamiento.

    6.15 Gestión de las colas (Queues)

    Hasta ahora hemos visto que un FlowFile pasa de un Processor a otro a través de una Connection.

    Sin embargo, una Connection no es únicamente una línea que une dos componentes.

    Cada Connection incorpora una Queue, es decir, una cola donde permanecen temporalmente los FlowFiles hasta que el siguiente Processor pueda procesarlos.

    flowchart LR

A[Processor A]

-->

Q[(Queue)]

-->

B[Processor B]

    La Queue actúa como un mecanismo de desacoplamiento entre Processors.

    Esto significa que un Processor puede continuar generando FlowFiles aunque el siguiente Processor procese los datos a una velocidad inferior, siempre que no se alcance el límite configurado.

    Idea clave

    Las colas permiten que cada Processor trabaje a su propio ritmo sin depender directamente de la velocidad del resto de componentes.

    6.16 ¿Qué información almacena una Queue?

    Cada Queue mantiene información sobre los FlowFiles que contiene.

    Entre otros datos, pueden consultarse:

    • número de FlowFiles;
    • tamaño total ocupado;
    • tiempo medio de permanencia;
    • prioridad;
    • porcentaje de utilización;
    • estado de Back Pressure.

    En la interfaz de NiFi esta información aparece sobre la propia Connection.

    Queue

FlowFiles : 12

Size : 2.3 MB

Queued : 15 s

    6.17 Back Pressure

    Uno de los mecanismos más importantes de Apache NiFi es el Back Pressure.

    Su finalidad consiste en impedir que un Processor produzca FlowFiles indefinidamente cuando el siguiente Processor no puede procesarlos.

    Supongamos el siguiente escenario.

    flowchart LR

A[GenerateFlowFile]

-->

Q[(Queue)]

-->

B[PutDatabaseRecord]

    Si la base de datos deja de responder, la Queue comenzará a crecer.

    Cuando se alcance el límite configurado, Apache NiFi detendrá automáticamente el Processor de origen.

    flowchart LR

A[GenerateFlowFile]

-- Flujo detenido -->

Q[(Queue llena)]

-.->

B[Processor lento]

    Esto evita:

    • consumir toda la memoria;
    • llenar completamente el disco;
    • provocar una sobrecarga del sistema.

    Protección automática

    El Back Pressure protege el sistema frente a productores mucho más rápidos que los consumidores.

    Configuración del Back Pressure

    Cada Connection dispone de dos límites independientes.

    Parámetro Descripción
    Back Pressure Object Threshold Número máximo de FlowFiles
    Back Pressure Data Size Threshold Tamaño máximo permitido

    Cuando cualquiera de estos límites se supera, NiFi deja de transferir nuevos FlowFiles hacia la Queue.

    6.18 Priorización de FlowFiles

    No siempre interesa procesar los FlowFiles en el orden en que llegaron.

    Apache NiFi permite modificar ese comportamiento mediante Prioritizers.

    Sin priorizador:

    1

2

3

4

    Con priorizador:

    4

1

2

3

    Existen distintos tipos de priorización.

    Por ejemplo:

    • First In First Out (FIFO)
    • Last In First Out (LIFO)
    • Prioridad por tamaño
    • Prioridad por atributo
    • Prioridad personalizada
    flowchart LR

Queue

-->

Prioritizer

-->

Processor

    Los Prioritizers resultan especialmente útiles cuando algunos FlowFiles deben procesarse antes que otros.

    6.19 Penalización (Penalization)

    En determinadas situaciones un Processor puede indicar que un FlowFile no debe volver a procesarse inmediatamente.

    En ese caso el FlowFile queda penalizado durante un tiempo.

        flowchart LR
    Processor
    -->
    Penalized FlowFile
    -->
    Espera
    -->
    Queue

    Mientras permanece penalizado, el FlowFile continúa en la Queue pero no será seleccionado para su procesamiento.

    Esto evita intentos repetitivos que probablemente volverían a fallar.

    6.20 Expiración de FlowFiles

    También es posible definir un tiempo máximo de permanencia en una Queue.

    Cuando dicho tiempo se supera, el FlowFile expira.

    Ejemplo:

    FlowFile Expiration

30 min

    Una vez expirado, Apache NiFi puede:

    • descartarlo;
    • dirigirlo hacia otra Relationship;
    • registrar el evento en Provenance.

    La expiración resulta útil cuando los datos dejan de tener valor pasado un determinado tiempo.

    6.21 FlowFile Swap

    Cuando el número de FlowFiles pendientes es muy elevado, mantenerlos todos en memoria resultaría ineficiente.

    Apache NiFi utiliza entonces un mecanismo denominado FlowFile Swap.

    flowchart LR

RAM

-->

Swap

-->

RAM

    Los FlowFiles menos utilizados se trasladan temporalmente al disco.

    Cuando vuelven a ser necesarios, NiFi los recupera automáticamente.

    Este proceso es completamente transparente para el usuario.

    Note

    El FlowFile Swap no modifica el contenido del FlowFile; únicamente cambia dónde se mantiene temporalmente su información de estado.

    6.22 Relación entre Queue, Swap y Back Pressure

    Estos tres mecanismos trabajan conjuntamente.

    flowchart LR

Processor

-->

Queue

-->

BackPressure

-->

Swap

-->

Processor

    Cada uno tiene una finalidad distinta.

    Mecanismo Función
    Queue Almacenar temporalmente FlowFiles
    Back Pressure Limitar el crecimiento de la cola
    Swap Reducir el consumo de memoria

    6.23 Buenas prácticas

    A medida que los flujos aumentan de tamaño, conviene adoptar una serie de recomendaciones.

    Mantener colas pequeñas

    Las colas muy grandes suelen indicar que existe un cuello de botella.

    Supervisar el Back Pressure

    Si una Connection permanece constantemente en Back Pressure, probablemente exista un problema en el Processor de destino.

    Utilizar Prioritizers únicamente cuando aporten valor

    La priorización añade complejidad al flujo.

    No conviene utilizarla si todos los FlowFiles pueden procesarse indistintamente.

    Evitar Queue infinitas

    Permitir un crecimiento ilimitado de las colas puede provocar un consumo excesivo de disco.

    Revisar periódicamente Data Provenance

    Permite detectar rápidamente:

    • cuellos de botella;
    • Processors lentos;
    • FlowFiles retenidos;
    • errores de configuración.

    6.24 Errores frecuentes

    Pensar que una Connection es únicamente una flecha

    No lo es.

    Cada Connection incorpora una Queue.

    Configurar un Back Pressure demasiado elevado

    Puede retrasar la detección de problemas y aumentar innecesariamente el consumo de recursos.

    Ignorar las colas

    Una Queue creciendo continuamente suele indicar un problema de rendimiento.

    Utilizar Prioritizers innecesarios

    No todos los flujos requieren procesamiento prioritario.

    No supervisar el tiempo de permanencia

    Un FlowFile retenido durante horas suele indicar una incidencia en el flujo.

    Resumen del capítulo

    En este capítulo hemos estudiado el elemento central de Apache NiFi: el FlowFile.

    Hemos aprendido que:

    • un FlowFile representa la unidad básica de procesamiento;
    • está formado por contenido y atributos;
    • el contenido reside en el Content Repository;
    • el estado se almacena en el FlowFile Repository;
    • el historial se registra en el Provenance Repository;
    • las Connections incorporan una Queue;
    • el Back Pressure protege el sistema;
    • los Prioritizers modifican el orden de procesamiento;
    • los FlowFiles pueden penalizarse, expirar o intercambiarse mediante Swap;
    • Data Provenance permite reconstruir el recorrido completo de cada FlowFile.

    Comprender estos conceptos resulta imprescindible para interpretar correctamente el funcionamiento interno de Apache NiFi y sacar el máximo partido a los Processors que se estudiarán en el siguiente capítulo.
