    Capítulo 8. Connections y Queues en Apache NiFi 2.x

    Los Processors realizan las operaciones. Las Connections permiten que los FlowFiles esperen y circulen de forma controlada entre ellas.

    Objetivos

    Al finalizar este capítulo serás capaz de:

    • Comprender qué es una Connection.
    • Diferenciar una Connection de una Relationship.
    • Explicar por qué una Connection actúa como Queue.
    • Crear y configurar Connections desde la interfaz.
    • Interpretar la información mostrada sobre una Queue.
    • Comprender cómo se almacenan los FlowFiles pendientes.
    • Seleccionar las Relationships que atraviesan una Connection.
    • Identificar el componente origen y el componente destino.
    • Comprender el comportamiento de las colas durante la ejecución.
    • Examinar, descargar y eliminar FlowFiles en espera.
    • Configurar Back Pressure.
    • Aplicar FlowFile Prioritizers.
    • Configurar FlowFile Expiration.
    • Comprender las estrategias de Load Balance en clúster.
    • Detectar acumulaciones y cuellos de botella.

    Introducción

    En los capítulos anteriores se estudiaron los dos componentes principales de un DataFlow:

    • los FlowFiles, que representan los datos;
    • los Processors, que realizan operaciones sobre esos datos.

    Sin embargo, todavía falta un elemento fundamental: el componente que permite transportar los FlowFiles entre Processors.

    Ese componente es la Connection.

    flowchart LR
    A[Processor A]
    --> C[[Connection]]
    --> B[Processor B]

    Una Connection no es únicamente una línea visual.

    También representa una Queue persistente en la que los FlowFiles pueden permanecer hasta que el siguiente componente esté preparado para procesarlos.

    flowchart LR
    A[Processor productor]
    --> Q[(Queue de FlowFiles)]
    --> B[Processor consumidor]

    Esta separación permite que ambos Processors trabajen a velocidades diferentes.

    Por ejemplo:

    • el Processor A puede generar 100 FlowFiles por segundo;
    • el Processor B puede procesar 50 FlowFiles por segundo;
    • los FlowFiles restantes permanecerán temporalmente en la Queue.
    flowchart LR
    A[Productor<br/>100 FlowFiles/s]
    --> Q[(Queue)]
    --> B[Consumidor<br/>50 FlowFiles/s]

    Idea fundamental

    Una Connection enlaza componentes, pero también desacopla sus velocidades de ejecución.

    8.1 ¿Qué es una Connection?

    Una Connection es un enlace dirigido entre dos componentes de un DataFlow.

    Normalmente conecta:

    • un Processor con otro Processor;
    • un Processor con un Process Group;
    • un Processor con un Funnel;
    • un Input Port con un Processor;
    • un Processor con un Output Port;
    • un Funnel con otro componente.
    flowchart TB
    A[Processor]
    --> B[Processor]

    C[Processor]
    --> D[[Process Group]]

    E[Input Port]
    --> F[Processor]

    G[Processor]
    --> H[Output Port]

    I[Funnel]
    --> J[Processor]

    La Connection contiene los FlowFiles que han salido del componente origen, pero todavía no han sido obtenidos por el componente destino.

    flowchart LR
    A[Origen]
    -->|Transfiere FlowFile| Q[(Connection)]
    -->|Obtiene FlowFile| B[Destino]

    Apache NiFi describe las Connections como enlaces entre Processors que actúan como colas y permiten que los procesos interactúen a velocidades diferentes. Estas colas pueden aplicar límites y mecanismos de prioridad.

    8.2 Connection y Queue

    En la interfaz de NiFi, los términos Connection y Queue están estrechamente relacionados.

    Connection

    Representa el enlace completo entre dos componentes.

    Incluye:

    • componente origen;
    • componente destino;
    • Relationships seleccionadas;
    • nombre;
    • configuración de Back Pressure;
    • priorización;
    • expiración;
    • Load Balance;
    • Queue de FlowFiles.

    Queue

    Es la parte de la Connection en la que esperan los FlowFiles.

    flowchart TB
    C[Connection]

    C --> O[Origen]
    C --> R[Relationships]
    C --> Q[Queue]
    C --> D[Destino]
    C --> BP[Back Pressure]
    C --> P[Prioritizers]

    En la práctica, cuando se selecciona la línea de una Connection, muchas de las acciones disponibles actúan sobre la Queue.

    Note

    La Connection es el enlace configurado. La Queue es el almacenamiento temporal de los FlowFiles dentro de ese enlace.

    8.3 La Connection como buffer

    Una Queue actúa como un buffer entre el productor y el consumidor.

    Supongamos este flujo:

    flowchart LR
    A[GetFile]
    --> Q[(Queue)]
    --> B[PutDatabaseRecord]

    GetFile puede leer archivos rápidamente.

    Sin embargo, PutDatabaseRecord puede depender de:

    • la velocidad de la base de datos;
    • el número de conexiones;
    • los bloqueos;
    • la latencia de red;
    • el tamaño de los lotes.

    Si la base de datos procesa más lentamente que GetFile, los FlowFiles se acumularán en la Queue.

    sequenceDiagram
    participant G as GetFile
    participant Q as Queue
    participant D as Base de datos

    G->>Q: FlowFile 1
    G->>Q: FlowFile 2
    G->>Q: FlowFile 3
    Q->>D: FlowFile 1
    G->>Q: FlowFile 4
    Q->>D: FlowFile 2

    Sin la Queue, el Processor productor tendría que esperar directamente a que finalizara el consumidor.

    Gracias a la Connection:

    • ambos componentes pueden ejecutarse de forma independiente;
    • los datos pueden absorber variaciones temporales;
    • el flujo puede recuperarse de interrupciones;
    • es posible aplicar control de carga.

    8.4 Desacoplamiento de componentes

    Una de las principales ventajas de las Connections es el desacoplamiento.

    flowchart LR
    A[Processor A]
    --> Q[(Queue)]
    --> B[Processor B]

    El Processor A no necesita conocer:

    • cuándo se ejecutará B;
    • cuánto tardará B;
    • cuántas tareas concurrentes utiliza B;
    • si B está detenido temporalmente;
    • si B se encuentra esperando un servicio externo.

    A simplemente transfiere el FlowFile a la Connection.

    Posteriormente, B lo obtiene cuando puede procesarlo.

    flowchart TB
    A[Processor A termina]
    --> B[Transfiere el FlowFile]
    --> C[(Queue persistente)]
    --> D[Processor B lo obtiene después]

    Diseño desacoplado

    Las Connections permiten construir el DataFlow como una serie de etapas independientes, unidas mediante colas controladas.

    8.5 Connection y Relationship

    Una Relationship no es lo mismo que una Connection.

    Relationship

    Representa un resultado posible de un Processor.

    Ejemplos:

    success
failure
matched
unmatched
retry
original
split

    Connection

    Representa el enlace físico y lógico por el que circulan una o varias Relationships.

    flowchart LR
    A[Processor]
    -->|Relationship success| C[[Connection]]
    --> B[Processor destino]

    La Relationship pertenece al Processor.

    La Connection utiliza esa Relationship para determinar qué FlowFiles debe recibir.

    Ejemplo

    Supongamos un EvaluateJsonPath con las relaciones:

    matched
unmatched
failure

    Podemos crear tres Connections:

    flowchart TB
    A[EvaluateJsonPath]

    A -->|matched| B[Procesamiento correcto]
    A -->|unmatched| C[Datos incompletos]
    A -->|failure| D[Errores JSON]

    Cada línea representa una Connection diferente.

    Cada Connection transporta una Relationship concreta.

    Varias Relationships en una Connection

    Una Connection puede transportar más de una Relationship.

    Por ejemplo:

    unmatched
failure

    podrían dirigirse al mismo Process Group de errores.

    flowchart TB
    A[EvaluateJsonPath]

    A -->|matched| B[Flujo normal]
    A -->|unmatched y failure| C[Gestión de errores]

    En este caso, la Connection hacia la gestión de errores incluiría dos Relationships.

    Warning

    Si varias Relationships comparten una Connection, los FlowFiles llegarán al mismo destino. Es posible conservar un atributo que permita distinguir el motivo de la ruta.

    8.6 Componentes de origen y destino

    Toda Connection tiene:

    • un Source Component;
    • un Destination Component.
    flowchart LR
    A[Source Component]
    --> C[[Connection]]
    --> B[Destination Component]

    Source Component

    Es el componente que transfiere los FlowFiles a la Connection.

    Puede ser:

    • un Processor;
    • un Input Port;
    • un Funnel;
    • un Process Group, mediante sus puertos.

    Destination Component

    Es el componente que obtiene los FlowFiles de la Queue.

    Puede ser:

    • un Processor;
    • un Output Port;
    • un Funnel;
    • un Process Group.

    Dirección de la Connection

    Las Connections son dirigidas.

    Esto significa que los FlowFiles solo circulan desde el origen hacia el destino.

    flowchart LR
    A[Origen]
    --> B[Destino]

    No circulan automáticamente en sentido contrario.

    flowchart LR
    A[Origen]
    --X B[Destino]

    Si se necesita devolver un FlowFile a una etapa anterior, debe crearse otra Connection.

    flowchart LR
    A[Validar]
    --> B[Procesar]

    B -->|retry| A

    Ciclos

    NiFi permite crear ciclos, pero deben diseñarse con cuidado para evitar reintentos infinitos o FlowFiles atrapados permanentemente.

    8.7 Creación de una Connection

    Una Connection se crea arrastrando desde un componente origen hacia un componente destino.

    Procedimiento general

    1. Sitúa ambos componentes en el lienzo.
    2. Coloca el cursor sobre el componente origen.
    3. Utiliza el controlador de conexión.
    4. Arrastra la línea hasta el componente destino.
    5. Selecciona las Relationships.
    6. Asigna opcionalmente un nombre.
    7. Guarda la configuración.
    flowchart LR
    A[Seleccionar origen]
    --> B[Arrastrar conexión]
    --> C[Seleccionar destino]
    --> D[Elegir Relationships]
    --> E[Crear Connection]

    Ejemplo

    Disponemos de:

    GenerateFlowFile
LogAttribute

    Creamos una Connection desde GenerateFlowFile hasta LogAttribute.

    La Relationship disponible será normalmente:

    success

    El resultado será:

    flowchart LR
    A[GenerateFlowFile]
    -->|success| Q[(Queue)]
    --> B[LogAttribute]

    8.8 Selección de Relationships

    Durante la creación de una Connection, NiFi muestra las Relationships disponibles en el componente origen.

    Ejemplo:

    success
failure
original

    Se puede seleccionar una o varias.

    flowchart TB
    A[Processor origen]
    --> B{Relationships}

    B --> C[success]
    B --> D[failure]
    B --> E[original]

    Solo los FlowFiles transferidos a las Relationships seleccionadas entrarán en esa Connection.

    Relationship ya utilizada

    Una Relationship puede, dependiendo del Processor y del diseño, dirigirse a una o varias Connections.

    Por ejemplo, una Relationship success puede enviarse a dos destinos:

    flowchart TB
    A[Processor]

    A -->|success| B[Destino 1]
    A -->|success| C[Destino 2]

    En este caso, NiFi puede crear copias lógicas del FlowFile para transferirlo a ambos destinos.

    Duplicación lógica

    Conectar la misma Relationship a varios destinos implica que el FlowFile continuará por varias ramas. No es un reparto alternativo automático.

    Distribución frente a duplicación

    Supongamos que success está conectada a:

    • PutFile;
    • PublishKafka.
    flowchart TB
    A[Transformar pedido]

    A -->|success| B[PutFile]
    A -->|success| C[PublishKafka]

    El pedido se enviará a ambos destinos:

    1. se guardará como archivo;
    2. se publicará en Kafka.

    No se enviará unas veces a uno y otras veces al otro.

    Para repartir alternativamente los FlowFiles deben utilizarse otros mecanismos de diseño, como:

    • rutas explícitas;
    • particionamiento;
    • balanceo en clúster;
    • estrategias específicas de distribución.

    8.9 Nombre de la Connection

    Una Connection puede tener un nombre descriptivo.

    Ejemplos:

    Pedidos validados

    Errores pendientes de reintento

    Facturas internacionales

    Mensajes para Kafka

    Esto facilita la interpretación del flujo.

    flowchart LR
    A[Validar pedido]
    -->|Pedidos válidos| B[Guardar pedido]

    Un nombre resulta especialmente útil cuando:

    • se transportan varias Relationships;
    • la ruta representa una decisión funcional;
    • existen muchas conexiones;
    • el flujo contiene ciclos;
    • se conectan Process Groups.

    Tip

    Nombra la Connection según los datos que contiene, no únicamente según el componente al que se dirige.

    8.10 La Queue durante la ejecución

    Cuando un Processor transfiere un FlowFile, este entra en la Queue.

    sequenceDiagram
    participant A as Processor A
    participant Q as Queue
    participant B as Processor B

    A->>Q: Transferir FlowFile
    Q-->>Q: FlowFile en espera
    Q->>B: Entregar FlowFile

    El FlowFile puede permanecer en la Queue porque:

    • el Processor destino está detenido;
    • el destino todavía no ha sido programado;
    • no existen hilos disponibles;
    • el destino está en yield;
    • el FlowFile está penalizado;
    • existen otros FlowFiles con mayor prioridad;
    • se está aplicando balanceo;
    • el sistema externo es lento.

    Processor destino detenido

    flowchart LR
    A[Processor A ejecutándose]
    --> Q[(Queue creciente)]
    -.-> B[Processor B detenido]

    Mientras B permanezca detenido, los FlowFiles se acumularán.

    Cuando B se inicie:

    flowchart LR
    Q[(Queue)]
    --> B[Processor B iniciado]

    comenzará a obtener FlowFiles de la Queue.

    Processor origen detenido

    flowchart LR
    A[Processor A detenido]
    -.-> Q[(Queue existente)]
    --> B[Processor B ejecutándose]

    Aunque el origen esté detenido, el destino puede continuar procesando los FlowFiles que ya estén en la Queue.

    Note

    Detener un Processor no elimina los FlowFiles que ya ha transferido.

    8.11 Persistencia de los FlowFiles en la Queue

    Los FlowFiles en espera no dependen únicamente de la memoria RAM.

    NiFi utiliza sus repositorios para conservar:

    • el estado del FlowFile;
    • los atributos;
    • la referencia a su contenido;
    • la posición dentro del flujo.
    flowchart TB
    Q[Queue]

    Q --> F[FlowFile Repository]
    Q --> C[Content Repository]
    Q --> P[Provenance Repository]

    El FlowFile Repository registra el estado y la ubicación lógica del FlowFile.

    El Content Repository conserva el contenido mediante Content Claims.

    El Provenance Repository registra los eventos relacionados con su recorrido.

    flowchart LR
    A[FlowFile en Queue]
    --> B[Metadatos en FlowFile Repository]
    --> C[Contenido referenciado en Content Repository]

    Esta arquitectura permite que los FlowFiles pendientes sobrevivan normalmente a un reinicio controlado de NiFi.

    Note

    La Queue se visualiza en el lienzo, pero su persistencia depende de los repositorios internos estudiados en el capítulo de FlowFiles.

    8.12 Información mostrada en una Connection

    La interfaz muestra información resumida sobre cada Queue.

    Normalmente puede incluir:

    • número de FlowFiles;
    • tamaño total;
    • estado de Back Pressure;
    • antigüedad del FlowFile más antiguo;
    • indicador de expiración;
    • actividad reciente.

    Ejemplo conceptual:

    125 FlowFiles / 82.4 MB

    Esto significa que la Queue contiene:

    125 objetos
82,4 MB de contenido total

    flowchart TB
    Q[Queue]

    Q --> A[Número de FlowFiles]
    Q --> B[Tamaño total]
    Q --> C[Antigüedad]
    Q --> D[Estado de presión]

    Número de FlowFiles

    Representa la cantidad de FlowFiles pendientes.

    Ejemplo:

    250 FlowFiles

    Una gran cantidad no implica necesariamente un problema.

    Depende de:

    • el tamaño de los FlowFiles;
    • la velocidad de entrada;
    • la velocidad de salida;
    • el diseño del flujo;
    • los umbrales configurados.

    Tamaño total

    Representa la suma aproximada de los contenidos referenciados por los FlowFiles.

    Ejemplo:

    2.8 GB

    Una Queue puede contener:

    • muchos FlowFiles pequeños;
    • pocos FlowFiles grandes.

    Estas dos situaciones generan cargas diferentes.

    Queue Objetos Tamaño
    A 1.000.000 500 MB
    B 10 50 GB

    La Queue A puede ejercer mayor presión sobre la gestión de metadatos.

    La Queue B puede ejercer mayor presión sobre el almacenamiento.

    FlowFile más antiguo

    La antigüedad del FlowFile más antiguo ayuda a detectar latencia acumulada.

    Ejemplo:

    Oldest FlowFile = 2 hours

    Esto indica que al menos un FlowFile lleva dos horas esperando.

    flowchart LR
    A[FlowFile entra]
    --> B[Espera en Queue]
    --> C[Antigüedad creciente]

    Latencia

    Una Queue con pocos FlowFiles también puede ser problemática si alguno lleva demasiado tiempo sin procesarse.

    8.13 Interpretación visual de una Queue

    La Connection puede cambiar su apariencia según su estado.

    Puede mostrar visualmente:

    • Queue vacía;
    • FlowFiles acumulados;
    • Back Pressure activa;
    • FlowFiles expirados o próximos a expirar;
    • transmisión balanceada;
    • datos en movimiento.

    La representación exacta puede variar entre versiones y según el tema de la interfaz.

    Tip

    No dependas únicamente del color. Revisa también los contadores, el tamaño, la antigüedad y la configuración.

    8.14 Abrir una Queue

    Al seleccionar una Connection puede utilizarse la opción List Queue.

    Esta acción permite consultar los FlowFiles que están esperando.

    flowchart LR
    A[Seleccionar Connection]
    --> B[List Queue]
    --> C[Listado de FlowFiles]

    La lista puede mostrar información como:

    • UUID;
    • posición;
    • tamaño;
    • fecha de entrada;
    • antigüedad;
    • atributos;
    • estado de penalización.

    List Queue no detiene necesariamente el flujo

    Mientras se solicita el listado, el Processor destino podría continuar consumiendo FlowFiles.

    Por tanto, la lista obtenida representa una vista temporal.

    sequenceDiagram
    participant U as Usuario
    participant Q as Queue
    participant P as Processor

    U->>Q: Solicitar listado
    Q->>P: Entregar algunos FlowFiles
    Q-->>U: Mostrar estado observado

    Note

    En una Queue activa, algunos FlowFiles pueden desaparecer de la lista porque ya han sido procesados.

    8.15 Examinar un FlowFile de la Queue

    Desde el listado puede seleccionarse un FlowFile para consultar sus detalles.

    Normalmente es posible examinar:

    • atributos;
    • contenido;
    • tamaño;
    • UUID;
    • información de Provenance;
    • posición en la Queue.
    flowchart TB
    A[FlowFile seleccionado]

    A --> B[Attributes]
    A --> C[Content]
    A --> D[Provenance]
    A --> E[Metadata]

    Visualizar atributos

    Ejemplo:

    filename = pedido_1001.json
pedido.id = 1001
cliente.pais = ES
pedido.importe = 1250
mime.type = application/json

    Esto permite comprobar si los Processors anteriores han generado los metadatos esperados.

    Visualizar contenido

    Para contenido textual puede utilizarse una vista previa.

    Ejemplo:

    {
  "pedido": 1001,
  "cliente": "Alberto",
  "pais": "ES",
  "importe": 1250
}

    Para archivos binarios, la previsualización puede no ser interpretable.

    Descargar contenido

    También puede descargarse el contenido para analizarlo externamente.

    Esto resulta útil para:

    • documentos grandes;
    • archivos binarios;
    • pruebas con validadores;
    • comparación de transformaciones;
    • análisis de errores.

    Datos sensibles

    La descarga o visualización de FlowFiles puede exponer datos personales, credenciales, tokens o información empresarial. Deben respetarse los permisos y las políticas de seguridad.

    8.16 Vaciar una Queue

    NiFi permite eliminar todos los FlowFiles pendientes mediante la acción Empty Queue.

    flowchart LR
    A[(Queue con FlowFiles)]
    --> B[Empty Queue]
    --> C[(Queue vacía)]

    Esta operación descarta los FlowFiles.

    No los envía al siguiente Processor.

    No los mueve automáticamente a una papelera.

    Cuándo puede utilizarse

    • limpieza de un laboratorio;
    • eliminación de datos de prueba;
    • reinicio de una prueba;
    • descarte consciente de información inválida;
    • retirada de una acumulación que ya no debe procesarse.

    Cuándo no debe utilizarse

    • para resolver rápidamente un atasco de producción;
    • sin conocer qué datos contiene;
    • cuando no existe una copia en el origen;
    • si los FlowFiles representan operaciones económicas;
    • si es necesario conservar trazabilidad completa.

    Operación destructiva

    `Empty Queue` provoca la eliminación de los FlowFiles pendientes. Debe comprobarse siempre el contenido y el impacto antes de confirmar.

    8.17 Eliminar una Connection

    Para eliminar una Connection normalmente debe encontrarse vacía.

    flowchart TD
    A[Eliminar Connection]
    --> B{¿Queue vacía?}

    B -->|Sí| C[Eliminar]
    B -->|No| D[Procesar o vaciar los FlowFiles]

    Si contiene datos, primero deben:

    • procesarse;
    • trasladarse mediante el flujo;
    • eliminarse conscientemente.

    Además, los componentes relacionados pueden necesitar estar detenidos.

    8.18 Modificar una Connection

    Una Connection existente puede configurarse desde su ventana de propiedades.

    Entre las opciones disponibles se encuentran:

    • nombre;
    • Relationships;
    • Back Pressure Object Threshold;
    • Back Pressure Data Size Threshold;
    • FlowFile Expiration;
    • Prioritizers;
    • Load Balance Strategy;
    • Partitioning Attribute;
    • Compression.
    flowchart TB
    C[Configure Connection]

    C --> N[Name]
    C --> R[Relationships]
    C --> B[Back Pressure]
    C --> E[Expiration]
    C --> P[Prioritizers]
    C --> L[Load Balance]

    Estas opciones se desarrollarán en las siguientes partes del capítulo.

    8.19 Conectar un Processor con varias entradas

    Un Processor puede recibir FlowFiles desde varias Connections.

    flowchart TB
    A[Origen A]
    --> Q1[(Queue A)]
    --> D[Processor destino]

    B[Origen B]
    --> Q2[(Queue B)]
    --> D

    Por ejemplo:

    flowchart TB
    A[Pedidos HTTP]
    --> D[Validar pedidos]

    B[Pedidos Kafka]
    --> D

    El Processor destino puede consumir FlowFiles de ambas colas.

    Selección entre varias Queues

    NiFi selecciona FlowFiles de las Connections de entrada según su disponibilidad y la configuración interna.

    No debe asumirse necesariamente un orden global perfecto entre varias Queues.

    flowchart TB
    Q1[(Queue A)]
    --> P[Processor]

    Q2[(Queue B)]
    --> P

    Posible secuencia:

    A1
B1
B2
A2

    Aunque las entradas originales fueran:

    Queue A: A1, A2
Queue B: B1, B2

    Orden global

    Mantener el orden dentro de una única Queue no garantiza un orden global cuando un Processor recibe datos desde varias Connections.

    8.20 Conectar una salida con varios destinos

    Una Relationship puede dirigir FlowFiles hacia varias Connections.

    flowchart TB
    A[Processor]

    A -->|success| B[Destino A]
    A -->|success| C[Destino B]

    Este patrón se utiliza cuando es necesario realizar varias operaciones con los mismos datos.

    Ejemplo:

    flowchart TB
    A[Pedido validado]

    A --> B[Guardar en PostgreSQL]
    A --> C[Publicar en Kafka]
    A --> D[Archivar en disco]

    NiFi gestiona referencias al mismo contenido y puede evitar copias físicas innecesarias mediante el modelo de Content Claims y Copy-on-Write.

    8.21 Funnels y Connections

    Un Funnel permite reunir varias Connections en una única salida.

    flowchart TB
    A[Origen A]
    --> F((Funnel))

    B[Origen B]
    --> F

    C[Origen C]
    --> F

    F --> D[Destino común]

    Resulta útil para:

    • reducir líneas visuales;
    • centralizar rutas;
    • enviar varios tipos de error a un mismo Process Group;
    • mejorar la organización del lienzo.

    Ejemplo de errores

    flowchart TB
    A[Processor A]
    -->|failure| F((Funnel de errores))

    B[Processor B]
    -->|failure| F

    C[Processor C]
    -->|failure| F

    F --> D[[Gestión de errores]]

    Note

    El Funnel no transforma los FlowFiles. Se utiliza principalmente para simplificar y reorganizar Connections.

    8.22 Connections y Process Groups

    Los Process Groups encapsulan conjuntos de componentes.

    La comunicación con su exterior se realiza mediante:

    • Input Ports;
    • Output Ports.
    flowchart LR
    A[Processor externo]
    --> I[Input Port]
    --> PG[[Process Group]]
    --> O[Output Port]
    --> B[Processor externo]

    Una Connection exterior no se conecta directamente a un Processor interno.

    Se conecta al puerto correspondiente.

    Entrada a un Process Group

    flowchart LR
    A[Flujo externo]
    --> B[Input Port]
    --> C[Flujo interno]

    Salida de un Process Group

    flowchart LR
    A[Flujo interno]
    --> B[Output Port]
    --> C[Flujo externo]

    Este mecanismo permite tratar un Process Group como un componente reutilizable.

    8.23 Connections locales y remotas

    Las Connections habituales enlazan componentes dentro del mismo flujo o clúster.

    Para comunicar distintas instancias de NiFi se utilizan mecanismos como:

    • Remote Process Groups;
    • Site-to-Site;
    • sistemas externos de mensajería;
    • HTTP;
    • Kafka.
    flowchart LR
    A[NiFi origen]
    --> R[Remote Process Group]
    --> B[NiFi destino]

    El Remote Process Group se conecta mediante Connections locales a los componentes del DataFlow.

    8.24 Ciclo de un FlowFile entre Processors

    El recorrido general de un FlowFile es:

    flowchart LR
    A[Processor A obtiene FlowFile]
    --> B[Processor A lo modifica]
    --> C[Transferencia a Relationship]
    --> D[(Connection / Queue)]
    --> E[Processor B obtiene FlowFile]

    De forma más detallada:

    sequenceDiagram
    participant Q1 as Queue de entrada
    participant A as Processor A
    participant Q2 as Queue de salida
    participant B as Processor B

    Q1->>A: Obtener FlowFile
    A->>A: Procesar
    A->>Q2: Transferir por Relationship
    Q2->>B: Obtener FlowFile

    Una vez que el FlowFile se transfiere correctamente:

    • deja la sesión del Processor anterior;
    • queda asociado a la Connection;
    • espera al siguiente componente;
    • conserva sus atributos y contenido;
    • genera eventos de Provenance según la operación.

    8.25 Transaction boundaries

    Los Processors trabajan dentro de sesiones transaccionales.

    De forma conceptual, un Processor:

    1. obtiene uno o varios FlowFiles;
    2. lee o modifica sus datos;
    3. los transfiere a Relationships;
    4. confirma la sesión.
    flowchart TD
    A[Obtener FlowFile]
    --> B[Procesar]
    --> C[Transferir]
    --> D[Commit]

    Si la sesión falla antes de confirmarse, NiFi puede revertir los cambios de la sesión.

    flowchart TD
    A[Obtener FlowFile]
    --> B[Procesar]
    --> C{¿Operación correcta?}

    C -->|Sí| D[Commit]
    C -->|No| E[Rollback]

    Las Connections marcan los límites entre las etapas confirmadas del DataFlow.

    Note

    Cuando un FlowFile aparece en una Queue, el Processor anterior ya ha completado y confirmado normalmente su transferencia.

    8.26 Detectar un cuello de botella

    Una Queue que crece de manera continuada puede indicar que el componente posterior procesa más lentamente que el anterior.

    flowchart LR
    A[Entrada rápida]
    --> Q[(Queue creciente)]
    --> B[Salida lenta]

    Posibles causas:

    • Processor destino detenido;
    • errores repetidos;
    • base de datos lenta;
    • API saturada;
    • falta de tareas concurrentes;
    • CPU insuficiente;
    • disco lento;
    • mala configuración de lotes;
    • FlowFiles penalizados;
    • reglas de priorización inadecuadas.

    Crecimiento temporal

    No toda acumulación es un problema.

    Ejemplo:

    • llegan datos intensamente durante diez minutos;
    • la Queue crece;
    • después disminuye hasta vaciarse.
    xychart-beta
    title "Crecimiento temporal de una Queue"
    x-axis [0, 5, 10, 15, 20, 25]
    y-axis "FlowFiles" 0 --> 1000
    line [0, 400, 900, 700, 300, 0]

    Crecimiento sostenido

    Si la Queue no deja de crecer, existe un desequilibrio.

    xychart-beta
    title "Crecimiento sostenido"
    x-axis [0, 5, 10, 15, 20, 25]
    y-axis "FlowFiles" 0 --> 2000
    line [0, 300, 650, 1000, 1400, 1800]

    Warning

    Un crecimiento sostenido terminará activando Back Pressure o agotando recursos si los límites no están correctamente configurados.

    8.27 Métricas básicas para analizar una Queue

    Antes de modificar el flujo conviene observar:

    Métrica Pregunta
    FlowFiles en espera ¿Cuántos objetos están acumulados?
    Tamaño total ¿Cuánto almacenamiento ocupan?
    Edad máxima ¿Cuánto lleva esperando el más antiguo?
    Entrada ¿A qué velocidad llegan?
    Salida ¿A qué velocidad se consumen?
    Back Pressure ¿Se han alcanzado los límites?
    Penalización ¿Hay FlowFiles no disponibles temporalmente?
    Errores ¿El destino está fallando? 
    flowchart TB
    Q[Analizar Queue]

    Q --> A[Cantidad]
    Q --> B[Tamaño]
    Q --> C[Antigüedad]
    Q --> D[Entrada/salida]
    Q --> E[Errores]

    8.28 Errores frecuentes

    Considerar la Connection una simple línea

    Una Connection mantiene una Queue y dispone de configuración propia.

    Confundir Relationship y Connection

    La Relationship es el resultado del Processor.

    La Connection es el enlace por el que circula ese resultado.

    Vaciar una Queue sin revisar sus datos

    Puede provocar pérdida irreversible.

    Ignorar la antigüedad

    Una Queue pequeña puede contener FlowFiles bloqueados desde hace horas.

    Conectar la misma Relationship a varios destinos sin prever duplicación

    El FlowFile continuará por todas las ramas conectadas.

    Crear ciclos sin límite

    Un FlowFile puede permanecer indefinidamente en el flujo.

    No nombrar Connections importantes

    Esto dificulta interpretar rutas complejas.

    Acumular datos sin Back Pressure

    Una Queue sin límites adecuados puede consumir todo el almacenamiento disponible.

    Suponer que varias entradas mantienen un orden global

    Cada Queue conserva su propio contexto de ordenación, pero varias entradas pueden intercalarse.

    8.29 Buenas prácticas iniciales

    Utilizar nombres funcionales

    Pedidos pendientes de validación

    es más informativo que:

    Connection 1

    Separar las rutas de error

    flowchart TB
    A[Processor]

    A -->|success| B[Flujo normal]
    A -->|failure| C[Gestión de errores]

    Revisar las Queues antes de detener NiFi

    Una detención controlada conserva normalmente los FlowFiles, pero conviene saber qué datos quedan pendientes.

    Observar número, tamaño y antigüedad

    No utilices una única métrica para evaluar la salud de la Queue.

    Evitar FlowFiles excesivamente pequeños

    Una cantidad enorme de objetos pequeños incrementa la carga de gestión.

    Diseñar explícitamente los ciclos

    Incluye:

    • contador de reintentos;
    • espera;
    • ruta definitiva;
    • Dead Letter Queue.

    No auto-terminar relaciones para eliminar avisos

    Cada Relationship debe tener un destino consciente.

    Laboratorio 1. Creación y observación de una Connection

    Objetivo

    Crear una Connection y observar cómo funciona su Queue.

    Flujo

    flowchart LR
    A[GenerateFlowFile]
    --> Q[(Queue)]
    --> B[LogAttribute]

    Configuración de GenerateFlowFile

    Contenido:

    {
  "mensaje": "Prueba de Connection",
  "curso": "Apache NiFi"
}

    Configura:

    Batch Size = 3

    Procedimiento

    1. Añade GenerateFlowFile.
    2. Añade LogAttribute.
    3. Crea una Connection entre ambos.
    4. Selecciona la Relationship success.
    5. Mantén LogAttribute detenido.
    6. Ejecuta GenerateFlowFile mediante Run Once.
    7. Observa la Queue.

    Resultado esperado

    La Connection mostrará:

    3 FlowFiles

    Los FlowFiles permanecerán en espera porque LogAttribute está detenido.

    Segunda parte

    1. Inicia LogAttribute.
    2. Observa cómo disminuye la Queue.
    3. Detén nuevamente el Processor.
    4. Comprueba que la Queue queda vacía.

    Laboratorio 2. Examinar los FlowFiles de una Queue

    Objetivo

    Consultar los atributos y el contenido de un FlowFile pendiente.

    Procedimiento

    1. Genera tres FlowFiles.
    2. Mantén detenido el Processor destino.
    3. Selecciona la Connection.
    4. Utiliza List Queue.
    5. Selecciona uno de los FlowFiles.
    6. Examina sus atributos.
    7. Utiliza View Content.
    8. Comprueba el JSON generado.

    Atributos esperados

    Entre otros:

    filename
path
uuid
mime.type

    Los valores exactos dependerán de la configuración utilizada.

    Laboratorio 3. Varias Relationships hacia un mismo destino

    Objetivo

    Comprender que una Connection puede transportar varias Relationships.

    Flujo

    flowchart TB
    A[RouteOnAttribute]

    A -->|urgente| B[LogAttribute normal]
    A -->|unmatched| B

    Configuración previa

    Crea un atributo:

    prioridad = alta

    En RouteOnAttribute, añade:

    urgente = ${prioridad:equals("urgente")}

    Conecta a LogAttribute:

    urgente
unmatched

    Procedimiento

    1. Ejecuta un FlowFile con prioridad = alta.
    2. Comprueba que se envía por unmatched.
    3. Cambia el atributo a prioridad = urgente.
    4. Ejecuta otro FlowFile.
    5. Comprueba que ambos llegan al mismo destino mediante relaciones diferentes.

    Laboratorio 4. Una Relationship hacia dos destinos

    Objetivo

    Comprobar que una misma Relationship puede alimentar varias ramas.

    Flujo

    flowchart TB
    A[GenerateFlowFile]

    A -->|success| B[LogAttribute A]
    A -->|success| C[LogAttribute B]

    Procedimiento

    1. Conecta success a LogAttribute A.
    2. Conecta también success a LogAttribute B.
    3. Ejecuta GenerateFlowFile mediante Run Once.
    4. Mantén ambos destinos detenidos.
    5. Observa las dos Queues.
    6. Comprueba que ambas contienen un FlowFile.
    7. Compara sus UUID y atributos.

    Resultado esperado

    El flujo se distribuye hacia las dos ramas.

    El contenido puede compartir inicialmente el mismo Content Claim, aunque cada rama mantiene su propio FlowFile lógico.

    Laboratorio 5. Vaciar una Queue de prueba

    Objetivo

    Conocer el comportamiento de Empty Queue.

    Procedimiento

    1. Genera cinco FlowFiles de prueba.
    2. Mantén el destino detenido.
    3. Abre List Queue.
    4. Examina uno de los FlowFiles.
    5. Cierra el listado.
    6. Selecciona Empty Queue.
    7. Confirma la operación.
    8. Comprueba que la Queue queda vacía.

    Warning

    Realiza este laboratorio únicamente con datos generados expresamente para la prueba.
