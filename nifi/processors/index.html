    Capítulo 7. Processors en Apache NiFi 2.x

    Los FlowFiles representan los datos que circulan por Apache NiFi. Los Processors representan las operaciones que se realizan sobre esos datos.

    Objetivos

    Al finalizar este capítulo serás capaz de:

    • Comprender qué es un Processor y cuál es su función dentro de un DataFlow.
    • Identificar las principales partes de un Processor.
    • Interpretar sus propiedades, relaciones y requisitos de entrada.
    • Diferenciar entre propiedades obligatorias, opcionales y dinámicas.
    • Comprender los estados de ejecución y validación.
    • Configurar correctamente un Processor.
    • Interpretar los mensajes de error y las advertencias mostradas por NiFi.
    • Conocer las principales categorías de Processors.
    • Seleccionar el Processor adecuado para cada operación.
    • Diseñar flujos teniendo en cuenta rendimiento, errores y trazabilidad.

    Introducción

    En el capítulo anterior se estudió el FlowFile, la unidad básica de información de Apache NiFi.

    Un FlowFile puede contener:

    • un documento JSON;
    • un fichero CSV;
    • una imagen;
    • un mensaje procedente de Kafka;
    • una respuesta de una API;
    • cualquier secuencia de bytes.

    Sin embargo, el FlowFile por sí mismo no realiza ninguna operación.

    Para crear, recibir, transformar, dividir, unir, enrutar o enviar esos datos se utilizan los Processors.

    flowchart LR
    A[Origen de datos]
    --> B[Processor]
    --> C[FlowFile]
    --> D[Processor]
    --> E[Destino]

    Un DataFlow está formado principalmente por una red de Processors conectados mediante Connections.

    flowchart LR
    A[Processor de entrada]
    --> Q1[(Queue)]
    --> B[Processor de transformación]
    --> Q2[(Queue)]
    --> C[Processor de salida]

    Idea fundamental

    Los Processors realizan las operaciones, mientras que los FlowFiles transportan los datos y sus atributos.

    7.1 ¿Qué es un Processor?

    Un Processor es un componente de Apache NiFi encargado de ejecutar una operación concreta sobre uno o varios FlowFiles.

    Cada Processor está diseñado para realizar una tarea específica.

    Por ejemplo:

    Processor Función principal
    GenerateFlowFile Generar FlowFiles
    GetFile Leer archivos de un directorio
    UpdateAttribute Crear o modificar atributos
    EvaluateJsonPath Extraer valores de un JSON
    RouteOnAttribute Enrutar según atributos
    ReplaceText Modificar contenido textual
    SplitText Dividir archivos de texto
    MergeContent Combinar varios FlowFiles
    PutFile Guardar archivos en disco
    PublishKafka Publicar mensajes en Kafka

    Un Processor puede realizar una o varias de las siguientes operaciones:

    • crear FlowFiles;
    • leer el contenido;
    • modificar el contenido;
    • leer atributos;
    • crear o modificar atributos;
    • conectarse con sistemas externos;
    • validar datos;
    • transformar formatos;
    • dividir información;
    • unir información;
    • enrutar FlowFiles;
    • enviar datos a un destino;
    • eliminar FlowFiles.
    flowchart TB
    P[Processor]

    P --> A[Crear]
    P --> B[Leer]
    P --> C[Transformar]
    P --> D[Enrutar]
    P --> E[Dividir]
    P --> F[Unir]
    P --> G[Enviar]

    7.2 El Processor como unidad de trabajo

    Un Processor no debe entenderse como una aplicación completa.

    Normalmente realiza una operación pequeña y especializada.

    Por ejemplo, para recibir un JSON, extraer el país, clasificarlo y guardarlo en una carpeta pueden utilizarse varios Processors:

    flowchart LR
    A[ListenHTTP]
    --> B[EvaluateJsonPath]
    --> C[RouteOnAttribute]
    --> D[UpdateAttribute]
    --> E[PutFile]

    Cada componente tiene una responsabilidad concreta:

    Processor Responsabilidad
    ListenHTTP Recibir la petición
    EvaluateJsonPath Extraer información del JSON
    RouteOnAttribute Decidir la ruta
    UpdateAttribute Preparar los metadatos
    PutFile Guardar el archivo

    Este diseño sigue una filosofía de componentes pequeños, reutilizables y conectables.

    Una responsabilidad por Processor

    Resulta más sencillo mantener y depurar un flujo formado por operaciones pequeñas que un único componente encargado de realizar toda la lógica.

    7.3 Anatomía de un Processor

    Desde la interfaz gráfica, un Processor contiene varios elementos importantes.

    flowchart TB
    P[Processor]

    P --> N[Nombre]
    P --> T[Tipo]
    P --> PR[Properties]
    P --> SC[Scheduling]
    P --> RE[Relationships]
    P --> ST[Settings]
    P --> CO[Comments]

    Los principales son:

    • nombre;
    • tipo de Processor;
    • identificador;
    • propiedades;
    • relaciones;
    • estrategia de planificación;
    • número de tareas concurrentes;
    • penalización;
    • rendimiento;
    • estado;
    • documentación.

    Nombre del Processor

    El nombre permite identificar su función dentro del flujo.

    Al añadir un Processor, NiFi utiliza inicialmente el nombre de su clase:

    UpdateAttribute

    Sin embargo, es recomendable utilizar nombres descriptivos:

    Añadir metadatos del pedido

    Extraer país del cliente

    Guardar facturas validadas

    Esto facilita la comprensión del DataFlow.

    Ejemplo poco descriptivo

    flowchart LR
    A[EvaluateJsonPath]
    --> B[RouteOnAttribute]
    --> C[PutFile]

    Ejemplo descriptivo

    flowchart LR
    A[Extraer datos del pedido]
    --> B[Clasificar por país]
    --> C[Guardar pedidos españoles]

    Convención de nombres

    Utiliza un verbo seguido del objeto sobre el que actúa el Processor:

- `Validar pedido`
- `Extraer identificador`
- `Convertir CSV a JSON`
- `Guardar registros erróneos`

    Tipo del Processor

    El tipo identifica la implementación utilizada.

    Por ejemplo:

    org.apache.nifi.processors.attributes.UpdateAttribute

    Aunque la interfaz suele mostrar simplemente:

    UpdateAttribute

    Dos Processors pueden tener el mismo nombre visible, pero realizar funciones diferentes si pertenecen a extensiones distintas.

    El tipo completo permite identificar:

    • la organización que lo proporciona;
    • el paquete al que pertenece;
    • la implementación concreta;
    • la versión instalada.

    Identificador

    Cada Processor posee un identificador único.

    Ejemplo:

    8c42df8a-019b-1000-4edf-bb5a7104df23

    Este identificador se utiliza internamente para:

    • distinguir componentes;
    • gestionar permisos;
    • consultar eventos de Provenance;
    • utilizar la API REST;
    • localizar errores en los logs.

    Note

    El identificador del Processor no debe confundirse con el UUID de los FlowFiles que procesa.

    7.4 Estados de un Processor

    Un Processor puede encontrarse en distintos estados.

    Los más importantes son:

    Estado Descripción
    Stopped El Processor está detenido
    Running El Processor está ejecutándose
    Disabled El Processor está deshabilitado
    Invalid La configuración no es válida
    Validating NiFi está comprobando su configuración

    Processor detenido

    Un Processor detenido conserva su configuración, pero no procesa FlowFiles.

    Stopped

    Puede recibir FlowFiles en su Queue de entrada, pero no los consumirá hasta que se inicie.

    flowchart LR
    A[Processor anterior]
    --> Q[(FlowFiles acumulados)]
    -.-> B[Processor detenido]

    Processor en ejecución

    Cuando se encuentra en estado Running, NiFi lo ejecuta según la estrategia configurada.

    Running

    El Processor puede:

    • consumir FlowFiles de entrada;
    • generar nuevos FlowFiles;
    • consultar sistemas externos;
    • transferir FlowFiles a las relaciones correspondientes.

    Processor deshabilitado

    Un Processor deshabilitado no puede ejecutarse.

    Disabled

    Este estado resulta útil cuando se desea mantener un componente en el flujo, pero evitar que se inicie accidentalmente.

    Detenido y deshabilitado no son lo mismo

    Un Processor detenido puede volver a iniciarse directamente. Un Processor deshabilitado debe habilitarse antes de poder ejecutarse.

    Processor no válido

    Un Processor se considera Invalid cuando su configuración no cumple los requisitos necesarios.

    Las causas más frecuentes son:

    • falta una propiedad obligatoria;
    • una propiedad contiene un valor incorrecto;
    • una Relationship no está conectada ni auto-terminada;
    • falta un Controller Service;
    • el Controller Service está deshabilitado;
    • la expresión configurada no es válida;
    • el Processor no dispone de una entrada necesaria.
    flowchart LR
    A[Configuración incompleta]
    --> B[Processor inválido]
    --> C[No puede iniciarse]

    NiFi muestra un símbolo de advertencia sobre el componente.

    Al situar el cursor sobre el aviso puede consultarse el motivo.

    No ignores los errores de validación

    Un Processor inválido no puede ejecutarse. Debe corregirse cada uno de los problemas indicados por NiFi.

    7.5 Ventana de configuración

    Al seleccionar un Processor y abrir su configuración se muestran varias pestañas.

    Las más habituales son:

    • Settings
    • Scheduling
    • Properties
    • Relationships
    • Comments
    flowchart LR
    A[Configure Processor]
    --> B[Settings]
    --> C[Scheduling]
    --> D[Properties]
    --> E[Relationships]
    --> F[Comments]

    El contenido exacto puede variar en función del Processor y de la versión de NiFi.

    7.6 Pestaña Settings

    La pestaña Settings contiene la configuración general del componente.

    Normalmente incluye:

    • nombre;
    • estado;
    • estrategia de penalización;
    • duración de la penalización;
    • nivel de mensajes del Bulletin;
    • auto-terminación de Relationships.

    Name

    Permite modificar el nombre visible del Processor.

    Ejemplo:

    Extraer atributos del pedido

    Penalty Duration

    Determina cuánto tiempo permanecerá penalizado un FlowFile cuando el Processor decida que no debe procesarse inmediatamente.

    Ejemplo:

    30 sec

    Durante ese periodo, el FlowFile continúa en la Queue, pero no será seleccionado de nuevo.

    Yield Duration

    Indica cuánto tiempo debe esperar un Processor antes de volver a ejecutarse después de que no haya podido realizar trabajo útil.

    Ejemplo:

    1 sec

    La penalización afecta a un FlowFile concreto.

    El yield afecta temporalmente a la ejecución del Processor.

    Mecanismo Afecta a
    Penalización Un FlowFile
    Yield El Processor

    Bulletin Level

    Determina el nivel mínimo de mensajes que el Processor mostrará como Bulletins.

    Según el componente pueden aparecer niveles como:

    • DEBUG;
    • INFO;
    • WARN;
    • ERROR.

    Los Bulletins permiten detectar problemas directamente desde el lienzo.

    Tip

    En un entorno de producción conviene prestar especial atención a los Bulletins de nivel `WARN` y `ERROR`.

    7.7 Pestaña Properties

    La pestaña Properties contiene los parámetros que determinan el comportamiento del Processor.

    Por ejemplo, GenerateFlowFile puede incluir propiedades relacionadas con:

    • tamaño del archivo;
    • formato de los datos;
    • texto personalizado;
    • número de FlowFiles por ejecución.

    Por otro lado, PutFile necesita información como:

    • directorio de destino;
    • estrategia ante conflictos;
    • permisos del archivo.
    flowchart LR
    A[Processor]
    --> B[Properties]
    --> C[Comportamiento]

    Propiedades obligatorias

    Las propiedades obligatorias deben tener un valor válido para que el Processor pueda ejecutarse.

    Normalmente aparecen identificadas visualmente en la interfaz.

    Ejemplo:

    Directory = /datos/salida

    Si la propiedad obligatoria no está configurada, el Processor será inválido.

    Propiedades opcionales

    Las propiedades opcionales permiten modificar el comportamiento predeterminado.

    Si no se configuran, NiFi utiliza:

    • un valor por defecto;
    • una operación predeterminada;
    • la ausencia de esa funcionalidad.

    Propiedades sensibles

    Algunas propiedades contienen información confidencial:

    • contraseñas;
    • tokens;
    • claves;
    • secretos;
    • credenciales.

    NiFi oculta sus valores en la interfaz.

    Password = ********

    Credenciales

    No deben escribirse contraseñas directamente en propiedades normales ni almacenarse como atributos del FlowFile. Cuando sea posible deben utilizarse Parameter Contexts con parámetros sensibles o servicios específicos de credenciales.

    Propiedades dinámicas

    Algunos Processors permiten crear propiedades adicionales.

    Estas reciben el nombre de Dynamic Properties.

    Por ejemplo, en UpdateAttribute cada propiedad dinámica crea o modifica un atributo:

    Propiedad dinámica Valor
    departamento facturacion
    fecha.proceso ${now():format("yyyy-MM-dd")}
    nombre.salida ${filename:toUpper()}

    Las propiedades dinámicas no tienen siempre el mismo significado.

    Su comportamiento depende del Processor:

    • en UpdateAttribute, crean atributos;
    • en RouteOnAttribute, crean rutas;
    • en EvaluateJsonPath, extraen valores del JSON;
    • en ReplaceText, pueden intervenir en la transformación;
    • en otros Processors pueden representar cabeceras, consultas o parámetros.

    Warning

    No debe asumirse que todas las propiedades dinámicas crean atributos. Es necesario consultar la documentación del Processor.

    7.8 Expression Language en las propiedades

    Muchas propiedades admiten NiFi Expression Language.

    Esto permite calcular sus valores dinámicamente utilizando atributos del FlowFile.

    Ejemplo:

    ${filename}

    Otro ejemplo:

    ${filename:toUpper()}

    También pueden combinarse texto fijo y expresiones:

    procesado_${filename}

    O construir una ruta dinámica:

    /datos/${departamento}/${now():format("yyyy/MM/dd")}

    flowchart LR
    A[Atributos del FlowFile]
    --> B[Expression Language]
    --> C[Valor de la propiedad]

    Supongamos estos atributos:

    departamento = ventas
filename = pedidos.csv

    La propiedad:

    /salida/${departamento}/${filename}

    producirá:

    /salida/ventas/pedidos.csv

    Note

    No todas las propiedades permiten Expression Language y no todas admiten el mismo ámbito de evaluación. Esta información aparece en la documentación de cada propiedad.

    7.9 Pestaña Relationships

    Cuando un Processor termina de trabajar con un FlowFile debe transferirlo a una Relationship.

    Las Relationships representan los posibles resultados de la operación.

    Por ejemplo, un Processor puede disponer de:

    success
failure

    Otro puede ofrecer:

    matched
unmatched
failure

    flowchart TB
    P[Processor]

    P -->|success| A[Procesamiento correcto]
    P -->|failure| B[Error]

    Las relaciones dependen del tipo de Processor.

    Relationship success

    Normalmente representa que la operación se ha completado correctamente.

    flowchart LR
    A[Processor]
    -->|success| B[Siguiente Processor]

    Relationship failure

    Representa que se ha producido algún error.

    flowchart LR
    A[Processor]
    -->|failure| B[Gestión de errores]

    No todos los errores implican que NiFi se detenga.

    Con frecuencia, el FlowFile se envía por failure para que pueda:

    • reintentarse;
    • almacenarse en cuarentena;
    • registrarse;
    • enviarse a revisión;
    • descartarse controladamente.

    Relaciones específicas

    Algunos Processors utilizan relaciones relacionadas con su función.

    Por ejemplo:

    Relationship Significado habitual
    matched El FlowFile cumple una condición
    unmatched No cumple la condición
    original FlowFile original
    split Fragmentos generados
    merged FlowFile combinado
    retry Debe reintentarse
    not.found No se encontró el recurso
    response Respuesta recibida

    Note

    El significado exacto debe comprobarse siempre en la documentación del Processor.

    7.10 Conectar o auto-terminar Relationships

    Todas las Relationships deben:

    • estar conectadas con otro componente; o
    • configurarse como auto-terminadas.

    Si una Relationship no cumple ninguna de estas condiciones, el Processor será inválido.

    flowchart TB
    P[Processor]

    P -->|success| A[Conectada]
    P -->|failure| B[Auto-terminada]

    Relationship conectada

    El FlowFile continúa por la Connection correspondiente.

    flowchart LR
    A[Processor]
    -->|success| B[Siguiente Processor]

    Relationship auto-terminada

    El FlowFile finaliza su recorrido y se elimina del flujo.

    flowchart LR
    A[Processor]
    -->|success| B[Auto-terminate]
    --> C[FlowFile eliminado]

    Pérdida de datos

    Auto-terminar una Relationship significa descartar los FlowFiles enviados a ella. No debe utilizarse únicamente para eliminar un aviso de validación.

    Ejemplo

    Supongamos un PutFile con estas relaciones:

    success
failure

    Una configuración adecuada podría ser:

    flowchart TB
    A[PutFile]

    A -->|success| B[Auto-terminate]
    A -->|failure| C[Registrar error]

    Los FlowFiles guardados correctamente finalizan.

    Los que producen errores continúan hacia un flujo de tratamiento de incidencias.

    7.11 Requisito de entrada

    No todos los Processors necesitan recibir un FlowFile.

    En su documentación aparece un campo denominado Input Requirement.

    Los valores habituales son:

    Requisito Significado
    INPUT_REQUIRED Necesita un FlowFile de entrada
    INPUT_ALLOWED Puede funcionar con o sin entrada
    INPUT_FORBIDDEN No admite Connections entrantes

    Entrada obligatoria

    Un Processor como UpdateAttribute necesita recibir un FlowFile existente.

    flowchart LR
    A[FlowFile]
    --> B[UpdateAttribute]

    Sin una Connection entrante no puede realizar su trabajo.

    Entrada no permitida

    Un Processor de origen puede crear FlowFiles sin recibir ninguno.

    Ejemplos habituales:

    • GenerateFlowFile;
    • Processors que consultan periódicamente una fuente;
    • algunos Processors de escucha o recepción.
    flowchart LR
    A[GenerateFlowFile]
    --> B[Nuevo FlowFile]

    No debe conectarse otro Processor a su entrada.

    Entrada opcional

    Algunos Processors pueden trabajar de las dos formas.

    Su comportamiento puede cambiar dependiendo de si reciben o no un FlowFile.

    Tip

    Antes de diseñar una Connection, comprueba el `Input Requirement` del Processor de destino.

    7.12 Documentación integrada del Processor

    Apache NiFi incluye documentación asociada a cada Processor.

    Desde la interfaz puede consultarse información como:

    • descripción;
    • propiedades;
    • valores permitidos;
    • soporte de Expression Language;
    • atributos leídos;
    • atributos escritos;
    • relaciones;
    • requisitos de entrada;
    • Controller Services necesarios;
    • restricciones;
    • ejemplos o detalles adicionales.

    La documentación de un Processor debe considerarse parte del proceso normal de diseño.

    Antes de utilizar un Processor

    Comprueba siempre:

1. Qué entrada necesita.
2. Qué contenido espera.
3. Qué atributos lee.
4. Qué atributos crea.
5. Qué Relationships genera.
6. Qué Controller Services necesita.
7. Si admite Expression Language.

    7.13 Planificación de los Processors

    Configurar correctamente las propiedades de un Processor no es suficiente.

    También es necesario determinar:

    • cuándo debe ejecutarse;
    • con qué frecuencia;
    • cuántas tareas puede ejecutar simultáneamente;
    • en qué nodos debe trabajar;
    • cuánto tiempo puede permanecer procesando datos en cada ejecución.

    Estas opciones se encuentran principalmente en la pestaña Scheduling.

    flowchart TB
    S[Scheduling]

    S --> A[Scheduling Strategy]
    S --> B[Run Schedule]
    S --> C[Concurrent Tasks]
    S --> D[Execution]
    S --> E[Run Duration]

    La configuración de planificación influye directamente en:

    • la latencia;
    • el rendimiento;
    • el consumo de CPU;
    • el número de operaciones externas;
    • el orden de procesamiento;
    • la carga generada sobre otros sistemas.

    Configuración de rendimiento

    Aumentar la frecuencia o el número de tareas concurrentes no garantiza que el flujo procese más datos. Una configuración excesiva puede saturar la CPU, el disco, la red o el sistema de destino.

    7.14 ¿Cuándo se ejecuta un Processor?

    Un Processor puede estar configurado como Running, pero eso no significa que se esté ejecutando continuamente.

    Para que NiFi active un Processor deben cumplirse determinadas condiciones.

    De forma simplificada:

    flowchart TD
    A[Processor iniciado]
    --> B{¿Existe trabajo?}

    B -->|Sí| C{¿Puede enviar resultados?}
    B -->|No| D[Esperar]

    C -->|Sí| E[Ejecutar Processor]
    C -->|No, Back Pressure| D

    Normalmente existe trabajo cuando:

    • hay al menos un FlowFile en una Queue de entrada;
    • el Processor no necesita entrada y puede generar o consultar datos;
    • el Processor está diseñado para ejecutarse incluso sin FlowFiles de entrada.

    Además, NiFi comprueba el estado de las conexiones de salida.

    Si una Queue de salida ha alcanzado el límite de Back Pressure, normalmente el Processor dejará de activarse hasta que vuelva a existir capacidad.

    Running no significa ejecución continua

    El estado `Running` indica que el Processor está programado para ejecutarse. NiFi solo lo activará cuando se cumplan las condiciones necesarias.

    La activación de un Processor depende de su planificación, de la existencia de trabajo y, por defecto, de que sus destinos puedan aceptar nuevos FlowFiles.

    7.15 Scheduling Strategy

    La propiedad Scheduling Strategy determina cómo decide NiFi cuándo debe activar el Processor.

    Las estrategias más importantes son:

    • Timer Driven
    • CRON Driven

    En determinadas versiones o componentes también puede aparecer una estrategia basada en eventos, aunque su disponibilidad y uso pueden variar.

    flowchart TB
    A[Scheduling Strategy]

    A --> B[Timer Driven]
    A --> C[CRON Driven]

    7.16 Timer Driven

    Timer Driven es la estrategia más utilizada.

    Permite ejecutar un Processor periódicamente utilizando un intervalo de tiempo.

    Ejemplos:

    0 sec

    1 sec

    30 sec

    5 min

    flowchart LR
    A[Inicio]
    --> B[Espera configurada]
    --> C[Ejecución]
    --> D[Espera configurada]
    --> E[Ejecución]

    El intervalo se configura mediante la propiedad Run Schedule.

    Run Schedule igual a cero

    Cuando se configura:

    Run Schedule = 0 sec

    NiFi intenta ejecutar el Processor tan frecuentemente como sea posible, siempre que:

    • exista trabajo;
    • las conexiones de salida no estén bloqueadas;
    • el Processor no se encuentre en estado de yield;
    • existan recursos de ejecución disponibles.
    flowchart LR
    A[Trabajo disponible]
    --> B[Ejecutar]
    --> C[Trabajo disponible]
    --> D[Ejecutar]
    --> E[...]

    Esta configuración es habitual para Processors que deben consumir continuamente datos de una Queue.

    Ejemplos:

    • UpdateAttribute;
    • EvaluateJsonPath;
    • RouteOnAttribute;
    • ConvertRecord;
    • PutFile.

    Note

    `0 sec` no significa que el Processor disponga de un hilo dedicado ejecutándose sin interrupción. Significa que puede volver a ser programado tan pronto como sea posible.

    Intervalos superiores a cero

    Un valor como:

    Run Schedule = 10 sec

    indica que NiFi programará periódicamente el Processor con ese intervalo.

    Esta configuración resulta útil para:

    • consultar un directorio cada cierto tiempo;
    • revisar una API periódicamente;
    • ejecutar una consulta recurrente;
    • generar datos de prueba;
    • limitar la frecuencia de acceso a un sistema externo.
    sequenceDiagram
    participant N as NiFi
    participant P as Processor

    N->>P: Ejecutar
    Note over N,P: Esperar 10 segundos
    N->>P: Ejecutar
    Note over N,P: Esperar 10 segundos
    N->>P: Ejecutar

    Ejemplo con GenerateFlowFile

    Para generar un FlowFile cada cinco segundos:

    Scheduling Strategy = Timer Driven
Run Schedule = 5 sec
Concurrent Tasks = 1

    El resultado será aproximadamente:

    00:00:00 → FlowFile 1
00:00:05 → FlowFile 2
00:00:10 → FlowFile 3
00:00:15 → FlowFile 4

    Timer Driven y procesamiento de colas

    Supongamos una Queue con 1.000 FlowFiles y un Processor configurado con:

    Run Schedule = 1 min

    El Processor solo será programado periódicamente cada minuto.

    Esto puede generar una latencia innecesaria.

    Para un Processor que consume datos ya disponibles en una Queue suele ser más apropiado:

    Run Schedule = 0 sec

    Regla inicial

    Para Processors de transformación que consumen FlowFiles de una Queue, comienza normalmente con `Timer Driven` y `0 sec`. Ajusta la configuración únicamente cuando exista una razón concreta.

    En Timer Driven, el valor predeterminado 0 sec permite que el Processor sea ejecutado tan frecuentemente como sea posible mientras tenga trabajo disponible.

    7.17 CRON Driven

    CRON Driven permite ejecutar un Processor en momentos concretos utilizando una expresión CRON.

    Resulta adecuado cuando la operación debe realizarse según un calendario.

    Ejemplos:

    • todos los días a medianoche;
    • cada hora en el minuto 15;
    • de lunes a viernes;
    • el primer día de cada mes;
    • durante determinadas franjas horarias.
    flowchart LR
    A[Expresión CRON]
    --> B[Fecha y hora coincidente]
    --> C[Ejecución del Processor]

    Estructura general de una expresión CRON

    En NiFi, una expresión CRON utiliza normalmente seis campos obligatorios y puede incluir un séptimo campo opcional.

    segundo minuto hora día-del-mes mes día-de-la-semana [año]

    Ejemplo:

    0 0 0 * * ?

    Esta expresión representa una ejecución diaria a las 00:00:00.

    Campo Valor
    Segundo 0
    Minuto 0
    Hora 0
    Día del mes *
    Mes *
    Día de la semana ?

    Ejemplos de expresiones

    Todos los días a las 02:00

    0 0 2 * * ?

    Cada hora

    0 0 * * * ?

    Cada cinco minutos

    0 0/5 * * * ?

    De lunes a viernes a las 08:30

    0 30 8 ? * MON-FRI

    El primer día de cada mes a medianoche

    0 0 0 1 * ?

    Sintaxis CRON

    La sintaxis utilizada por NiFi no debe confundirse con el formato CRON tradicional de cinco campos utilizado habitualmente en Linux.

    Cuándo utilizar CRON Driven

    CRON Driven es apropiado para:

    • ejecuciones programadas;
    • cargas nocturnas;
    • informes periódicos;
    • consultas diarias;
    • procesos de cierre;
    • sincronizaciones calendarizadas.

    No suele ser la mejor opción para consumir continuamente una Queue.

    flowchart TD
    A{¿Necesitas una hora concreta?}

    A -->|Sí| B[CRON Driven]
    A -->|No| C{¿Necesitas un intervalo?}

    C -->|Sí| D[Timer Driven]
    C -->|No| E[Revisar el diseño]

    Processors de agrupación

    Algunos Processors, especialmente determinados componentes de unión o agrupación, desaconsejan expresamente el uso de `CRON Driven`. Debe revisarse siempre la documentación del componente.

    Por ejemplo, la documentación oficial de MergeContent y MergeRecord advierte que no deben configurarse mediante CRON Driven.

    7.18 Timer Driven frente a CRON Driven

    Característica Timer Driven CRON Driven
    Tipo de planificación Por intervalo Por calendario
    Configuración Duración Expresión CRON
    Ejemplo Cada 10 segundos Cada día a las 02:00
    Uso habitual Procesamiento continuo Tareas programadas
    Complejidad Baja Media
    Precisión temporal Por frecuencia Por fecha y hora
    Consumo de Queue Habitual Menos habitual

    Tip

    Utiliza `Timer Driven` como estrategia predeterminada y `CRON Driven` cuando exista un requisito temporal explícito.

    7.19 Ejecutar una sola vez: Run Once

    La opción Run Once permite solicitar la ejecución de un Processor una única vez.

    Resulta especialmente útil durante:

    • laboratorios;
    • pruebas;
    • depuración;
    • validación de una configuración;
    • generación controlada de FlowFiles.
    flowchart LR
    A[Run Once]
    --> B[Una activación]
    --> C[Processor detenido]

    Ejemplo con GenerateFlowFile

    Supongamos esta configuración:

    Batch Size = 3

    Al seleccionar:

    Run Once

    GenerateFlowFile genera tres FlowFiles en una única activación.

    flowchart LR
    A[Run Once]
    --> B[GenerateFlowFile]
    --> C[FlowFile 1]
    B --> D[FlowFile 2]
    B --> E[FlowFile 3]

    Esta es la forma adecuada de generar exactamente tres FlowFiles en un laboratorio.

    No debe configurarse un intervalo y detener manualmente el Processor, ya que el número generado dependería del tiempo transcurrido.

    Condiciones que pueden impedir Run Once

    Solicitar Run Once no garantiza que el Processor realice trabajo.

    Puede no ejecutarse de forma efectiva cuando:

    • no existen FlowFiles en la entrada;
    • la Queue de salida está en Back Pressure;
    • falta un recurso externo;
    • la configuración no permite realizar la operación;
    • no se cumplen los requisitos internos del Processor.

    Note

    `Run Once` solicita una única activación. No obliga al Processor a producir resultados si no existe trabajo disponible.

    La documentación oficial indica que Run Once funciona con las estrategias Timer Driven y CRON Driven; además, si no existen datos de entrada o el destino tiene Back Pressure, el Processor puede no llegar a activarse.

    7.20 Concurrent Tasks

    La propiedad Concurrent Tasks determina cuántas tareas pueden ejecutar simultáneamente el mismo Processor.

    Concurrent Tasks = 1

    significa que solo una tarea puede ejecutar el Processor en un momento dado.

    Concurrent Tasks = 4

    permite hasta cuatro ejecuciones simultáneas.

    flowchart TB
    P[Processor]

    P --> T1[Tarea 1]
    P --> T2[Tarea 2]
    P --> T3[Tarea 3]
    P --> T4[Tarea 4]

    Concurrencia igual a uno

    Con:

    Concurrent Tasks = 1

    los FlowFiles se procesan mediante una única tarea.

    flowchart LR
    Q[(Queue)]
    --> T1[Tarea única]
    --> D[Destino]

    Es la configuración inicial más segura.

    Resulta recomendable cuando:

    • se está aprendiendo;
    • se está depurando un flujo;
    • importa especialmente el orden;
    • el sistema externo no soporta concurrencia;
    • el Processor mantiene estado;
    • se desconoce el comportamiento del componente.

    Varias tareas concurrentes

    Con:

    Concurrent Tasks = 3

    NiFi puede procesar varios FlowFiles paralelamente.

    flowchart LR
    Q[(Queue)]

    Q --> T1[Tarea 1]
    Q --> T2[Tarea 2]
    Q --> T3[Tarea 3]

    T1 --> D[Destino]
    T2 --> D
    T3 --> D

    Esto puede aumentar el rendimiento cuando:

    • existe suficiente trabajo pendiente;
    • hay recursos de CPU disponibles;
    • las operaciones son independientes;
    • el destino admite conexiones simultáneas;
    • el Processor permite ejecución paralela.

    La concurrencia no multiplica siempre el rendimiento

    Supongamos un Processor que tarda un segundo por FlowFile.

    Teóricamente:

    Concurrent Tasks Rendimiento aproximado
    1 1 FlowFile/s
    2 2 FlowFiles/s
    4 4 FlowFiles/s

    En la práctica, este crecimiento puede no producirse debido a:

    • límites de CPU;
    • velocidad del disco;
    • ancho de banda;
    • bloqueos;
    • latencia del sistema externo;
    • límites de conexiones;
    • costes de sincronización.
    flowchart LR
    A[Más concurrencia]
    --> B{¿Existen recursos?}

    B -->|Sí| C[Mayor rendimiento]
    B -->|No| D[Contención y degradación]

    Warning

    No aumentes `Concurrent Tasks` de forma indiscriminada. Mide el rendimiento antes y después del cambio.

    Processors que limitan la concurrencia

    Algunos Processors solo permiten una tarea concurrente porque necesitan ejecutar su lógica de forma secuencial.

    NiFi puede fijar automáticamente:

    Concurrent Tasks = 1

    En estos casos no debe intentarse forzar una ejecución paralela.

    La anotación interna TriggerSerially hace que un Processor se ejecute con una sola tarea concurrente.

    Concurrencia y orden de procesamiento

    Cuando se utilizan varias tareas, no debe asumirse que los FlowFiles finalizarán en el mismo orden en que fueron obtenidos.

    Entrada:

    FlowFile A
FlowFile B
FlowFile C

    Posible salida:

    FlowFile B
FlowFile A
FlowFile C

    Esto puede ocurrir porque cada tarea requiere un tiempo diferente.

    Orden

    Si el orden es un requisito funcional, debe diseñarse explícitamente. Reducir la concurrencia puede ayudar, pero no sustituye una estrategia completa de ordenación.

    Concurrencia y sistemas externos

    Antes de aumentar las tareas concurrentes deben considerarse las capacidades del destino.

    Por ejemplo, con:

    Concurrent Tasks = 20

    un Processor de base de datos podría intentar realizar numerosas operaciones simultáneas.

    Esto puede:

    • agotar el pool de conexiones;
    • provocar bloqueos;
    • saturar la base de datos;
    • superar límites de una API;
    • generar respuestas HTTP 429;
    • aumentar los errores temporales.
    flowchart LR
    A[20 tareas]
    --> B[Pool de 5 conexiones]
    --> C[Esperas y errores]

    Concurrencia y estado

    Los Processors que mantienen estado requieren especial precaución.

    Por ejemplo, una operación puede:

    1. leer el estado actual;
    2. calcular un nuevo valor;
    3. actualizar el estado.

    Con varias tareas concurrentes, dos ejecuciones pueden intentar actualizar el mismo estado.

    sequenceDiagram
    participant T1 as Tarea 1
    participant S as Estado
    participant T2 as Tarea 2

    T1->>S: Leer estado
    T2->>S: Leer estado
    T1->>S: Actualizar
    T2->>S: Actualizar

    La documentación de cada Processor debe indicar si existen precauciones específicas.

    Por ejemplo, la documentación de UpdateAttribute advierte que, al utilizar su opción con estado, las tareas concurrentes deben configurarse con cautela.

    7.21 Ejecución en un clúster

    En un clúster de NiFi existen varios nodos capaces de ejecutar el mismo DataFlow.

    La propiedad Execution determina en qué nodos se ejecutará un Processor.

    Las opciones principales son:

    • All Nodes
    • Primary Node
    flowchart TB
    P[Processor]

    P --> A[All Nodes]
    P --> B[Primary Node]

    7.22 All Nodes

    Con:

    Execution = All Nodes

    el Processor se programa en todos los nodos del clúster.

    flowchart TB
    C[Clúster NiFi]

    C --> N1[Nodo 1: Processor]
    C --> N2[Nodo 2: Processor]
    C --> N3[Nodo 3: Processor]

    Esto permite aprovechar la capacidad de procesamiento distribuido.

    Es apropiado cuando:

    • cada nodo dispone de FlowFiles que debe procesar;
    • la operación puede ejecutarse de forma paralela;
    • el sistema de origen admite varias conexiones;
    • no se producirán datos duplicados.

    7.23 Primary Node

    Con:

    Execution = Primary Node

    el Processor se ejecuta únicamente en el nodo designado como primario.

    flowchart TB
    C[Clúster NiFi]

    C --> N1[Nodo primario: ejecuta]
    C --> N2[Nodo 2: no ejecuta]
    C --> N3[Nodo 3: no ejecuta]

    Esta opción es especialmente importante para Processors que:

    • consultan una fuente compartida;
    • generan eventos periódicos;
    • enumeran recursos externos;
    • podrían producir duplicados si se ejecutaran en todos los nodos.

    Ejemplo de duplicación

    Supongamos un Processor que consulta una API cada minuto.

    En un clúster de tres nodos:

    Execution = All Nodes

    podría provocar tres consultas simultáneas y generar tres copias de los mismos datos.

    flowchart LR
    N1[Nodo 1] --> API[API externa]
    N2[Nodo 2] --> API
    N3[Nodo 3] --> API

    API --> D[Datos duplicados]

    Con:

    Execution = Primary Node

    solo se realizaría una consulta.

    flowchart LR
    P[Nodo primario]
    --> API[API externa]
    --> D[Una única obtención]

    Clúster

    Un flujo correcto en una instalación de un solo nodo puede generar duplicados cuando se despliega en clúster si no se revisa la propiedad `Execution`.

    La documentación oficial distingue entre ejecución en todos los nodos y ejecución exclusiva en el nodo primario. También señala que algunos Processors deben restringirse al nodo primario para evitar duplicaciones o comportamientos no deseados.

    7.24 Run Once en un clúster

    El comportamiento de Run Once también depende de la propiedad Execution.

    Primary Node

    Execution = Primary Node

    El Processor se ejecutará una vez en el nodo primario.

    All Nodes

    Execution = All Nodes

    El Processor podrá ejecutarse una vez en cada nodo.

    En un clúster de tres nodos, un GenerateFlowFile con:

    Batch Size = 3
Execution = All Nodes

    podría generar:

    3 FlowFiles × 3 nodos = 9 FlowFiles

    Warning

    Al utilizar `Run Once` en un clúster debe comprobarse siempre la propiedad `Execution`.

    Este comportamiento está descrito en la documentación oficial de Run Once: la ejecución se produce una vez en el nodo primario o una vez en cada nodo, según la configuración.

    7.25 Run Duration

    La propiedad Run Duration determina cuánto tiempo puede continuar trabajando un Processor cada vez que obtiene un hilo de ejecución.

    Conceptualmente, permite ajustar el equilibrio entre:

    • menor latencia;
    • mayor rendimiento.
    flowchart LR
    A[Menor Run Duration]
    --> B[Menor latencia]

    C[Mayor Run Duration]
    --> D[Mayor throughput]

    Run Duration bajo

    Una duración baja favorece que el Processor devuelva antes el control al framework.

    Ventajas:

    • mejor reparto de recursos;
    • menor latencia para otros Processors;
    • mayor capacidad de respuesta del flujo.

    Inconveniente:

    • pueden aumentar las operaciones de commit y gestión interna.

    Run Duration alto

    Una duración mayor permite que el Processor continúe procesando más trabajo antes de finalizar la ejecución.

    Ventajas:

    • puede aumentar el rendimiento;
    • reduce proporcionalmente ciertos costes de gestión;
    • permite procesar más FlowFiles por activación.

    Inconvenientes:

    • puede aumentar la latencia;
    • un Processor puede retener un hilo durante más tiempo;
    • puede reducir la capacidad de respuesta de otros componentes.
    flowchart TB
    A[Run Duration]

    A --> B[Valor bajo]
    B --> C[Menor latencia]
    B --> D[Más commits]

    A --> E[Valor alto]
    E --> F[Mayor throughput]
    E --> G[Mayor uso continuado del hilo]

    Tip

    Mantén inicialmente el valor predeterminado. Modifica `Run Duration` únicamente después de medir el comportamiento del flujo.

    La guía oficial describe Run Duration como un ajuste entre menor latencia y mayor throughput; al finalizar una ejecución, el Processor debe actualizar los repositorios para transferir sus FlowFiles.

    7.26 Penalización

    La penalización afecta a un FlowFile concreto.

    Cuando un Processor penaliza un FlowFile, este regresa a una Queue, pero no puede volver a seleccionarse inmediatamente.

    flowchart LR
    A[Processor]
    --> B[Error temporal]
    --> C[FlowFile penalizado]
    --> D[Esperar]
    --> E[Disponible de nuevo]

    La duración se configura mediante:

    Penalty Duration

    Ejemplo:

    Penalty Duration = 30 sec

    Ejemplo

    Un Processor intenta enviar un documento a un servidor remoto.

    El servidor responde temporalmente con un error.

    En lugar de intentar procesar inmediatamente el mismo FlowFile una y otra vez:

    1. el FlowFile se penaliza;
    2. vuelve a la Queue;
    3. espera el periodo configurado;
    4. vuelve a quedar disponible.
    sequenceDiagram
    participant Q as Queue
    participant P as Processor
    participant S as Servidor

    Q->>P: FlowFile
    P->>S: Enviar
    S-->>P: Error temporal
    P->>Q: FlowFile penalizado
    Note over Q: Espera configurada
    Q->>P: FlowFile disponible

    Note

    La penalización no detiene todo el Processor. Otros FlowFiles no penalizados pueden continuar procesándose.

    7.27 Yield

    El mecanismo de yield afecta al Processor completo.

    Cuando un Processor realiza yield, NiFi espera el periodo configurado antes de volver a programarlo.

    flowchart LR
    A[Processor]
    --> B[No puede realizar trabajo útil]
    --> C[Yield]
    --> D[Esperar]
    --> E[Volver a programar]

    La duración se configura mediante:

    Yield Duration

    Ejemplo:

    Yield Duration = 1 sec

    Ejemplo

    Un Processor consulta un servicio que se encuentra temporalmente fuera de servicio.

    Si continuara ejecutándose de forma inmediata:

    • consumiría CPU;
    • generaría múltiples conexiones fallidas;
    • llenaría los logs;
    • aumentaría la carga sobre el servicio.

    Al realizar yield, el Processor espera antes de volver a intentarlo.

    7.28 Diferencia entre Penalization y Yield

    Característica Penalization Yield
    Afecta a Un FlowFile Todo el Processor
    Elemento que espera FlowFile Processor
    Otros FlowFiles pueden continuar Sí No durante el periodo
    Uso habitual Error asociado a un dato Falta de trabajo o recurso
    Configuración Penalty Duration Yield Duration 
    flowchart TB
    A[Incidencia]

    A --> B{¿Afecta a un FlowFile concreto?}

    B -->|Sí| C[Penalization]
    B -->|No, afecta al Processor| D[Yield]

    Ejemplo sencillo

    Si un paquete concreto tiene un problema, se aparta temporalmente ese paquete: penalización.

Si toda la máquina no puede trabajar, se detiene temporalmente la máquina: yield.

    7.29 Back Pressure y planificación

    La planificación de un Processor no funciona de manera aislada.

    También depende de las Connections de salida.

    flowchart LR
    A[Processor]
    --> B{Queue de salida llena}

    B -->|No| C[Ejecutar]
    B -->|Sí| D[No programar]

    Supongamos:

    flowchart LR
    A[GenerateFlowFile]
    --> Q[(Queue)]
    --> B[PutFile detenido]

    Si la Queue alcanza su límite de Back Pressure:

    Object Threshold = 10.000 FlowFiles

    o:

    Data Size Threshold = 1 GB

    GenerateFlowFile dejará normalmente de producir nuevos FlowFiles hasta que la Queue vuelva a disponer de capacidad.

    Tip

    Antes de aumentar tareas concurrentes en un Processor de origen, comprueba que los componentes de destino pueden absorber el incremento de datos.

    Por defecto, NiFi no activa un Processor cuando una de sus conexiones de salida está llena, lo que permite propagar el Back Pressure hacia los componentes anteriores.

    7.30 Configuración inicial recomendada

    Para un flujo sencillo de transformación:

    GenerateFlowFile
        ↓
EvaluateJsonPath
        ↓
UpdateAttribute
        ↓
RouteOnAttribute

    puede utilizarse inicialmente:

    Processor Strategy Run Schedule Concurrent Tasks
    GenerateFlowFile Timer Driven 5 sec 1
    EvaluateJsonPath Timer Driven 0 sec 1
    UpdateAttribute Timer Driven 0 sec 1
    RouteOnAttribute Timer Driven 0 sec 1

    Esta configuración permite:

    • generar datos de forma controlada;
    • procesarlos en cuanto estén disponibles;
    • mantener una ejecución sencilla;
    • observar fácilmente las Queues.

    7.31 Ejemplo de ajuste de rendimiento

    Supongamos que EvaluateJsonPath acumula FlowFiles en su Queue de entrada.

    Situación inicial:

    Concurrent Tasks = 1
Run Schedule = 0 sec

    Antes de aumentar la concurrencia deben revisarse:

    1. El número de FlowFiles pendientes.
    2. El tiempo medio de procesamiento.
    3. El uso de CPU.
    4. El rendimiento del Processor posterior.
    5. El estado del Back Pressure.
    6. La memoria disponible.

    Después puede probarse:

    Concurrent Tasks = 2

    Si mejora el rendimiento sin saturar el sistema, puede mantenerse.

    Posteriormente podría evaluarse:

    Concurrent Tasks = 4

    El ajuste debe realizarse progresivamente.

    flowchart LR
    A[1 tarea]
    --> B[Medir]
    --> C[2 tareas]
    --> D[Medir]
    --> E[4 tareas]
    --> F[Medir]

    Optimización basada en datos

    No optimices un flujo únicamente por intuición. Modifica un parámetro cada vez y compara las métricas antes y después.

    7.32 Errores frecuentes de planificación

    Utilizar un intervalo elevado en un Processor de transformación

    Configurar:

    Run Schedule = 5 min

    en UpdateAttribute provoca que los FlowFiles permanezcan innecesariamente en la Queue.

    Una configuración habitual sería:

    Run Schedule = 0 sec

    Utilizar CRON para todo

    CRON está pensado para calendarios concretos.

    No aporta ventajas para un Processor que debe consumir datos continuamente.

    Aumentar demasiado Concurrent Tasks

    Una concurrencia elevada puede:

    • saturar el servidor;
    • desordenar resultados;
    • agotar conexiones;
    • bloquear una base de datos;
    • superar límites de una API.

    Ejecutar una fuente en todos los nodos

    En clúster puede provocar datos duplicados.

    Debe evaluarse si corresponde utilizar:

    Execution = Primary Node

    Confundir Run Once con un resultado garantizado

    Run Once no procesará datos si:

    • no hay FlowFiles;
    • existe Back Pressure;
    • el Processor no puede realizar trabajo.

    Confundir penalización con yield

    La penalización afecta a un FlowFile.

    El yield afecta al Processor.

    Cambiar varias opciones de rendimiento simultáneamente

    Si se modifican a la vez:

    • Run Schedule;
    • Concurrent Tasks;
    • Run Duration;
    • Back Pressure;

    será difícil determinar qué cambio produjo la mejora o el problema.

    7.33 Buenas prácticas

    Comenzar con una tarea concurrente

    Concurrent Tasks = 1

    Aumentar únicamente cuando exista una necesidad demostrada.

    Utilizar Timer Driven como punto de partida

    Para la mayoría de las transformaciones:

    Scheduling Strategy = Timer Driven
Run Schedule = 0 sec

    Reservar CRON para calendarios

    Utilizarlo cuando la ejecución deba producirse en fechas u horas concretas.

    Utilizar Run Once durante los laboratorios

    Permite generar resultados controlados y facilita la observación del flujo.

    Revisar Execution antes de desplegar en clúster

    Determinar si el Processor debe trabajar:

    • en todos los nodos;
    • únicamente en el nodo primario.

    Proteger los sistemas externos

    La concurrencia de NiFi debe ajustarse a la capacidad de:

    • APIs;
    • bases de datos;
    • servidores de archivos;
    • brokers;
    • servicios remotos.

    Medir antes de optimizar

    Utilizar:

    • métricas de las Queues;
    • estadísticas del Processor;
    • Data Provenance;
    • uso de CPU;
    • tiempos de procesamiento;
    • Bulletins;
    • logs.

    Warning

    No inicies el Processor mediante `Start`, ya que continuará generando nuevos lotes mientras permanezca ejecutándose.

    Laboratorio 3. Observar el Back Pressure

    Objetivo

    Comprobar cómo una Queue llena impide que el Processor anterior continúe generando datos.

    Flujo

    flowchart LR
    A[GenerateFlowFile]
    --> Q[(Queue)]
    --> B[LogAttribute detenido]

    Configuración de la Connection

    Establece:

    Back Pressure Object Threshold = 10

    Configura GenerateFlowFile con:

    Batch Size = 1
Run Schedule = 1 sec

    Procedimiento

    1. Mantén LogAttribute detenido.
    2. Inicia GenerateFlowFile.
    3. Observa cómo crece la Queue.
    4. Espera hasta alcanzar diez FlowFiles.
    5. Comprueba que la generación queda limitada.
    6. Inicia LogAttribute.
    7. Observa cómo disminuye la Queue.
    8. Comprueba que GenerateFlowFile puede volver a producir datos.

    Laboratorio 4. Comparación de tareas concurrentes

    Objetivo

    Analizar el efecto de la concurrencia sobre un Processor.

    Flujo

    flowchart LR
    A[GenerateFlowFile]
    --> B[EvaluateJsonPath]
    --> C[LogAttribute]

    Contenido generado

    {
  "pedido": 1001,
  "cliente": "Alberto",
  "pais": "ES",
  "importe": 1250
}

    EvaluateJsonPath

    Configura:

    Destination = flowfile-attribute

    Añade:

    Atributo JsonPath
    pedido.id $.pedido
    cliente.nombre $.cliente
    cliente.pais $.pais
    pedido.importe $.importe

    Procedimiento

    1. Genera un lote elevado de FlowFiles.
    2. Mantén inicialmente:
    Concurrent Tasks = 1
    1. Observa cuánto tarda en vaciarse la Queue.
    2. Repite el ejercicio con:
    Concurrent Tasks = 2

    1. Compara:

    2. tiempo de procesamiento;

    3. uso de CPU;
    4. comportamiento de las Queues;
    5. orden de finalización.

    Note

    En un laboratorio pequeño la diferencia puede ser mínima. La finalidad es aprender el procedimiento de medición, no demostrar necesariamente una mejora elevada.

    7.34 Clasificación funcional de los Processors

    Apache NiFi dispone de una gran cantidad de Processors.

    Memorizar todos sus nombres no resulta práctico. Es más útil clasificarlos según la función que desempeñan dentro del DataFlow.

    Las principales categorías son:

    1. Generación y recepción de datos.
    2. Enumeración y recuperación.
    3. Extracción de información.
    4. Gestión de atributos.
    5. Transformación del contenido.
    6. Enrutamiento y filtrado.
    7. División de FlowFiles.
    8. Agrupación y combinación.
    9. Validación y enriquecimiento.
    10. Persistencia y envío.
    11. Integración con mensajería.
    12. Invocación de servicios.
    13. Gestión de errores y observabilidad.
    flowchart TB
    P[Processors]

    P --> A[Generación y recepción]
    P --> B[Extracción]
    P --> C[Transformación]
    P --> D[Enrutamiento]
    P --> E[División y combinación]
    P --> F[Persistencia]
    P --> G[Comunicación]
    P --> H[Control y errores]

    Clasificación orientativa

    Un mismo Processor puede participar en más de una categoría. La clasificación se utiliza para comprender su responsabilidad principal dentro del flujo.

    7.35 Processors de generación de datos

    Los Processors de generación crean nuevos FlowFiles sin necesitar necesariamente un FlowFile de entrada.

    Se utilizan para:

    • generar información de prueba;
    • producir mensajes periódicos;
    • iniciar un flujo;
    • consultar una fuente externa;
    • recibir eventos o peticiones.
    flowchart LR
    A[Fuente]
    --> B[Processor de generación]
    --> C[Nuevo FlowFile]

    GenerateFlowFile

    GenerateFlowFile crea uno o varios FlowFiles con contenido configurable.

    Resulta especialmente útil para:

    • laboratorios;
    • pruebas de rendimiento;
    • validación de expresiones;
    • simulación de fuentes de datos;
    • comprobación de rutas.

    Ejemplo de contenido:

    {
  "pedido": 1001,
  "cliente": "Alberto",
  "pais": "ES",
  "importe": 1250
}

    Configuración básica:

    Custom Text = JSON anterior
Batch Size = 1
Data Format = Text

    Warning

    `GenerateFlowFile` es adecuado para pruebas, pero no debe utilizarse como sustituto de una fuente real en producción.

    ListenHTTP

    ListenHTTP permite que NiFi actúe como un punto de recepción HTTP.

    El Processor:

    1. abre un puerto;
    2. espera peticiones;
    3. crea un FlowFile por cada petición recibida;
    4. almacena el cuerpo de la petición como contenido;
    5. añade información HTTP como atributos.
    sequenceDiagram
    participant C as Cliente
    participant N as NiFi
    participant F as FlowFile

    C->>N: Petición HTTP
    N->>F: Crear FlowFile
    F-->>N: Contenido y atributos

    Posibles atributos:

    http.method = POST
http.request.uri = /pedidos
http.remote.host = 192.168.1.50
mime.type = application/json

    Note

    Los nombres exactos de los atributos dependen del Processor y de su versión. Deben consultarse en la documentación integrada.

    ConsumeKafka

    Los Processors de consumo de Kafka reciben mensajes desde uno o varios topics y crean FlowFiles con esos datos.

    Se utilizan en arquitecturas:

    • orientadas a eventos;
    • de streaming;
    • de integración de microservicios;
    • de procesamiento de logs;
    • de Internet de las cosas.
    flowchart LR
    A[Productores]
    --> B[(Kafka)]
    --> C[ConsumeKafka]
    --> D[FlowFiles]

    Dependiendo del Processor y de su configuración, varios mensajes pueden:

    • agruparse en un FlowFile;
    • producir FlowFiles separados;
    • conservar información sobre topic, partición y offset.

    7.36 Processors de listado y recuperación

    En muchos sistemas conviene separar dos operaciones:

    1. detectar qué elementos existen;
    2. recuperar su contenido.

    Este patrón se conoce habitualmente como List/Fetch.

    flowchart LR
    A[Listar recursos]
    --> B[FlowFiles con metadatos]
    --> C[Recuperar contenido]
    --> D[FlowFiles completos]

    Ejemplos:

    ListFile → FetchFile

    ListSFTP → FetchSFTP

    ListFTP → FetchFTP

    ListHDFS → FetchHDFS

    ListFile

    ListFile examina un directorio y genera información sobre los archivos encontrados.

    Por defecto puede crear un FlowFile por cada archivo listado, incorporando atributos como:

    filename
path
fileSize
file.lastModifiedTime

    El contenido del archivo todavía no tiene por qué estar dentro del FlowFile.

    flowchart LR
    A[Directorio]
    --> B[ListFile]
    --> C[FlowFile con metadatos]

    El Processor mantiene estado para evitar listar repetidamente los mismos archivos.

    FetchFile

    FetchFile utiliza los atributos generados previamente para recuperar el contenido real del archivo.

    flowchart LR
    A[FlowFile con filename y path]
    --> B[FetchFile]
    --> C[FlowFile con contenido]

    El patrón completo sería:

    flowchart LR
    A[ListFile]
    --> B[FetchFile]
    --> C[Procesamiento]

    La documentación oficial recomienda habitualmente combinar ListFile y FetchFile para vigilar un directorio y recuperar nuevos archivos mediante un flujo continuo.

    List/Fetch

    Utiliza el patrón List/Fetch cuando necesites:

- conservar el archivo original;
- distribuir la recuperación;
- controlar qué elementos ya se han procesado;
- separar la detección de la descarga.

    GetFile

    GetFile reúne en un solo Processor la detección y la lectura de archivos locales.

    Lee archivos de un directorio y crea nuevos FlowFiles cuyo contenido corresponde al archivo original.

    flowchart LR
    A[Directorio local]
    --> B[GetFile]
    --> C[FlowFile con contenido]

    GetFile es sencillo y adecuado para laboratorios, pero debe configurarse con precaución porque puede eliminar el archivo original después de procesarlo, dependiendo de la propiedad correspondiente.

    Archivo de origen

    Antes de iniciar `GetFile`, revisa siempre la opción que determina si el archivo original se conserva o se elimina.

    GetFile frente a ListFile y FetchFile

    Característica GetFile ListFile + FetchFile
    Número de Processors Uno Dos
    Configuración inicial Sencilla Más elaborada
    Separación listado/lectura No Sí
    Gestión distribuida Limitada Más flexible
    Adecuado para laboratorios Sí Sí
    Adecuado para diseños escalables Según el caso Habitualmente mejor

    7.37 Processors de extracción de información

    Los Processors de extracción leen el contenido de un FlowFile y generan atributos a partir de él.

    No tienen por qué modificar el contenido.

    flowchart LR
    A[Contenido]
    --> B[Processor de extracción]
    --> C[Atributos]

    Ejemplos:

    • EvaluateJsonPath;
    • EvaluateXPath;
    • ExtractText;
    • ExtractEmailHeaders;
    • ExtractGrok;
    • CountText.

    EvaluateJsonPath

    EvaluateJsonPath evalúa expresiones JsonPath sobre un contenido JSON.

    Puede enviar el resultado:

    • a un atributo;
    • al contenido del FlowFile.

    Ejemplo de entrada:

    {
  "pedido": 1001,
  "cliente": {
    "nombre": "Alberto",
    "pais": "ES"
  },
  "importe": 1250
}

    Propiedades dinámicas:

    Atributo JsonPath
    pedido.id $.pedido
    cliente.nombre $.cliente.nombre
    cliente.pais $.cliente.pais
    pedido.importe $.importe

    Con:

    Destination = flowfile-attribute

    se obtendrán:

    pedido.id = 1001
cliente.nombre = Alberto
cliente.pais = ES
pedido.importe = 1250

    flowchart LR
    A[JSON]
    --> B[EvaluateJsonPath]
    --> C[Atributos extraídos]

    Tip

    Extrae como atributos únicamente los valores que necesites para controlar el flujo. No conviertas todo el documento en atributos sin una razón concreta.

    EvaluateXPath

    EvaluateXPath realiza una función semejante sobre documentos XML.

    Entrada:

    <pedido>
    <id>1001</id>
    <cliente pais="ES">Alberto</cliente>
    <importe>1250</importe>
</pedido>

    Propiedades:

    Atributo XPath
    pedido.id /pedido/id/text()
    cliente.nombre /pedido/cliente/text()
    cliente.pais /pedido/cliente/@pais
    pedido.importe /pedido/importe/text()

    EvaluateXPath puede escribir los resultados como atributos o como contenido, según su configuración.

    ExtractText

    ExtractText evalúa expresiones regulares sobre contenido textual y almacena las coincidencias como atributos.

    Contenido:

    PEDIDO=1001;PAIS=ES;IMPORTE=1250

    Propiedades dinámicas:

    pedido.id = PEDIDO=([0-9]+)

    cliente.pais = PAIS=([A-Z]{2})

    pedido.importe = IMPORTE=([0-9]+)

    Resultado:

    pedido.id = 1001
cliente.pais = ES
pedido.importe = 1250

    flowchart LR
    A[Texto]
    --> B[Expresión regular]
    --> C[Atributos]

    ExtractText asigna a atributos los resultados obtenidos mediante expresiones regulares configuradas como propiedades dinámicas.

    Expresiones regulares

    No utilices expresiones regulares para analizar formatos estructurados complejos como JSON o XML cuando existan Processors específicos para esos formatos.

    CountText

    CountText analiza contenido textual y puede generar atributos relacionados con:

    • número de líneas;
    • número de palabras;
    • número de caracteres;
    • presencia de determinadas estructuras.

    Puede utilizarse para validar tamaños o tomar decisiones sin transformar el contenido.

    7.38 Processors de gestión de atributos

    Estos Processors trabajan principalmente con los metadatos del FlowFile.

    Los más habituales son:

    • UpdateAttribute;
    • DeleteAttribute;
    • AttributesToJSON;
    • LogAttribute.

    UpdateAttribute

    UpdateAttribute permite:

    • crear atributos;
    • modificar atributos;
    • calcular valores;
    • aplicar NiFi Expression Language;
    • utilizar reglas avanzadas;
    • mantener determinado estado en configuraciones específicas.

    Ejemplo:

    departamento = facturacion

    fecha.proceso = ${now():format("yyyy-MM-dd")}

    nombre.salida = ${filename:substringBeforeLast(".")}_procesado.json

    flowchart LR
    A[Atributos originales]
    --> B[UpdateAttribute]
    --> C[Atributos actualizados]

    DeleteAttribute

    DeleteAttribute elimina atributos cuyos nombres coinciden con un patrón.

    Ejemplo:

    Delete Attributes Expression = ^temporal\..*

    Podría eliminar:

    temporal.usuario
temporal.fecha
temporal.prueba

    y conservar:

    filename
path
pedido.id

    Warning

    No deben eliminarse atributos estándar como `filename`, `path` o `uuid` sin comprender el efecto sobre los Processors posteriores.

    AttributesToJSON

    AttributesToJSON convierte atributos seleccionados en un documento JSON.

    Atributos:

    pedido.id = 1001
cliente.pais = ES
pedido.importe = 1250

    Resultado:

    {
  "pedido.id": "1001",
  "cliente.pais": "ES",
  "pedido.importe": "1250"
}

    El resultado puede escribirse:

    • en el contenido;
    • en otro atributo.

    Warning

    Si el destino es el contenido del FlowFile, el contenido anterior será sustituido por el JSON generado.

    LogAttribute

    LogAttribute registra atributos del FlowFile en los logs de NiFi.

    Resulta útil para:

    • laboratorios;
    • depuración;
    • comprobar expresiones;
    • verificar rutas;
    • observar cambios.
    flowchart LR
    A[FlowFile]
    --> B[LogAttribute]
    --> C[Log de NiFi]

    Producción

    Registrar todos los atributos o el contenido de grandes volúmenes de FlowFiles puede generar logs excesivos y exponer información sensible.

    7.39 Processors de transformación del contenido

    Los Processors de transformación cambian los datos almacenados en el Content Repository.

    flowchart LR
    A[Contenido original]
    --> B[Processor de transformación]
    --> C[Nuevo contenido]

    Entre ellos se encuentran:

    • ReplaceText;
    • JoltTransformJSON;
    • TransformXml;
    • ConvertRecord;
    • UpdateRecord;
    • QueryRecord;
    • ConvertCharacterSet;
    • CompressContent;
    • EncryptContent.

    ReplaceText

    ReplaceText modifica contenido textual.

    Puede utilizarse para:

    • sustituir una cadena;
    • reemplazar todo el contenido;
    • añadir una cabecera;
    • añadir un pie;
    • utilizar expresiones regulares;
    • construir contenido mediante atributos.

    Ejemplo de entrada:

    Hola ${nombre}

    También puede configurarse para generar un documento nuevo utilizando atributos:

    {
  "pedido": "${pedido.id}",
  "pais": "${cliente.pais}",
  "procesado": "${now():format('yyyy-MM-dd HH:mm:ss')}"
}

    Warning

    `ReplaceText` es útil para transformaciones sencillas. Para JSON, XML o datos tabulares complejos conviene utilizar Processors estructurados.

    JoltTransformJSON

    JoltTransformJSON aplica especificaciones Jolt sobre documentos JSON.

    Permite:

    • cambiar nombres de campos;
    • reestructurar objetos;
    • mover valores;
    • crear arrays;
    • eliminar campos;
    • adaptar un JSON al contrato de otro sistema.

    Entrada:

    {
  "id": 1001,
  "customer": "Alberto",
  "country": "ES"
}

    Salida deseada:

    {
  "pedido": {
    "identificador": 1001,
    "cliente": "Alberto"
  },
  "pais": "ES"
}

    flowchart LR
    A[JSON de origen]
    --> B[JoltTransformJSON]
    --> C[JSON de destino]

    TransformXml

    TransformXml aplica una transformación XSLT sobre contenido XML.

    flowchart LR
    A[XML]
    --> B[TransformXml + XSLT]
    --> C[XML, HTML o texto]

    Se utiliza en integraciones donde es necesario adaptar documentos XML entre distintos esquemas.

    ConvertRecord

    ConvertRecord transforma datos estructurados utilizando:

    • un Record Reader;
    • un Record Writer.

    Ejemplos:

    CSV → JSON

    JSON → Avro

    Avro → CSV

    XML → JSON

    flowchart LR
    A[Contenido]
    --> B[Record Reader]
    --> C[Records]
    --> D[Record Writer]
    --> E[Nuevo formato]

    El Processor no necesita que la transformación se programe campo a campo cuando ambos formatos representan los mismos registros.

    Note

    Los Record Readers y Record Writers son Controller Services y se estudiarán en profundidad en los capítulos posteriores.

    UpdateRecord

    UpdateRecord modifica campos concretos dentro de registros estructurados.

    Ejemplos:

    • actualizar un país;
    • calcular un importe;
    • eliminar un campo;
    • normalizar una fecha;
    • crear un valor derivado.
    flowchart LR
    A[Registros]
    --> B[UpdateRecord]
    --> C[Registros modificados]

    Es preferible a transformar todo el documento con texto cuando se trabaja con datos estructurados.

    QueryRecord

    QueryRecord permite consultar registros mediante sentencias similares a SQL.

    Ejemplo conceptual:

    SELECT *
FROM FLOWFILE
WHERE importe > 1000

    Puede crear relaciones dinámicas como:

    pedidos_altos
pedidos_normales

    flowchart TB
    A[Registros]
    --> B[QueryRecord]

    B -->|importe > 1000| C[Pedidos altos]
    B -->|importe <= 1000| D[Pedidos normales]

    7.40 Processors de enrutamiento y filtrado

    Estos Processors deciden por qué camino debe continuar cada FlowFile.

    flowchart TB
    A[FlowFile]
    --> B[Condición]

    B -->|Verdadera| C[Ruta A]
    B -->|Falsa| D[Ruta B]

    Ejemplos:

    • RouteOnAttribute;
    • RouteOnContent;
    • RouteText;
    • QueryRecord;
    • DetectDuplicate.

    RouteOnAttribute

    RouteOnAttribute evalúa expresiones sobre los atributos del FlowFile.

    Cada propiedad dinámica define:

    • el nombre de una Relationship;
    • una expresión booleana.

    Ejemplo:

    Relationship Expresión
    urgentes ${pedido.urgente:equals("true")}
    espana ${cliente.pais:equals("ES")}
    importe_alto ${pedido.importe:toNumber():gt(1000)} 
    flowchart TB
    A[RouteOnAttribute]

    A -->|urgentes| B[Procesamiento prioritario]
    A -->|espana| C[Flujo nacional]
    A -->|unmatched| D[Otros]

    Las expresiones configuradas deben producir un valor booleano.

    RouteOnAttribute crea relaciones dinámicas a partir del nombre de cada propiedad y utiliza Expression Language sobre los atributos para decidir el enrutamiento.

    Estrategias de enrutamiento

    Según la configuración, un FlowFile puede:

    • enviarse a todas las rutas coincidentes;
    • enviarse a la primera ruta coincidente;
    • enviarse según una combinación de condiciones.

    Ejemplo:

    pais = ES
importe = 1250

    El mismo FlowFile podría coincidir con:

    espana
importe_alto

    Warning

    Antes de diseñar rutas, decide si un FlowFile puede recorrer varias salidas o debe elegir únicamente una.

    Relationship unmatched

    Los FlowFiles que no cumplen ninguna expresión suelen enviarse a:

    unmatched

    No debe auto-terminarse automáticamente sin analizar si esos datos:

    • son válidos;
    • deben conservarse;
    • requieren revisión;
    • representan un caso no contemplado.

    RouteOnContent

    RouteOnContent examina el contenido mediante expresiones regulares y crea rutas según las coincidencias.

    Contenido:

    ERROR No se pudo conectar con la base de datos

    Ruta dinámica:

    errores = ERROR

    flowchart LR
    A[Contenido]
    --> B[RouteOnContent]
    -->|Coincide| C[Ruta de error]
    -->|No coincide| D[unmatched]

    RouteText

    RouteText está orientado a enrutar líneas individuales de texto.

    Puede evaluar cada línea y separar, por ejemplo:

    • registros válidos;
    • registros con error;
    • cabeceras;
    • comentarios;
    • líneas vacías.

    7.41 Processors de división

    Los Processors de división generan varios FlowFiles a partir de uno original.

    flowchart LR
    A[FlowFile original]
    --> B[Split]
    --> C[Fragmento 1]
    B --> D[Fragmento 2]
    B --> E[Fragmento 3]

    Ejemplos:

    • SplitText;
    • SplitContent;
    • SplitJson;
    • SplitXml;
    • SplitRecord.

    SplitText

    SplitText divide contenido textual según:

    • número de líneas;
    • tamaño;
    • cabeceras;
    • límites configurados.

    Entrada:

    pedido1
pedido2
pedido3
pedido4

    Configurado para una línea por fragmento:

    FlowFile 1 → pedido1
FlowFile 2 → pedido2
FlowFile 3 → pedido3
FlowFile 4 → pedido4

    SplitJson

    SplitJson divide una estructura JSON utilizando una expresión JsonPath.

    Entrada:

    {
  "pedidos": [
    {"id": 1},
    {"id": 2},
    {"id": 3}
  ]
}

    Expresión:

    $.pedidos[*]

    Resultado:

    {"id": 1}

    {"id": 2}

    {"id": 3}

    SplitRecord

    SplitRecord divide un conjunto de registros utilizando un Record Reader y un Record Writer.

    Es apropiado para:

    • CSV;
    • JSON;
    • Avro;
    • otros formatos estructurados.
    flowchart LR
    A[10.000 registros]
    --> B[SplitRecord]
    --> C[1.000 registros]
    B --> D[1.000 registros]
    B --> E[...]

    Atributos de fragmentación

    Los Processors de división suelen generar atributos que permiten identificar los fragmentos.

    Conceptualmente:

    fragment.identifier
fragment.index
fragment.count

    Estos metadatos permiten reagrupar posteriormente las partes relacionadas.

    Note

    Los atributos exactos escritos por cada Processor deben comprobarse en su documentación.

    Riesgo de explosión de FlowFiles

    Dividir un fichero muy grande puede crear miles o millones de FlowFiles.

    Ejemplo:

    1 archivo con 10.000.000 de líneas

    Si se genera un FlowFile por línea:

    10.000.000 de FlowFiles

    Esto puede provocar:

    • colas enormes;
    • presión sobre el FlowFile Repository;
    • incremento de Provenance;
    • mayor uso de memoria;
    • menor rendimiento.

    Granularidad

    No dividas los datos más de lo necesario. Cuando sea posible, procesa lotes de registros en lugar de crear un FlowFile por cada registro.

    7.42 Processors de combinación

    Los Processors de combinación realizan la operación contraria: generan un FlowFile a partir de varios.

    flowchart LR
    A[FlowFile 1]
    --> D[Merge]

    B[FlowFile 2]
    --> D

    C[FlowFile 3]
    --> D

    D --> E[FlowFile combinado]

    Ejemplos:

    • MergeContent;
    • MergeRecord;
    • MergeTableNode;
    • Processors específicos de agregación.

    MergeContent

    MergeContent combina el contenido de varios FlowFiles.

    Puede utilizar estrategias como:

    • concatenación;
    • ensamblaje de fragmentos;
    • empaquetado en ZIP;
    • empaquetado en TAR.

    Ejemplo:

    pedido1
pedido2
pedido3

    Resultado concatenado:

    pedido1
pedido2
pedido3

    MergeRecord

    MergeRecord combina registros utilizando un Record Reader y un Record Writer.

    Es preferible a MergeContent cuando el contenido representa datos estructurados.

    flowchart LR
    A[Records A]
    --> C[MergeRecord]

    B[Records B]
    --> C

    C --> D[Conjunto de records]

    Bins

    Los Processors de combinación suelen agrupar FlowFiles en estructuras internas denominadas bins.

    Un bin puede cerrarse cuando se alcanza:

    • un número mínimo;
    • un número máximo;
    • un tamaño mínimo;
    • un tamaño máximo;
    • una antigüedad máxima.
    flowchart TB
    A[FlowFiles]
    --> B[Bin]

    B -->|Umbral alcanzado| C[FlowFile combinado]

    Esperas indefinidas

    Una configuración incorrecta puede provocar que los FlowFiles permanezcan mucho tiempo esperando a completar un grupo.

    Correlation Attribute

    Cuando solo deben combinarse FlowFiles relacionados, puede utilizarse un atributo de correlación.

    Ejemplo:

    pedido.lote = lote-2026-07-31

    Solo se combinarían FlowFiles con el mismo valor.

    flowchart TB
    A[Lote A]
    --> M1[Merge A]

    B[Lote A]
    --> M1

    C[Lote B]
    --> M2[Merge B]

    7.43 Processors de validación

    Los Processors de validación comprueban si los datos cumplen determinados requisitos.

    Ejemplos:

    • ValidateJson;
    • ValidateXml;
    • ValidateRecord;
    • VerifyContentMD5;
    • VerifyContentCRC32.
    flowchart TB
    A[Datos]
    --> B[Validación]

    B -->|valid| C[Procesamiento]
    B -->|invalid| D[Cuarentena]

    ValidateRecord

    ValidateRecord valida datos estructurados respecto de un esquema.

    Puede comprobar:

    • tipos;
    • campos obligatorios;
    • estructura;
    • compatibilidad con el esquema;
    • valores interpretables.
    flowchart LR
    A[Registros]
    --> B[Record Reader]
    --> C[Schema]
    --> D{¿Válidos?}

    D -->|Sí| E[valid]
    D -->|No| F[invalid]

    Validación técnica y validación de negocio

    No deben confundirse.

    Validación técnica

    Comprueba cuestiones como:

    • JSON correctamente formado;
    • fecha interpretable;
    • número válido;
    • estructura compatible.

    Validación de negocio

    Comprueba reglas como:

    • importe superior a cero;
    • país permitido;
    • pedido existente;
    • cliente activo;
    • fecha dentro del periodo.
    flowchart LR
    A[Datos]
    --> B[Validación técnica]
    --> C[Validación de negocio]
    --> D[Procesamiento]

    Tip

    Realiza primero la validación técnica. Solo después aplica reglas de negocio.

    7.44 Processors de enriquecimiento

    Enriquecer significa añadir información obtenida de otra fuente.

    Ejemplo inicial:

    {
  "cliente_id": 25,
  "importe": 1250
}

    Después del enriquecimiento:

    {
  "cliente_id": 25,
  "cliente_nombre": "Empresa A",
  "segmento": "Premium",
  "importe": 1250
}

    Ejemplos de Processors:

    • LookupAttribute;
    • LookupRecord;
    • ExecuteSQLRecord;
    • InvokeHTTP;
    • Processors de caché distribuida.

    LookupRecord

    LookupRecord consulta un Lookup Service para enriquecer cada registro.

    Puede utilizar fuentes como:

    • CSV;
    • base de datos;
    • mapa clave-valor;
    • servicio REST;
    • Elasticsearch;
    • fichero de propiedades.
    flowchart LR
    A[Registro con cliente_id]
    --> B[LookupRecord]
    --> C[Lookup Service]
    --> D[Registro enriquecido]

    El Processor utiliza un Record Reader, un Lookup Service y un Record Writer.

    Evitar una consulta por registro

    Supongamos que un FlowFile contiene 100.000 registros.

    Realizar una petición HTTP independiente para cada registro puede ser muy costoso.

    Antes de diseñar el enriquecimiento deben considerarse:

    • procesamiento por lotes;
    • caché;
    • Lookup Services;
    • consultas masivas;
    • límites de la API;
    • latencia del sistema externo.

    7.45 Processors de persistencia

    Los Processors de persistencia escriben el contenido en un sistema de almacenamiento.

    Ejemplos:

    • PutFile;
    • PutSFTP;
    • PutHDFS;
    • PutDatabaseRecord;
    • PutElasticsearchRecord;
    • Processors para almacenamiento cloud.
    flowchart LR
    A[FlowFile]
    --> B[Processor Put]
    --> C[Sistema de destino]

    PutFile

    PutFile escribe el contenido del FlowFile en el sistema de archivos local.

    Utiliza normalmente atributos como:

    filename
path

    Ejemplo:

    filename = pedido_1001.json

    Directorio configurado:

    /datos/salida

    Resultado:

    /datos/salida/pedido_1001.json

    Estrategia de conflicto

    Si el archivo ya existe, el Processor debe saber qué hacer.

    Las opciones pueden incluir:

    • reemplazar;
    • fallar;
    • ignorar;
    • conservar ambos según el componente.

    Warning

    Una estrategia de reemplazo puede destruir información existente. Debe seleccionarse de forma consciente.

    PutDatabaseRecord

    PutDatabaseRecord escribe registros en una base de datos.

    Requiere normalmente:

    • Record Reader;
    • servicio de conexión a base de datos;
    • nombre de tabla;

    • gestión de errores.
    flowchart LR
    A[CSV o JSON]
    --> B[Record Reader]
    --> C[PutDatabaseRecord]
    --> D[(Base de datos)]

    Puede utilizarse para operaciones como:

    • INSERT;
    • UPDATE;
    • UPSERT;
    • otras opciones compatibles con el Processor y la base de datos.

    Transacciones y lotes

    Al escribir en bases de datos debe considerarse:

    • tamaño del lote;
    • número de tareas concurrentes;
    • pool de conexiones;
    • tiempo de transacción;
    • bloqueos;
    • reintentos;
    • duplicados.
    flowchart LR
    A[Muchos registros]
    --> B[Lotes]
    --> C[Transacciones]
    --> D[(Base de datos)]

    InvokeHTTP

    Puede utilizar:

    • método dinámico;
    • URL dinámica;

    • autenticación;
    • cuerpo procedente del FlowFile;
    • respuesta como contenido.

    N->>A: Petición HTTP

    7.49 Selección del Processor adecuado

    Elegir correctamente un Processor requiere responder varias preguntas.

    flowchart TD
    A[Operación necesaria]
    --> B{¿Crear o recibir datos?}

    B -->|Sí| C[Processor de origen]
    B -->|No| D{¿Modificar atributos?}

    D -->|Sí| E[UpdateAttribute]
    D -->|No| F{¿Extraer del contenido?}

    F -->|JSON| G[EvaluateJsonPath]
    F -->|XML| H[EvaluateXPath]
    F -->|Texto| I[ExtractText]
    F -->|No| J{¿Transformar estructura?}

    J -->|Records| K[ConvertRecord o UpdateRecord]
    J -->|JSON complejo| L[JoltTransformJSON]
    J -->|Texto simple| M[ReplaceText]

    Pregunta 1. ¿Trabajarás con contenido o atributos?

    Atributos

    Utiliza, según la operación:

    • UpdateAttribute;
    • DeleteAttribute;
    • RouteOnAttribute;
    • AttributesToJSON.

    Contenido

    Utiliza, según el formato:

    • ReplaceText;
    • JoltTransformJSON;
    • TransformXml;
    • ConvertRecord;
    • UpdateRecord;
    • QueryRecord.

    Pregunta 2. ¿El formato es estructurado?

    Si los datos son:

    • CSV;
    • JSON;
    • Avro;
    • XML;
    • Parquet;
    • otros formatos tabulares;

    conviene evaluar el uso de Processors basados en Records.

    flowchart TD
    A{¿Datos estructurados?}

    A -->|Sí| B[Record Processors]
    A -->|No| C[Text o Content Processors]

    Pregunta 3. ¿Necesitas un FlowFile por registro?

    En muchos casos, no.

    Supongamos un CSV con un millón de filas.

    Alternativa poco eficiente

    SplitText → un FlowFile por línea

    Alternativa normalmente más eficiente

    QueryRecord
UpdateRecord
ConvertRecord
PutDatabaseRecord

    Los Record Processors pueden trabajar con múltiples registros dentro del mismo FlowFile.

    Tip

    Conserva los datos agrupados mientras no exista una razón funcional para dividirlos.

    Pregunta 4. ¿Necesitas extraer o transformar?

    No son lo mismo.

    Extraer

    Leer un valor y convertirlo en atributo:

    EvaluateJsonPath

    Transformar

    Modificar la estructura del contenido:

    JoltTransformJSON

    Actualizar un atributo

    Crear metadatos para controlar el flujo:

    UpdateAttribute

    Pregunta 5. ¿La fuente debe conservarse?

    Para archivos:

    • GetFile puede leer y retirar el original;
    • ListFile y FetchFile permiten separar el seguimiento de la recuperación;
    • otras fuentes poseen estrategias equivalentes.

    Pregunta 6. ¿Puede repetirse la operación?

    Antes de utilizar un Processor de salida, comprueba si la operación es idempotente.

    Una operación idempotente puede repetirse sin producir efectos adicionales no deseados.

    Ejemplo:

    Sobrescribir pedido_1001.json

    puede ser idempotente si siempre representa el mismo estado.

    Ejemplo no idempotente:

    INSERT del mismo pedido

    podría crear duplicados.

    7.51 Diseño de un flujo completo

    Supongamos que NiFi recibe pedidos JSON mediante HTTP.

    Los requisitos son:

    1. Recibir el JSON.
    2. Validar su estructura.
    3. Extraer el país y el importe.
    4. Clasificar el pedido.
    5. Añadir metadatos.
    6. Guardarlo en un directorio.
    7. Separar los errores.

    El flujo podría ser:

    flowchart LR
    A[ListenHTTP]
    --> B[ValidateJson]
    --> C[EvaluateJsonPath]
    --> D[UpdateAttribute]
    --> E[RouteOnAttribute]
    --> F[PutFile]

    B -->|invalid| G[Errores de validación]
    C -->|failure| H[Errores de extracción]
    F -->|failure| I[Errores de escritura]

    Paso 1. Recepción

    ListenHTTP crea el FlowFile.

    Contenido:

    {
  "pedido": 1001,
  "pais": "ES",
  "importe": 1250,
  "urgente": true
}

    Paso 2. Validación

    ValidateJson comprueba que el documento está correctamente formado.

    Rutas:

    valid
invalid

    Paso 3. Extracción

    EvaluateJsonPath genera:

    pedido.id = 1001
cliente.pais = ES
pedido.importe = 1250
pedido.urgente = true

    Paso 4. Enriquecimiento de atributos

    UpdateAttribute añade:

    fecha.proceso = ${now():format("yyyy-MM-dd'T'HH:mm:ss")}

    nombre.salida = pedido_${pedido.id}.json

    filename = ${nombre.salida}

    Paso 5. Clasificación

    RouteOnAttribute crea:

    urgentes = ${pedido.urgente:equals("true")}

    importe_alto = ${pedido.importe:toNumber():gt(1000)}

    espana = ${cliente.pais:equals("ES")}

    Paso 6. Persistencia

    PutFile utiliza:

    Directory = /datos/pedidos/${cliente.pais}

    El resultado sería:

    /datos/pedidos/ES/pedido_1001.json

    7.52 Gestión de errores

    Todo flujo de producción debe diseñar explícitamente qué ocurre cuando una operación falla.

    flowchart TB
    A[Processor principal]

    A -->|success| B[Flujo normal]
    A -->|failure| C[Gestión de errores]

    No basta con conectar todas las relaciones failure a un único LogAttribute.

    La estrategia debe considerar:

    • tipo de error;
    • posibilidad de reintento;
    • número de reintentos;
    • conservación del contenido;
    • notificación;
    • trazabilidad;
    • intervención humana.

    Errores temporales

    Son problemas que pueden desaparecer al repetir la operación:

    • API no disponible;
    • timeout;
    • conexión rechazada;
    • base de datos saturada;
    • broker temporalmente inaccesible;
    • respuesta HTTP 429;
    • respuesta HTTP 5xx.

    Estrategia posible:

    flowchart LR
    A[Operación]
    -->|fallo temporal| B[Penalización]
    --> C[Espera]
    --> D[Reintento]

    Errores permanentes

    No suelen resolverse repitiendo exactamente la misma operación:

    • JSON mal formado;
    • campo obligatorio ausente;
    • credenciales incorrectas;
    • URL inexistente;
    • dato incompatible con el esquema;
    • regla de negocio incumplida.

    Estrategia posible:

    flowchart LR
    A[Operación]
    -->|fallo permanente| B[Cuarentena]
    --> C[Revisión]

    Errores del dato y errores del sistema

    Error del dato

    El problema pertenece al FlowFile:

    importe = "desconocido"

    Error del sistema

    El dato puede ser correcto, pero el destino no responde:

    Connection refused

    flowchart TB
    A[Error]

    A --> B[Error del dato]
    B --> C[Cuarentena]

    A --> D[Error del sistema]
    D --> E[Reintento]

    7.53 Patrón de reintento controlado

    Un reintento debe tener límite.

    Puede utilizarse un atributo:

    retry.count

    Primera vez:

    retry.count = 1

    Siguientes intentos:

    retry.count = ${retry.count:plus(1)}

    Ruta de reintento:

    ${retry.count:toNumber():lt(3)}

    Ruta definitiva:

    ${retry.count:toNumber():ge(3)}

    flowchart TD
    A[Operación]
    -->|failure| B[Incrementar retry.count]
    --> C{¿Menos de 3?}

    C -->|Sí| D[Esperar y reintentar]
    D --> A

    C -->|No| E[Dead Letter Queue]

    Bucle infinito

    No conectes una relación `failure` directamente al mismo Processor sin límite, espera ni control. Podrías crear un ciclo de reintentos continuo.

    7.54 Dead Letter Queue

    Una Dead Letter Queue es una ruta donde se almacenan los FlowFiles que no han podido procesarse después de los intentos permitidos.

    Puede implementarse mediante:

    • una Queue específica;
    • un directorio;
    • una tabla;
    • un topic de Kafka;
    • un bucket;
    • un sistema de incidencias.
    flowchart LR
    A[Fallos definitivos]
    --> B[(Dead Letter Queue)]
    --> C[Análisis o reprocesamiento]

    Conviene conservar:

    error.message
error.processor
error.timestamp
retry.count
original.filename

    7.55 Flujo de errores reutilizable

    En lugar de repetir la misma lógica tras cada Processor, puede crearse un Process Group específico.

    flowchart LR
    A[Flujo principal]
    -->|failure| B[[Gestión de errores]]

    B --> C[Actualizar atributos]
    --> D[Registrar]
    --> E[Guardar en cuarentena]
    --> F[Notificar]

    El Process Group puede recibir FlowFiles mediante un Input Port.

    Ventajas:

    • lógica centralizada;
    • formato de error común;
    • menor duplicación;
    • mantenimiento sencillo;
    • observabilidad uniforme.

    7.57 Errores frecuentes

    Confundir extracción con transformación

    EvaluateJsonPath extrae valores.

    JoltTransformJSON reestructura el JSON.

    Utilizar UpdateAttribute para modificar el contenido

    UpdateAttribute solo trabaja con atributos.

    Utilizar AttributesToJSON esperando conservar el contenido

    Cuando escribe en flowfile-content, sustituye el contenido existente.

    Dividir excesivamente

    Un FlowFile por registro puede generar una sobrecarga muy elevada.

    Auto-terminar failure

    Puede ocultar errores y provocar pérdida silenciosa de datos.

    Reintentar errores permanentes

    Un JSON mal formado no se corregirá por repetir la misma operación.

    No controlar duplicados

    Un reintento de escritura puede repetir una operación que ya se completó en el sistema externo, aunque NiFi no recibiera la confirmación.

    Utilizar expresiones regulares sobre JSON complejo

    Es preferible utilizar EvaluateJsonPath, Record Processors o herramientas estructuradas.

    No comprobar la capacidad del destino

    Aumentar Concurrent Tasks en PutDatabaseRecord, InvokeHTTP o PublishKafka puede trasladar la saturación al sistema externo.

    Laboratorio 7. Gestión básica de errores

    Objetivo

    Separar el procesamiento correcto de los datos no válidos.

    Flujo

    flowchart TB
    A[GenerateFlowFile]
    --> B[EvaluateJsonPath]

    B -->|matched| C[Procesamiento correcto]
    B -->|unmatched| D[Actualizar error]
    B -->|failure| D

    D --> E[LogAttribute]

    La nomenclatura exacta de las Relationships debe adaptarse a las que muestre la versión instalada de EvaluateJsonPath.

    Documento correcto

    {
  "pedido": 1001,
  "pais": "ES"
}

    Documento incorrecto

    {
  "pedido": 1001,
  "pais":
}

    Ruta de error

    Añade UpdateAttribute:

    error.processor = EvaluateJsonPath

    error.timestamp = ${now():format("yyyy-MM-dd'T'HH:mm:ss")}

    error.filename = ${filename}

    Después conecta el FlowFile a LogAttribute.

    Laboratorio 8. Flujo completo de pedidos

    Objetivo

    Construir un flujo que combine generación, extracción, actualización, enrutamiento y persistencia.

    Flujo

    flowchart LR
    A[GenerateFlowFile]
    --> B[EvaluateJsonPath]
    --> C[UpdateAttribute]
    --> D[RouteOnAttribute]

    D -->|espana| E[PutFile ES]
    D -->|internacional| F[PutFile INT]

    B -->|failure| G[Gestión de errores]
    E -->|failure| G
    F -->|failure| G

    Contenido

    {
  "pedido": 1001,
  "cliente": "Alberto",
  "pais": "ES",
  "importe": 1250
}

    EvaluateJsonPath

    pedido.id = $.pedido
cliente.nombre = $.cliente
cliente.pais = $.pais
pedido.importe = $.importe

    UpdateAttribute

    filename = pedido_${pedido.id}.json

    fecha.proceso = ${now():format("yyyy-MM-dd")}

    tipo.pedido = ${pedido.importe:toNumber():gt(1000):ifElse("alto","normal")}

    RouteOnAttribute

    Ruta:

    espana

    Expresión:

    ${cliente.pais:equals("ES")}

    Ruta:

    internacional

    Expresión:

    ${cliente.pais:equals("ES"):not()}

    Directorios

    PutFile ES:

    Directory = /datos/pedidos/espana

    PutFile INT:

    Directory = /datos/pedidos/internacional

    Comprobación

    1. Ejecuta un pedido de España.
    2. Comprueba el directorio utilizado.
    3. Cambia el país a FR.
    4. Ejecuta otro FlowFile.
    5. Comprueba la segunda ruta.
    6. Fuerza un error indicando un directorio no válido.
    7. Analiza la Relationship failure.
    8. Consulta el recorrido completo en Data Provenance.
