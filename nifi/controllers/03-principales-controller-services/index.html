    Objetivos

    En el capítulo anterior se estudió cómo crear, configurar y habilitar un Controller Service utilizando como ejemplo DBCPConnectionPool. Sin embargo, Apache NiFi incorpora decenas de Controller Services destinados a resolver necesidades muy diferentes: acceso a bases de datos, lectura y escritura de registros, comunicaciones seguras, enriquecimiento de datos o integración con sistemas externos.

    El objetivo de este capítulo es presentar los Controller Services más utilizados en el desarrollo de flujos de datos, proporcionando una visión práctica de su finalidad, funcionamiento y escenarios de uso.

    Al finalizar este capítulo el lector será capaz de:

    • Comprender el papel de los principales Controller Services de Apache NiFi.
    • Identificar qué servicio utilizar según el problema que se desea resolver.
    • Configurar los servicios más habituales utilizados por los Processors.
    • Entender la relación existente entre Readers, Writers y Processors.
    • Diferenciar los distintos tipos de Lookup Services.
    • Diseñar flujos reutilizables mediante servicios compartidos.

    No se pretende realizar un estudio exhaustivo de cada componente, sino ofrecer una guía de referencia que permita reconocer rápidamente cuándo utilizar cada uno de ellos.

    Introducción

    Apache NiFi incorpora más de un centenar de Controller Services que proporcionan funcionalidades reutilizables a los Processors. Gracias a ellos es posible compartir configuraciones comunes, centralizar recursos y evitar la duplicación de información dentro de un flujo.

    En lugar de que cada Processor implemente su propia conexión a una base de datos, su propia configuración SSL o su propio lector de registros, estas tareas se delegan en Controller Services especializados.

    flowchart LR
    subgraph PG["Process Group"]
        P1["ExecuteSQL"]
        P2["PutDatabaseRecord"]
        P3["ConsumeKafka"]
        P4["FetchFile"]
    end

    DBCP["DBCPConnectionPool"]
    SSL["StandardSSLContextService"]
    READER["JsonTreeReader"]
    WRITER["JsonRecordSetWriter"]

    P1 --> DBCP
    P2 --> DBCP
    P2 --> READER
    P2 --> WRITER
    P3 --> SSL

    Cada Controller Service tiene una responsabilidad concreta.

    Controller Service Función principal
    DBCPConnectionPool Compartir conexiones JDBC
    StandardSSLContextService Gestionar conexiones TLS/SSL
    CSVReader Leer registros CSV
    JsonTreeReader Leer documentos JSON
    Record Writers Escribir registros en distintos formatos
    Lookup Services Consultar información externa para enriquecer datos

    Todos ellos comparten una característica común: no procesan FlowFiles directamente. Su misión consiste en proporcionar servicios reutilizables a otros componentes del flujo.

    Esta separación de responsabilidades aporta importantes ventajas:

    • Mayor reutilización.
    • Configuración centralizada.
    • Mantenimiento más sencillo.
    • Mejor seguridad.
    • Flujos más limpios y fáciles de comprender.
    • Menor duplicidad de configuraciones.

    En los siguientes apartados se estudiarán los Controller Services más utilizados en la mayoría de proyectos desarrollados con Apache NiFi.

    1. DBCPConnectionPool

    ¿Qué es?

    DBCPConnectionPool es el Controller Service encargado de administrar un pool de conexiones JDBC para que varios Processors puedan acceder a una base de datos sin crear una nueva conexión en cada operación.

    Su uso mejora el rendimiento y reduce el consumo de recursos.

    flowchart LR
    P1["ExecuteSQL"] --> DBCP["DBCPConnectionPool"]
    P2["PutDatabaseRecord"] --> DBCP
    DBCP --> DB["Base de datos"]

    ¿Cuándo utilizarlo?

    Debe utilizarse siempre que un Processor necesite acceder a una base de datos relacional, por ejemplo:

    • PostgreSQL
    • MariaDB
    • MySQL
    • Oracle
    • SQL Server

    Algunos Processors que lo utilizan son:

    • ExecuteSQL
    • ExecuteSQLRecord
    • PutDatabaseRecord
    • PutSQL
    • QueryDatabaseTable

    Propiedades principales

    Propiedad Descripción
    Database Connection URL URL JDBC de la base de datos
    Database Driver Class Name Clase del driver JDBC
    Database Driver Locations Ubicación del driver
    Database User Usuario
    Password Contraseña
    Max Total Connections Máximo de conexiones del pool

    Ejemplo

    Un Processor ExecuteSQL puede utilizar un único DBCPConnectionPool compartido con otros Processors.

    flowchart LR
    SQL["ExecuteSQL"]
    PUT["PutDatabaseRecord"]

    DBCP["DBCPConnectionPool"]

    DB["PostgreSQL"]

    SQL --> DBCP
    PUT --> DBCP
    DBCP --> DB

    De esta forma se centraliza la configuración y se evita duplicar conexiones.

    Buenas prácticas

    • Compartir un mismo pool cuando varios Processors acceden a la misma base de datos.
    • Utilizar Parameter Contexts para las credenciales.
    • Configurar un número máximo de conexiones adecuado.
    • Evitar utilizar cuentas con permisos de administrador.
    • Asignar nombres descriptivos al servicio, por ejemplo:
    DBCP-POSTGRESQL-PRODUCCION

    DBCPConnectionPool es, probablemente, el Controller Service más utilizado en Apache NiFi, ya que sirve de base para la mayoría de integraciones con bases de datos.

    2. StandardSSLContextService

    ¿Qué es?

    StandardSSLContextService es el Controller Service encargado de gestionar las conexiones seguras mediante SSL/TLS. Permite que los Processors se comuniquen de forma cifrada con servidores externos, garantizando la confidencialidad e integridad de la información transmitida.

    Muchos Processors que trabajan con HTTPS, FTPS, Kafka, MQTT o servicios REST requieren este Controller Service.

    flowchart LR
    P["Processor"]
    SSL["StandardSSLContextService"]
    SERVER["Servidor seguro<br/>HTTPS / TLS"]

    P --> SSL
    SSL --> SERVER

    ¿Cuándo utilizarlo?

    Se utiliza cuando un Processor necesita establecer una conexión cifrada, por ejemplo con:

    • APIs REST mediante HTTPS.
    • Servidores FTP seguros (FTPS).
    • Brokers Kafka.
    • Servidores MQTT.
    • Otros servicios que utilicen TLS/SSL.

    Algunos Processors compatibles son:

    • InvokeHTTP
    • PublishKafka
    • ConsumeKafka
    • ListenHTTP

    Propiedades principales

    Propiedad Descripción
    Keystore Filename Ruta del almacén de certificados del cliente
    Keystore Password Contraseña del Keystore
    Truststore Filename Ruta del almacén de certificados de confianza
    Truststore Password Contraseña del Truststore
    TLS Protocol Versión del protocolo TLS

    Ejemplo

    Un único StandardSSLContextService puede compartirse entre varios Processors que necesiten conexiones seguras.

    flowchart LR
    HTTP["InvokeHTTP"]
    KAFKA["PublishKafka"]

    SSL["StandardSSLContextService"]

    API["API HTTPS"]
    BROKER["Kafka"]

    HTTP --> SSL
    KAFKA --> SSL

    SSL --> API
    SSL --> BROKER

    Buenas prácticas

    • Utilizar siempre TLS 1.2 o superior.
    • Proteger los archivos Keystore y Truststore.
    • Parametrizar las contraseñas mediante Parameter Contexts.
    • Compartir el mismo servicio cuando varios Processors utilicen la misma configuración SSL.
    • Renovar los certificados antes de su fecha de expiración.

    StandardSSLContextService centraliza toda la configuración relacionada con certificados digitales, facilitando la administración y aumentando la seguridad de los flujos de datos.

    3. CSVReader

    ¿Qué es?

    CSVReader es un Controller Service que permite leer archivos CSV y convertir cada fila en un registro (Record) que puede ser procesado por los Processors de Apache NiFi.

    Gracias a este servicio, NiFi interpreta automáticamente las columnas del fichero y las pone a disposición del flujo de datos.

    flowchart LR
    CSV["Archivo CSV"]
    READER["CSVReader"]
    RECORDS["Records"]

    CSV --> READER
    READER --> RECORDS

    ¿Cuándo utilizarlo?

    Se utiliza cuando se trabaja con archivos CSV y Processors basados en Records, como por ejemplo:

    • ConvertRecord
    • QueryRecord
    • UpdateRecord
    • PutDatabaseRecord
    • PartitionRecord

    Propiedades principales

    Propiedad Descripción
    CSV Header Line Indica si la primera fila contiene los nombres de las columnas
    Value Separator Separador de campos (, ; \t, etc.)
    Quote Character Carácter utilizado para delimitar textos
    Schema Access Strategy Estrategia para obtener el esquema de los datos

    Ejemplo

    Supongamos el siguiente archivo:

    id,nombre,ciudad
1,Ana,Valencia
2,Carlos,Madrid

    Tras pasar por CSVReader, NiFi obtiene dos registros estructurados:

    flowchart LR
    CSV["clientes.csv"]
    READER["CSVReader"]
    RECORD1["Registro 1"]
    RECORD2["Registro 2"]

    CSV --> READER
    READER --> RECORD1
    READER --> RECORD2

    Estos registros pueden enviarse posteriormente a una base de datos, convertirse a JSON o transformarse mediante otros Processors.

    Buenas prácticas

    • Incluir siempre una fila de cabecera cuando sea posible.
    • Utilizar el separador correcto (, o ;).
    • Definir un esquema cuando los datos sean conocidos.
    • Utilizar CSVReader junto con un Record Writer para transformar fácilmente entre formatos.

    CSVReader es uno de los Readers más utilizados para integrar datos procedentes de hojas de cálculo, exportaciones de aplicaciones o sistemas heredados.

    4. JsonTreeReader

    ¿Qué es?

    JsonTreeReader es un Controller Service que permite leer documentos JSON y convertirlos en Records que pueden ser procesados por los Processors de Apache NiFi.

    Es uno de los Readers más utilizados, ya que JSON es uno de los formatos de intercambio de datos más habituales en APIs y aplicaciones modernas.

    flowchart LR
    JSON["Documento JSON"]
    READER["JsonTreeReader"]
    RECORDS["Records"]

    JSON --> READER
    READER --> RECORDS

    ¿Cuándo utilizarlo?

    Se utiliza cuando el flujo recibe información en formato JSON y se desea trabajar con Processors basados en Records, por ejemplo:

    • ConvertRecord
    • QueryRecord
    • UpdateRecord
    • PutDatabaseRecord
    • SplitRecord

    Propiedades principales

    Propiedad Descripción
    Schema Access Strategy Estrategia para obtener el esquema de los datos
    Date Format Formato de las fechas
    Time Format Formato de las horas
    Timestamp Format Formato de fecha y hora

    Ejemplo

    Documento JSON de entrada:

    ```json id="qqrr47" { "id": 1, "nombre": "Ana", "ciudad": "Valencia" } 

    Tras pasar por `JsonTreeReader`, NiFi interpreta el documento como un registro estructurado.

```mermaid
flowchart LR
    JSON["JSON"]
    READER["JsonTreeReader"]
    RECORD["Record"]

    JSON --> READER
    READER --> RECORD

    Este registro puede transformarse, consultarse o almacenarse en una base de datos mediante otros Processors.

    Buenas prácticas

    • Utilizar una estructura JSON consistente en todos los documentos.
    • Definir un esquema cuando sea posible para mejorar la validación.
    • Utilizar JsonTreeReader junto con un Record Writer para convertir fácilmente entre formatos.
    • Verificar el formato de fechas y marcas temporales cuando existan campos de tipo fecha.

    JsonTreeReader es el Reader recomendado para la mayoría de integraciones con APIs REST, aplicaciones web y servicios que intercambian información en formato JSON.

    5. Record Writers

    ¿Qué son?

    Los Record Writers son Controller Services encargados de escribir Records en un formato determinado. Trabajan junto con los Record Readers, permitiendo transformar fácilmente los datos entre distintos formatos.

    Por ejemplo, un flujo puede leer un archivo CSV mediante CSVReader y generar un documento JSON utilizando JsonRecordSetWriter.

    flowchart LR
    CSV["Archivo CSV"]
    READER["CSVReader"]
    RECORD["Records"]
    WRITER["JsonRecordSetWriter"]
    JSON["Documento JSON"]

    CSV --> READER
    READER --> RECORD
    RECORD --> WRITER
    WRITER --> JSON

    Writers más utilizados

    Writer Formato de salida
    JsonRecordSetWriter JSON
    CSVRecordSetWriter CSV
    AvroRecordSetWriter Avro
    FreeFormTextRecordSetWriter Texto plano

    ¿Cuándo utilizar cada uno?

    JsonRecordSetWriter

    Genera documentos JSON. Es el Writer más utilizado cuando los datos se envían a APIs REST o aplicaciones web.

    CSVRecordSetWriter

    Genera archivos CSV, muy útiles para exportaciones o intercambio de datos con hojas de cálculo.

    AvroRecordSetWriter

    Escribe los datos en formato Apache Avro, optimizado para almacenamiento y procesamiento de grandes volúmenes de información.

    FreeFormTextRecordSetWriter

    Permite generar texto plano personalizado mediante plantillas.

    Ejemplo

    El siguiente flujo convierte un archivo CSV en un documento JSON.

    flowchart LR
    FILE["clientes.csv"]
    CSVR["CSVReader"]
    CONVERT["ConvertRecord"]
    JSONW["JsonRecordSetWriter"]
    OUTPUT["clientes.json"]

    FILE --> CSVR
    CSVR --> CONVERT
    CONVERT --> JSONW
    JSONW --> OUTPUT

    Buenas prácticas

    • Elegir el Writer según el formato que necesite el sistema de destino.
    • Utilizar el mismo esquema en el Reader y el Writer para evitar incompatibilidades.
    • Configurar correctamente el formato de fechas y números.
    • Compartir el mismo Writer entre varios Processors cuando la salida tenga el mismo formato.

    Los Record Writers, junto con los Record Readers, constituyen la base del procesamiento de datos estructurados en Apache NiFi y permiten transformar información entre distintos formatos de manera sencilla y reutilizable.

    6. Lookup Services

    ¿Qué son?

    Los Lookup Services son Controller Services que permiten consultar información externa para enriquecer los datos que circulan por un flujo.

    En lugar de almacenar toda la información en el propio FlowFile, un Processor puede realizar una consulta a un Lookup Service para obtener valores adicionales, como códigos, descripciones o datos de referencia.

    flowchart LR
    FF["FlowFile"]
    PROC["LookupRecord"]
    LOOKUP["Lookup Service"]
    DATA["Origen de datos"]

    FF --> PROC
    PROC --> LOOKUP
    LOOKUP --> DATA
    LOOKUP --> PROC

    ¿Cuándo utilizarlos?

    Son útiles cuando es necesario:

    • Completar información de un registro.
    • Traducir códigos a descripciones.
    • Consultar tablas de referencia.
    • Evitar duplicar datos en el flujo.
    • Centralizar información compartida.

    Lookup Services más utilizados

    Lookup Service Función
    SimpleKeyValueLookupService Consulta pares clave-valor definidos manualmente.
    CSVRecordLookupService Busca información en un archivo CSV.
    DatabaseRecordLookupService Consulta datos en una base de datos mediante JDBC.

    Ejemplo

    Supongamos un FlowFile que contiene únicamente el código de una provincia:

    {
  "codigo": "46"
}

    El Lookup Service consulta una tabla de referencia y devuelve el nombre correspondiente.

    flowchart LR
    INPUT["Código 46"]
    LOOKUP["DatabaseRecordLookupService"]
    OUTPUT["Valencia"]

    INPUT --> LOOKUP
    LOOKUP --> OUTPUT

    El resultado podría ser:

    {
  "codigo": "46",
  "provincia": "Valencia"
}

    Buenas prácticas

    • Utilizar Lookups para información de referencia que cambia con poca frecuencia.
    • Centralizar los datos de consulta para evitar duplicidades.
    • Elegir el tipo de Lookup según el origen de la información (CSV, base de datos, etc.).
    • Compartir el mismo Lookup Service entre varios Processors cuando utilicen la misma fuente de datos.

    Los Lookup Services facilitan el enriquecimiento de los datos durante su procesamiento, permitiendo construir flujos más flexibles y reutilizables sin necesidad de incorporar toda la información dentro de los FlowFiles.

    Resumen

    En este capítulo se han presentado los Controller Services más utilizados en Apache NiFi. Estos componentes permiten centralizar configuraciones y compartir recursos entre distintos Processors, facilitando el desarrollo de flujos más reutilizables, seguros y fáciles de mantener.

    Cada Controller Service está especializado en una tarea concreta:

    Controller Service Función principal
    DBCPConnectionPool Gestiona conexiones JDBC compartidas.
    StandardSSLContextService Configura conexiones seguras mediante SSL/TLS.
    CSVReader Convierte archivos CSV en Records.
    JsonTreeReader Convierte documentos JSON en Records.
    Record Writers Generan la salida en distintos formatos (JSON, CSV, Avro, etc.).
    Lookup Services Enriquecen los datos mediante consultas externas.

    Su funcionamiento puede resumirse de la siguiente forma:

    flowchart LR
    INPUT["Datos de entrada"]
    READER["Record Reader"]
    PROCESSOR["Processor"]
    LOOKUP["Lookup Service"]
    WRITER["Record Writer"]
    OUTPUT["Datos de salida"]

    INPUT --> READER
    READER --> PROCESSOR
    LOOKUP --> PROCESSOR
    PROCESSOR --> WRITER
    WRITER --> OUTPUT

    En la práctica, estos servicios suelen combinarse dentro del mismo flujo. Por ejemplo, un Processor puede utilizar simultáneamente un DBCPConnectionPool para acceder a una base de datos, un JsonTreeReader para interpretar un documento JSON y un JsonRecordSetWriter para generar la salida.

    flowchart LR
    JSON["JSON"]
    JR["JsonTreeReader"]
    P["PutDatabaseRecord"]
    DBCP["DBCPConnectionPool"]
    DB["PostgreSQL"]

    JSON --> JR
    JR --> P
    P --> DBCP
    DBCP --> DB

    Ideas clave

    • Los Controller Services proporcionan funcionalidades compartidas a los Processors.
    • Favorecen la reutilización y evitan duplicar configuraciones.
    • Los Readers leen datos estructurados y los convierten en Records.
    • Los Writers generan la salida en distintos formatos.
    • DBCPConnectionPool centraliza las conexiones a bases de datos.
    • StandardSSLContextService gestiona las comunicaciones seguras.
    • Los Lookup Services permiten enriquecer los datos durante el procesamiento.

    En el siguiente capítulo se estudiarán diferentes arquitecturas de diseño para organizar Controller Services en Apache NiFi, analizando buenas prácticas de reutilización, modularidad y escalabilidad en entornos de producción.
