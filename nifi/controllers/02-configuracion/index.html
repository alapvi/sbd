    Configuración de Controller Services

    Introducción

    Después de estudiar qué son los Controller Services, cómo funciona su ciclo de vida y de qué manera se aplican el ámbito y la herencia, el siguiente paso consiste en aprender a configurarlos desde la interfaz de Apache NiFi.

    La configuración de un Controller Service suele seguir siempre el mismo proceso:

    1. Acceder al Process Group adecuado.
    2. Abrir la sección de Controller Services.
    3. Añadir una nueva instancia.
    4. Seleccionar el tipo de servicio.
    5. Configurar sus propiedades.
    6. Validar la configuración.
    7. Habilitar el servicio.
    8. Asociarlo a uno o varios Processors.
    flowchart LR
    SCOPE["Elegir ámbito"]
    CREATE["Crear servicio"]
    PROPS["Configurar propiedades"]
    VALIDATE["Validar"]
    ENABLE["Habilitar"]
    USE["Asignar a Processors"]

    SCOPE --> CREATE
    CREATE --> PROPS
    PROPS --> VALIDATE
    VALIDATE --> ENABLE
    ENABLE --> USE

    Aunque el procedimiento es sencillo, existen varias decisiones importantes que deben tomarse antes de crear el servicio. Entre ellas destacan su ubicación en la jerarquía, el tipo de Controller Service que se necesita y la forma en que se gestionarán las credenciales y los parámetros de entorno.

    Creación

    Antes de crear el servicio

    Antes de añadir un Controller Service conviene identificar con claridad qué problema debe resolver.

    No todos los recursos compartidos necesitan la misma implementación. Por ejemplo:

    Necesidad Controller Service habitual
    Conexión con una base de datos DBCPConnectionPool
    Interpretar registros JSON JsonTreeReader
    Generar registros JSON JsonRecordSetWriter
    Interpretar archivos CSV CSVReader
    Proporcionar contexto TLS StandardSSLContextService
    Consultar valores por clave LookupService
    Gestionar esquemas SchemaRegistry
    Compartir una caché distribuida DistributedMapCacheClientService

    Antes de crear el componente, es recomendable responder a las siguientes preguntas:

    • ¿Qué Processors van a utilizarlo?
    • ¿En qué Process Groups se encuentran?
    • ¿Existe ya un servicio equivalente?
    • ¿La configuración será común para varios flujos?
    • ¿Contendrá credenciales o información sensible?
    • ¿Dependerá de otro Controller Service?
    • ¿Debe variar entre desarrollo, preproducción y producción?

    Estas cuestiones permiten decidir el tipo de servicio, su ámbito y la estrategia de parametrización.

    Elegir el ámbito adecuado

    El Controller Service debe crearse en el Process Group que actúe como ancestro común más bajo de todos sus consumidores.

    Supongamos la siguiente jerarquía:

    flowchart TD
    ROOT["Plataforma NiFi"]
    FIN["Finanzas"]
    HR["Recursos Humanos"]
    BILL["Facturación"]
    ACC["Contabilidad"]

    ROOT --> FIN
    ROOT --> HR
    FIN --> BILL
    FIN --> ACC

    Si tanto Facturación como Contabilidad necesitan utilizar la misma conexión con PostgreSQL, el Controller Service debería crearse dentro de Finanzas.

    No sería recomendable crearlo:

    • En Facturación, porque Contabilidad no podría verlo.
    • En el grupo raíz, porque tendría un ámbito mayor del necesario.
    • Duplicado en ambos grupos, porque aumentaría el mantenimiento y el consumo de recursos.

    La decisión correcta sería:

    flowchart TD
    ROOT["Plataforma NiFi"]
    FIN["Finanzas<br/>DBCP-PostgreSQL-Finanzas"]
    BILL["Facturación"]
    ACC["Contabilidad"]

    ROOT --> FIN
    FIN --> BILL
    FIN --> ACC

    FIN -. "Servicio heredado" .-> BILL
    FIN -. "Servicio heredado" .-> ACC

    Acceder a la configuración del Process Group

    Para crear un Controller Service, el primer paso consiste en acceder al Process Group en el que se desea definir.

    El procedimiento habitual es:

    1. Entrar en el Process Group correspondiente.
    2. Abrir el menú contextual del grupo.
    3. Seleccionar la opción de configuración.
    4. Acceder a la pestaña Controller Services.

    Dependiendo de la versión de NiFi y del diseño de la interfaz, también puede accederse mediante el panel de operación situado en la parte superior de la aplicación.

    Dentro de la sección aparecerá una tabla con los servicios definidos en ese ámbito.

    Normalmente se muestran columnas similares a las siguientes:

    Columna Descripción
    Name Nombre asignado al servicio
    Type Implementación seleccionada
    Bundle Extensión o NAR que proporciona el servicio
    State Estado actual
    Referencing Components Componentes que dependen del servicio
    Comments Descripción o documentación adicional

    Añadir un nuevo Controller Service

    Para crear un servicio, se utiliza el botón de añadir Controller Service.

    Apache NiFi mostrará una ventana de selección con los tipos disponibles.

    Cada entrada incluye normalmente:

    • Nombre del componente.
    • Descripción.
    • Bundle.
    • Grupo del bundle.
    • Versión.
    • Etiquetas o información adicional.
    flowchart LR
    ADD["Add Controller Service"]
    SEARCH["Buscar tipo"]
    SELECT["Seleccionar implementación"]
    CREATE["Crear instancia"]

    ADD --> SEARCH
    SEARCH --> SELECT
    SELECT --> CREATE

    La cantidad de servicios disponibles depende de:

    • La versión de Apache NiFi.
    • Los NAR instalados.
    • Las extensiones adicionales.
    • Los componentes personalizados desplegados.
    • Los servicios incluidos por cada proveedor.

    Buscar el tipo de servicio

    La ventana de selección dispone de un buscador que permite filtrar los componentes.

    Por ejemplo, para crear una conexión JDBC puede buscarse:

    DBCP

    La interfaz mostrará servicios compatibles, como:

    DBCPConnectionPool

    Para un lector JSON puede utilizarse:

    JsonTreeReader

    Y para un contexto TLS:

    SSLContextService

    Es importante leer la descripción del componente antes de seleccionarlo. Algunos servicios pueden tener nombres similares, pero comportamientos o dependencias diferentes.

    Tipo, bundle y versión

    Cada Controller Service pertenece a un bundle.

    Un bundle es una unidad de distribución de extensiones de Apache NiFi, normalmente empaquetada como un archivo NAR.

    Por ejemplo, la interfaz puede mostrar información similar a:

    Type: DBCPConnectionPool
Bundle: org.apache.nifi:nifi-dbcp-service-nar
Version: 2.x

    Estos datos permiten identificar la implementación concreta utilizada por el flujo.

    Son especialmente importantes cuando:

    • Se migra un flujo entre entornos.
    • Se actualiza Apache NiFi.
    • Se utilizan componentes personalizados.
    • Existen varias versiones de una misma extensión.
    • Se importa un Process Group.

    Si el bundle no existe en el entorno de destino, el servicio aparecerá como componente ausente o incompatible.

    Crear la instancia

    Una vez seleccionado el tipo, Apache NiFi crea una nueva instancia del Controller Service.

    En este momento el servicio todavía no está configurado ni habilitado.

    Su estado inicial suele ser:

    Disabled

    o:

    Invalid

    Que aparezca como Invalid no significa necesariamente que exista un fallo grave. Normalmente indica que faltan propiedades obligatorias.

    Por ejemplo, un DBCPConnectionPool será inválido mientras no se hayan definido:

    • La URL JDBC.
    • La clase del driver.
    • La ubicación del driver, cuando sea necesaria.
    • Las credenciales, si la base de datos las requiere.

    Nombre del servicio

    Todos los Controller Services deberían recibir un nombre claro y descriptivo.

    No es recomendable mantener el nombre genérico generado por defecto.

    Por ejemplo:

    DBCPConnectionPool

    no permite saber:

    • A qué base de datos se conecta.
    • Qué entorno utiliza.
    • Qué aplicación lo consume.
    • Qué finalidad tiene.

    En cambio, un nombre como:

    DBCP-PostgreSQL-Clientes-PRO

    aporta información inmediata.

    Una convención útil puede ser:

    TIPO-TECNOLOGIA-FINALIDAD-ENTORNO

    Ejemplos:

    DBCP-POSTGRESQL-CLIENTES-PRO
DBCP-MARIADB-INVENTARIO-DEV
SSL-API-PAGOS-PRE
CSVREADER-PROVEEDOR-A
JSONWRITER-KAFKA-EVENTOS

    La convención debe ser:

    • Clara.
    • Homogénea.
    • Fácil de buscar.
    • Comprensible para todo el equipo.
    • Independiente del nombre interno del Processor.

    Descripción y comentarios

    Además del nombre, conviene utilizar el campo de comentarios o descripción.

    Una documentación útil puede incluir:

    • Sistema al que se conecta.
    • Finalidad.
    • Equipo responsable.
    • Entorno.
    • Process Groups consumidores.
    • Dependencias.
    • Consideraciones de seguridad.
    • Procedimiento de renovación de credenciales.

    Ejemplo:

    Pool JDBC compartido para los flujos de facturación y contabilidad.
Conecta con PostgreSQL de producción.
Las credenciales se obtienen mediante el Parameter Context FINANZAS-PRO.

    Esta documentación resulta muy valiosa cuando la plataforma contiene decenas o cientos de servicios.

    Creación desde un Processor

    Apache NiFi también permite crear determinados Controller Services directamente desde la propiedad de un Processor.

    Supongamos que se configura un Processor ExecuteSQL.

    En la propiedad destinada al servicio de conexión aparecerá una lista con los Controller Services compatibles.

    Si no existe ninguno, la interfaz puede ofrecer la posibilidad de crear uno nuevo.

    flowchart LR
    PROC["Configurar Processor"]
    PROPERTY["Propiedad Controller Service"]
    EXISTING{"¿Existe servicio compatible?"}
    SELECT["Seleccionar servicio"]
    CREATE["Crear nuevo servicio"]

    PROC --> PROPERTY
    PROPERTY --> EXISTING
    EXISTING -->|Sí| SELECT
    EXISTING -->|No| CREATE

    Este método resulta cómodo, pero debe utilizarse con precaución.

    Antes de crear el servicio desde el Processor conviene comprobar:

    • En qué ámbito se va a crear.
    • Si otros Processors también lo necesitarán.
    • Si ya existe un servicio equivalente.
    • Si debería situarse en un Process Group superior.

    Crear servicios rápidamente desde los Processors puede provocar duplicaciones si no se planifica correctamente.

    Referencias iniciales

    Tras crear el servicio, todavía no tendrá componentes consumidores.

    Una vez seleccionado desde un Processor, Apache NiFi registrará automáticamente la referencia.

    flowchart LR
    PROC["ExecuteSQL"]
    PROP["Database Connection Pooling Service"]
    SERVICE["DBCP-PostgreSQL"]

    PROC --> PROP
    PROP --> SERVICE

    A partir de ese momento, la sección de componentes referenciados permitirá consultar la dependencia.

    Creación de servicios dependientes

    Algunos Controller Services dependen de otros.

    Por ejemplo, un cliente puede requerir un SSLContextService.

    flowchart TD
    SSL["StandardSSLContextService"]
    CLIENT["Cliente HTTPS"]
    PROC["Processor"]

    SSL --> CLIENT
    CLIENT --> PROC

    En estos casos se recomienda crear primero los servicios base.

    El orden adecuado sería:

    1. Crear el servicio TLS.
    2. Configurarlo.
    3. Validarlo.
    4. Habilitarlo.
    5. Crear el servicio cliente.
    6. Asociar el servicio TLS.
    7. Habilitar el servicio cliente.
    8. Configurar el Processor.

    De este modo se evita que los componentes dependientes permanezcan inválidos por falta de recursos.

    Creación en clúster

    En una instalación NiFi en clúster, los Controller Services forman parte de la definición del flujo compartido.

    Esto significa que la configuración lógica se distribuye a todos los nodos.

    flowchart TD
    FLOW["Definición del flujo"]
    CS["Controller Service"]
    N1["Nodo 1"]
    N2["Nodo 2"]
    N3["Nodo 3"]

    FLOW --> CS
    CS --> N1
    CS --> N2
    CS --> N3

    Sin embargo, algunos recursos referenciados deben existir localmente en todos los nodos.

    Ejemplos:

    • Drivers JDBC.
    • Keystores.
    • Truststores.
    • Archivos de configuración.
    • Rutas locales.
    • Bibliotecas externas.

    Si un driver JDBC está configurado mediante una ruta como:

    /opt/nifi/drivers/postgresql.jar

    el archivo debe estar disponible en esa ubicación en todos los nodos del clúster.

    De lo contrario, el servicio puede habilitarse correctamente en algunos nodos y fallar en otros.

    Creación en Docker

    En entornos Docker debe prestarse especial atención a las rutas.

    Una ruta configurada dentro de NiFi se interpreta desde el sistema de archivos del contenedor, no desde el host.

    Por ejemplo:

    /opt/nifi/drivers/postgresql.jar

    debe existir dentro del contenedor.

    Puede proporcionarse mediante un bind mount:

    services:
  nifi:
    image: apache/nifi:2.10.0
    volumes:
      - ./drivers:/opt/nifi/drivers

    De este modo, un archivo situado en el host:

    ./drivers/postgresql.jar

    estará disponible dentro del contenedor como:

    /opt/nifi/drivers/postgresql.jar

    flowchart LR
    HOST["Host<br/>./drivers/postgresql.jar"]
    MOUNT["Bind mount"]
    CONTAINER["Contenedor NiFi<br/>/opt/nifi/drivers/postgresql.jar"]
    SERVICE["DBCPConnectionPool"]

    HOST --> MOUNT
    MOUNT --> CONTAINER
    CONTAINER --> SERVICE

    Este mismo principio se aplica a:

    • Certificados.
    • Drivers.
    • Archivos de configuración.
    • Esquemas.
    • Recursos auxiliares.

    Creación mediante definiciones de flujo

    Los Controller Services también pueden incorporarse mediante:

    • Importación de Process Groups.
    • Definiciones de flujo JSON.
    • NiFi Registry.
    • Versionado de flujos.
    • Despliegues automatizados.

    Cuando se importa un flujo, Apache NiFi intenta recrear sus Controller Services y dependencias.

    Sin embargo, es posible que sea necesario revisar:

    • Credenciales.
    • Parameter Contexts.
    • Rutas locales.
    • Drivers.
    • Certificados.
    • Identificadores sensibles.
    • Servicios externos.

    La estructura puede importarse correctamente, pero la configuración específica del entorno debe adaptarse.

    Errores frecuentes durante la creación

    Crear el servicio en el ámbito incorrecto

    Si se crea demasiado abajo, otros Process Groups no podrán utilizarlo.

    Si se crea demasiado arriba, quedará expuesto a más componentes de los necesarios.

    Duplicar servicios existentes

    Antes de crear uno nuevo, debe revisarse la lista de servicios disponibles y heredados.

    Mantener el nombre genérico

    Nombres como DBCPConnectionPool o JsonTreeReader dificultan la administración en plataformas grandes.

    Ignorar el bundle

    Un flujo puede depender de una extensión que no exista en otro entorno.

    Utilizar rutas del host en Docker

    NiFi solo puede acceder a las rutas disponibles dentro del contenedor.

    No considerar todos los nodos del clúster

    Los archivos locales necesarios deben existir en todos los nodos.

    Introducir credenciales directamente

    Las contraseñas deberían gestionarse mediante propiedades sensibles y Parameter Contexts, evitando configuraciones dispersas.

    Buenas prácticas

    • Definir primero el ámbito.
    • Buscar servicios existentes antes de crear uno nuevo.
    • Aplicar una convención de nombres.
    • Añadir una descripción funcional.
    • Crear primero los servicios base.
    • Usar Parameter Contexts para valores variables.
    • Mantener credenciales fuera de configuraciones visibles.
    • Verificar rutas en todos los nodos.
    • Utilizar bind mounts en Docker.
    • Documentar dependencias externas.
    • Revisar el bundle y la versión.
    • Evitar crear servicios de forma improvisada desde los Processors.

    Lista de comprobación

    Antes de dar por finalizada la creación del servicio, conviene verificar:

    • [ ] El tipo de servicio es el adecuado.
    • [ ] Se ha creado en el ámbito correcto.
    • [ ] No existe otro servicio equivalente.
    • [ ] Tiene un nombre descriptivo.
    • [ ] Dispone de comentarios o documentación.
    • [ ] Sus dependencias están identificadas.
    • [ ] Las rutas existen dentro de NiFi.
    • [ ] Los recursos locales están presentes en todos los nodos.
    • [ ] Las credenciales se gestionan de forma segura.
    • [ ] El bundle está disponible en todos los entornos.

    Ideas clave

    La creación de un Controller Service no consiste únicamente en pulsar el botón Add.

    También implica tomar decisiones sobre:

    • Tipo.
    • Ámbito.
    • Reutilización.
    • Seguridad.
    • Dependencias.
    • Portabilidad.
    • Mantenimiento.
    • Entorno de ejecución.

    Un servicio bien ubicado y correctamente documentado puede reutilizarse de forma segura durante años. Por el contrario, una creación improvisada puede generar duplicación, dependencias ocultas y problemas durante la migración.

    Propiedades

    Una vez creado un Controller Service, el siguiente paso consiste en configurar sus propiedades. Estas propiedades determinan el comportamiento del servicio y permiten adaptarlo al recurso que debe proporcionar.

    Dependiendo del tipo de Controller Service, el número de propiedades puede variar considerablemente. Algunos servicios únicamente requieren dos o tres parámetros, mientras que otros incorporan decenas de opciones de configuración.

    Por ejemplo:

    • Un JsonTreeReader necesita conocer cómo interpretar documentos JSON.
    • Un StandardSSLContextService requiere certificados, almacenes de claves y algoritmos criptográficos.
    • Un DBCPConnectionPool necesita la información necesaria para establecer conexiones con una base de datos.

    Aunque las propiedades cambian según el tipo de servicio, Apache NiFi utiliza una filosofía común para todos ellos, lo que facilita enormemente su aprendizaje.

    La ventana de configuración

    Al editar un Controller Service aparece una ventana similar a la de cualquier Processor.

    Generalmente se divide en varias pestañas:

    flowchart LR
    SETTINGS["Settings"]
    PROPERTIES["Properties"]
    COMMENTS["Comments"]

    SETTINGS --> PROPERTIES
    PROPERTIES --> COMMENTS

    La pestaña Properties concentra prácticamente toda la configuración funcional del servicio.

    Cada propiedad dispone normalmente de la siguiente información:

    • Nombre.
    • Valor.
    • Descripción.
    • Si es obligatoria.
    • Si admite Expression Language.
    • Si es sensible.
    • Si tiene un valor por defecto.
    • Restricciones de validación.

    Tipos de propiedades

    Apache NiFi utiliza diferentes tipos de propiedades dependiendo del dato que deba almacenarse.

    Las más habituales son:

    Tipo Ejemplo
    Texto Nombre de un esquema
    Número Tamaño del pool
    Booleano Activado / Desactivado
    Enumeración Estrategia de lectura
    Ruta Ubicación de un fichero
    URL Dirección de un servidor
    Contraseña Password JDBC
    Referencia Otro Controller Service

    Cada tipo incorpora su propio mecanismo de validación.

    Por ejemplo:

    • Un número debe contener un valor numérico válido.
    • Una URL debe respetar un formato correcto.
    • Una referencia debe apuntar a un Controller Service compatible.
    • Una contraseña permanece oculta en la interfaz.

    Propiedades obligatorias

    Muchas propiedades son obligatorias.

    Mientras una propiedad requerida permanezca vacía, el Controller Service será considerado Invalid.

    Por ejemplo, un DBCPConnectionPool no podrá habilitarse si faltan:

    • JDBC URL
    • Database Driver Class Name

    La interfaz muestra estas propiedades mediante indicadores visuales.

    JDBC URL *
Driver Class Name *

    El asterisco indica que el valor es obligatorio.

    Valores por defecto

    Muchos Controller Services incluyen valores predeterminados.

    Por ejemplo:

    Propiedad Valor por defecto
    Max Wait Time 500 ms
    Validation Timeout 1 min
    Max Total Connections 8

    Los valores por defecto permiten comenzar rápidamente, aunque en entornos de producción conviene revisarlos cuidadosamente.

    No siempre representan la configuración más adecuada para todos los escenarios.

    Propiedades sensibles

    Determinadas propiedades contienen información confidencial.

    Entre ellas destacan:

    • Contraseñas.
    • Tokens.
    • Claves privadas.
    • Secretos de autenticación.
    • Passwords de certificados.

    Apache NiFi marca estas propiedades como Sensitive.

    La interfaz oculta automáticamente su contenido.

    **************

    Aunque el usuario vuelva a abrir el Controller Service, el valor no será mostrado.

    Este comportamiento evita la exposición accidental de credenciales.

    Uso de Parameter Contexts

    En lugar de escribir directamente una contraseña, es recomendable utilizar un Parameter Context.

    Por ejemplo:

    En lugar de:

    Password = MiPassword2025

    utilizaremos:

    #{db.password}

    Del mismo modo:

    #{db.user}

#{db.host}

#{db.port}

#{db.name}

    Este enfoque aporta numerosas ventajas:

    • Separación entre configuración y lógica.
    • Mayor seguridad.
    • Facilidad para cambiar entre entornos.
    • Menor duplicación.
    • Despliegues más sencillos.

    Expression Language

    No todas las propiedades admiten Expression Language.

    Cuando una propiedad lo permite, Apache NiFi lo indica claramente en su descripción.

    Por ejemplo:

    Supports Expression Language: Yes

    o

    Supports Expression Language: No

    En los Controller Services es mucho más habitual utilizar Parameter Contexts que Expression Language.

    La razón es sencilla.

    Los Controller Services se inicializan antes de que existan FlowFiles.

    Como consecuencia, muchas variables asociadas al FlowFile no están disponibles durante su configuración.

    Referencias a otros Controller Services

    Una característica muy potente consiste en que un Controller Service puede utilizar otro Controller Service.

    Por ejemplo:

    flowchart LR
    SSL["StandardSSLContextService"]
    CLIENT["Client Service"]
    PROCESSOR["InvokeHTTP"]

    SSL --> CLIENT
    CLIENT --> PROCESSOR

    En este caso:

    • El Processor utiliza un Client Service.
    • El Client Service utiliza un SSLContextService.

    Apache NiFi gestiona automáticamente estas dependencias.

    Propiedades dinámicas

    Algunos Controller Services permiten crear propiedades dinámicas.

    Estas propiedades no aparecen inicialmente en la configuración y pueden añadirse según las necesidades del usuario.

    Su funcionamiento depende de cada implementación.

    Ejemplos habituales:

    • Cabeceras HTTP.
    • Parámetros personalizados.
    • Opciones específicas del proveedor.
    • Configuraciones avanzadas.

    No todos los servicios admiten propiedades dinámicas.

    Cuando están disponibles, la documentación del componente las describe detalladamente.

    Validación de propiedades

    Cada vez que una propiedad cambia, Apache NiFi ejecuta un proceso de validación.

    Este proceso verifica aspectos como:

    • Tipo correcto.
    • Formato.
    • Restricciones.
    • Dependencias.
    • Compatibilidad.

    Si alguna comprobación falla, el servicio permanecerá inválido.

    flowchart TD
    EDIT["Modificar propiedad"]
    VALIDATE["Validación automática"]
    OK["Configuración válida"]
    ERROR["Configuración inválida"]

    EDIT --> VALIDATE
    VALIDATE --> OK
    VALIDATE --> ERROR

    Esta validación inmediata evita numerosos errores durante la ejecución.

    Dependencias entre propiedades

    En algunos Controller Services determinadas propiedades dependen de otras.

    Por ejemplo:

    SSL Enabled = true

    provocará que aparezcan nuevas propiedades relacionadas con:

    • Keystore
    • Truststore
    • Passwords
    • Protocolos TLS

    Si SSL está desactivado, dichas propiedades pueden permanecer ocultas o dejar de ser obligatorias.

    Este comportamiento simplifica considerablemente la interfaz.

    Buenas prácticas

    Al configurar las propiedades de un Controller Service es recomendable:

    • Utilizar Parameter Contexts.
    • Evitar valores codificados.
    • Revisar siempre los valores por defecto.
    • Leer la documentación de cada propiedad.
    • Utilizar nombres descriptivos.
    • Documentar configuraciones complejas.
    • Mantener la configuración homogénea entre entornos.
    • Revisar periódicamente las propiedades sensibles.

    Errores frecuentes

    Los errores más habituales son:

    • Introducir credenciales directamente.
    • No utilizar parámetros.
    • Ignorar los valores por defecto.
    • Pensar que todas las propiedades admiten Expression Language.
    • Seleccionar un Controller Service incompatible.
    • Modificar propiedades críticas sin conocer su impacto.
    • Configurar rutas inexistentes.
    • No revisar la validación antes de habilitar el servicio.

    Ideas clave

    Las propiedades constituyen el núcleo de configuración de un Controller Service.

    Apache NiFi proporciona un sistema homogéneo de validación, parametrización y gestión de dependencias que facilita la creación de configuraciones reutilizables y seguras.

    Validación

    La validación es el proceso mediante el cual Apache NiFi comprueba que un Controller Service contiene una configuración coherente antes de permitir su habilitación.

    Este mecanismo actúa como una primera barrera frente a errores de configuración. Antes de inicializar conexiones, cargar certificados o crear clientes externos, NiFi revisa las propiedades declaradas por el componente y determina si cumplen las condiciones necesarias.

    Un Controller Service puede haber sido creado correctamente y, aun así, permanecer en estado Invalid. Este estado no indica necesariamente un fallo interno de NiFi. En la mayoría de los casos significa que falta una propiedad obligatoria, existe un valor con un formato incorrecto o alguna dependencia no está disponible.

    La validación permite detectar problemas antes de que el servicio sea utilizado por los Processors.

    flowchart LR
    CREATE["Crear Controller Service"]
    CONFIGURE["Configurar propiedades"]
    VALIDATE["Validación automática"]
    VALID{"¿Configuración válida?"}
    INVALID["Estado Invalid"]
    READY["Estado Disabled y válido"]
    ENABLE["Habilitar servicio"]

    CREATE --> CONFIGURE
    CONFIGURE --> VALIDATE
    VALIDATE --> VALID
    VALID -->|No| INVALID
    INVALID --> CONFIGURE
    VALID -->|Sí| READY

    Qué significa que un servicio sea válido

    Un Controller Service se considera válido cuando todas las propiedades y dependencias que pueden comprobarse antes de su ejecución cumplen los requisitos definidos por su implementación.

    Entre otras condiciones, NiFi puede comprobar que:

    • Las propiedades obligatorias tienen valor.
    • Los números se encuentran dentro del rango permitido.
    • Las URLs tienen un formato aceptable.
    • Los valores pertenecen a una lista de opciones válida.
    • Los Controller Services referenciados son compatibles.
    • Los parámetros utilizados existen.
    • Las expresiones empleadas son sintácticamente correctas.
    • Las dependencias entre propiedades se cumplen.
    • Las rutas y recursos declarados respetan las reglas del componente.

    Sin embargo, una configuración válida no garantiza que el recurso externo esté disponible.

    Por ejemplo, una URL JDBC puede tener un formato correcto y superar la validación, aunque la base de datos se encuentre apagada.

    Por tanto, es importante distinguir entre:

    Tipo de comprobación Ejemplo
    Validación de configuración La URL JDBC tiene un formato aceptado
    Inicialización del servicio El driver JDBC puede cargarse
    Comprobación de conectividad La base de datos acepta conexiones
    Funcionamiento en ejecución Las consultas se realizan correctamente

    La validación reduce errores, pero no sustituye las pruebas de conectividad ni la observación durante la ejecución.

    Estado Invalid

    Cuando la configuración no cumple los requisitos del servicio, Apache NiFi lo marca como Invalid.

    Este estado suele aparecer acompañado de un icono de advertencia o de un mensaje explicativo.

    Al situar el cursor sobre el indicador de validación, NiFi muestra las causas detectadas.

    Ejemplos habituales:

    'Database Connection URL' is invalid because it is required

    'Database Driver Class Name' is invalid because it is required

    'Maximum Pool Size' is invalid because it is not a valid integer

    'SSL Context Service' is invalid because the referenced Controller Service is disabled

    El servicio permanecerá en estado inválido hasta que se corrijan todas las causas.

    stateDiagram-v2
    [*] --> Invalid
    Invalid --> Invalid: Persisten errores
    Invalid --> ValidDisabled: Se corrige la configuración
    ValidDisabled --> Invalid: Se introduce un valor incorrecto
    ValidDisabled --> Enabling: Solicitud de habilitación
    Enabling --> Enabled: Inicialización correcta
    Enabling --> ValidDisabled: Inicialización fallida
    Enabled --> ValidDisabled: Deshabilitación

    Validación automática

    Apache NiFi realiza la validación de manera automática.

    No es necesario ejecutar manualmente una prueba cada vez que se modifica una propiedad. Cuando el usuario guarda la configuración, NiFi vuelve a evaluar el servicio.

    La validación también puede repetirse cuando cambia alguno de los elementos de los que depende el Controller Service.

    Por ejemplo:

    • Se modifica un parámetro.
    • Se elimina un parámetro.
    • Se deshabilita un servicio dependiente.
    • Se cambia un Parameter Context.
    • Se modifica una propiedad relacionada.
    • Se elimina un archivo necesario.
    • Se importa una nueva versión del flujo.

    Esto significa que un servicio anteriormente válido puede pasar a ser inválido si cambia alguna de sus dependencias.

    Tipos de validación

    El proceso de validación puede incluir diferentes niveles de comprobación.

    Propiedades obligatorias

    Es la validación más básica.

    Una propiedad marcada como obligatoria debe contener un valor antes de que el servicio pueda habilitarse.

    Por ejemplo:

    Controller Service Propiedad obligatoria
    DBCPConnectionPool URL JDBC
    DBCPConnectionPool Clase del driver JDBC
    StandardSSLContextService Configuración de keystore o truststore, según el uso
    CSVReader Estrategia de acceso al esquema
    JsonRecordSetWriter Estrategia de escritura del esquema

    Mientras falte una de estas propiedades, el Controller Service será inválido.

    flowchart LR
    REQUIRED["Propiedad obligatoria"]
    VALUE{"¿Tiene valor?"}
    OK["Validación superada"]
    ERROR["Servicio Invalid"]

    REQUIRED --> VALUE
    VALUE -->|Sí| OK
    VALUE -->|No| ERROR

    Tipo de dato

    Cada propiedad puede imponer un tipo de dato determinado.

    NiFi comprueba que el valor proporcionado pueda interpretarse correctamente.

    Tipos habituales:

    • Número entero.
    • Número decimal.
    • Duración.
    • Tamaño de datos.
    • Booleano.
    • URL.
    • Ruta.
    • Expresión regular.
    • Nombre de clase Java.
    • Lista de valores.

    Por ejemplo, una propiedad que representa el máximo número de conexiones no puede contener:

    muchas

    Debe contener un número válido:

    20

    Algunas propiedades de tiempo aceptan valores con unidades:

    500 ms
30 sec
5 min
1 hour

    Del mismo modo, las propiedades de tamaño pueden admitir formatos como:

    1 KB
20 MB
2 GB

    La unidad debe ser una de las reconocidas por la propiedad.

    Rango permitido

    Una propiedad puede aceptar un número y, aun así, ser inválida si se encuentra fuera del rango permitido.

    Por ejemplo:

    Maximum Pool Size = -5

    Aunque -5 es un número entero, no representa un tamaño de pool válido.

    La validación puede imponer condiciones como:

    • Mayor que cero.
    • Mayor o igual que cero.
    • Entre un valor mínimo y máximo.
    • Número positivo.
    • Porcentaje entre 0 y 100.
    flowchart TD
    VALUE["Valor numérico"]
    TYPE{"¿Es un número?"}
    RANGE{"¿Está dentro del rango?"}
    VALID["Válido"]
    INVALID_TYPE["Tipo incorrecto"]
    INVALID_RANGE["Fuera de rango"]

    VALUE --> TYPE
    TYPE -->|No| INVALID_TYPE
    TYPE -->|Sí| RANGE
    RANGE -->|Sí| VALID
    RANGE -->|No| INVALID_RANGE

    Valores permitidos

    Algunas propiedades únicamente admiten una lista cerrada de opciones.

    Por ejemplo:

    • true o false.
    • Una estrategia de acceso al esquema.
    • Un algoritmo de cifrado.
    • Un tipo de autenticación.
    • Una política de validación.
    • Una versión de protocolo.

    En estos casos, la interfaz suele presentar un selector desplegable.

    Esto reduce errores porque impide introducir valores no admitidos.

    Validación de formatos

    Algunas propiedades requieren un formato concreto.

    Ejemplos:

    • URL JDBC.
    • URL HTTP.
    • Nombre de clase Java.
    • Expresión regular.
    • Dirección de servidor.
    • Ruta de recurso.
    • Patrón de fecha.
    • Lista separada por comas.

    Una URL JDBC válida para PostgreSQL puede tener el siguiente formato:

    jdbc:postgresql://postgres:5432/clientes

    En cambio, el siguiente valor podría no ser interpretado como una URL JDBC adecuada:

    postgres:5432/clientes

    Otro ejemplo sería una clase de driver:

    org.postgresql.Driver

    Un error tipográfico en el nombre puede no detectarse completamente hasta la habilitación, cuando NiFi intenta cargar la clase.

    Referencias a Controller Services

    Cuando una propiedad requiere otro Controller Service, NiFi verifica que la referencia sea compatible.

    Por ejemplo, una propiedad que espera un RecordReaderFactory solo permitirá seleccionar servicios que implementen esa interfaz, como:

    • CSVReader.
    • JsonTreeReader.
    • AvroReader.
    • ParquetReader, cuando sea compatible con el componente.

    No permitirá seleccionar un DBCPConnectionPool, porque proporciona una funcionalidad diferente.

    flowchart TD
    PROC["Componente consumidor"]
    PROPERTY["Propiedad Record Reader"]
    INTERFACE["RecordReaderFactory"]
    CSV["CSVReader"]
    JSON["JsonTreeReader"]
    DBCP["DBCPConnectionPool"]

    PROC --> PROPERTY
    PROPERTY --> INTERFACE
    INTERFACE --> CSV
    INTERFACE --> JSON
    DBCP -. "Incompatible" .-> INTERFACE

    Además de la compatibilidad de tipo, el servicio referenciado debe estar disponible dentro del ámbito del componente consumidor.

    Un servicio creado en otro Process Group no relacionado no podrá seleccionarse.

    Validación de dependencias entre servicios

    Cuando un Controller Service depende de otro, la validación puede tener en cuenta el estado del servicio referenciado.

    Supongamos un servicio cliente que depende de un StandardSSLContextService.

    flowchart LR
    SSL["StandardSSLContextService"]
    CLIENT["Servicio cliente"]
    PROCESSOR["Processor"]

    SSL --> CLIENT
    CLIENT --> PROCESSOR

    Si el servicio TLS contiene una configuración incorrecta, el servicio cliente también puede quedar inválido.

    Se forma una cadena de dependencias:

    flowchart TD
    BASE["Servicio base inválido"]
    DEPENDENT["Servicio dependiente inválido"]
    PROCESSOR["Processor inválido o no ejecutable"]

    BASE --> DEPENDENT
    DEPENDENT --> PROCESSOR

    Por este motivo, los errores deben corregirse comenzando por el nivel más bajo de la dependencia.

    El orden recomendado es:

    1. Corregir el servicio base.
    2. Validarlo.
    3. Habilitarlo.
    4. Corregir el servicio dependiente.
    5. Habilitarlo.
    6. Iniciar los Processors consumidores.

    Validación de parámetros

    Los Controller Services pueden utilizar parámetros mediante la sintaxis:

    #{nombre.parametro}

    NiFi comprueba que el parámetro exista dentro del Parameter Context asociado al Process Group.

    Por ejemplo:

    jdbc:postgresql://#{db.host}:#{db.port}/#{db.name}

    Para que la propiedad sea válida deben existir los parámetros:

    db.host
db.port
db.name

    Si uno de ellos no existe, NiFi mostrará un error similar a:

    Parameter 'db.host' is not defined

    flowchart LR
    PROPERTY["Propiedad del servicio"]
    REFERENCE["#{db.host}"]
    CONTEXT["Parameter Context"]
    EXISTS{"¿Existe el parámetro?"}
    VALID["Válido"]
    INVALID["Invalid"]

    PROPERTY --> REFERENCE
    REFERENCE --> CONTEXT
    CONTEXT --> EXISTS
    EXISTS -->|Sí| VALID
    EXISTS -->|No| INVALID

    Parámetros sensibles

    Una propiedad sensible debe utilizar un parámetro marcado también como sensible.

    Por ejemplo, la contraseña de una base de datos puede definirse mediante:

    #{db.password}

    El parámetro db.password debería declararse como sensible dentro del Parameter Context.

    Esto impide que su valor se muestre en texto claro.

    flowchart TD
    PARAM["Parámetro db.password"]
    SENSITIVE{"¿Marcado como sensible?"}
    PROPERTY["Propiedad Password"]
    SECURE["Uso seguro"]
    WARNING["Configuración insegura"]

    PARAM --> SENSITIVE
    SENSITIVE -->|Sí| PROPERTY
    PROPERTY --> SECURE
    SENSITIVE -->|No| WARNING

    Una vez creado un parámetro sensible, su valor no puede visualizarse posteriormente desde la interfaz.

    Cuando sea necesario cambiarlo, deberá introducirse un nuevo valor.

    Expression Language

    Algunas propiedades permiten utilizar NiFi Expression Language.

    La propia descripción de la propiedad indica si está soportada y cuál es su ámbito de evaluación.

    Sin embargo, los Controller Services no procesan FlowFiles directamente. Por ello, no debe asumirse que están disponibles atributos como:

    ${filename}
${uuid}
${path}

    Estas expresiones dependen de un FlowFile y, normalmente, no tienen sentido durante la inicialización de un Controller Service.

    En cambio, pueden ser válidas expresiones basadas en:

    • Propiedades del sistema.
    • Variables disponibles en el entorno.
    • Funciones compatibles con la propiedad.
    • Parámetros, utilizando la sintaxis específica de Parameter Contexts.

    Antes de utilizar Expression Language debe revisarse la documentación de la propiedad.

    Validación de rutas

    Los Controller Services pueden requerir rutas a archivos o directorios.

    Ejemplos:

    • Drivers JDBC.
    • Keystores.
    • Truststores.
    • Archivos de configuración.
    • Esquemas.
    • Recursos auxiliares.

    Una ruta puede ser sintácticamente correcta, pero no existir en el entorno de ejecución.

    Por ejemplo:

    /opt/nifi/drivers/postgresql.jar

    En una instalación local, el archivo debe existir en el servidor NiFi.

    En Docker, debe existir dentro del contenedor.

    flowchart LR
    HOST["Host<br/>./drivers/postgresql.jar"]
    MOUNT["Volumen Docker"]
    CONTAINER["Contenedor<br/>/opt/nifi/drivers/postgresql.jar"]
    SERVICE["Controller Service"]

    HOST --> MOUNT
    MOUNT --> CONTAINER
    CONTAINER --> SERVICE

    En un clúster, el recurso debe estar disponible en todos los nodos que inicialicen el servicio.

    Validación sintáctica y validación operativa

    Una distinción especialmente importante es la diferencia entre validación sintáctica y validación operativa.

    Validación sintáctica

    Comprueba si la configuración tiene una estructura correcta.

    Ejemplos:

    • La URL no está vacía.
    • El puerto es un número.
    • El tiempo de espera utiliza una unidad admitida.
    • La propiedad obligatoria tiene valor.
    • La referencia apunta a un servicio compatible.

    Validación operativa

    Comprueba si el recurso puede utilizarse realmente.

    Ejemplos:

    • El servidor responde.
    • Las credenciales son correctas.
    • El certificado es válido.
    • El driver puede cargarse.
    • La base de datos acepta conexiones.
    • El usuario dispone de permisos.

    Muchas validaciones operativas se realizan durante la habilitación o durante el primer uso del servicio.

    flowchart TD
    CONFIG["Configuración"]
    SYNTACTIC["Validación sintáctica"]
    VALID{"¿Sintácticamente válida?"}
    ENABLE["Habilitación"]
    OPERATIONAL["Inicialización operativa"]
    READY["Servicio disponible"]
    ERROR["Error de inicialización"]

    CONFIG --> SYNTACTIC
    SYNTACTIC --> VALID
    VALID -->|No| CONFIG
    VALID -->|Sí| ENABLE
    ENABLE --> OPERATIONAL
    OPERATIONAL -->|Correcta| READY
    OPERATIONAL -->|Falla| ERROR

    Un servicio válido puede fallar al habilitarse

    Una de las confusiones más habituales consiste en asumir que un servicio válido siempre podrá habilitarse.

    No es así.

    La validación puede confirmar que:

    • La URL JDBC tiene formato correcto.
    • La clase del driver está informada.
    • El usuario tiene valor.
    • La contraseña está configurada.

    Sin embargo, al habilitar el servicio pueden aparecer errores como:

    • Driver no encontrado.
    • Archivo JAR inexistente.
    • Base de datos inaccesible.
    • Credenciales incorrectas.
    • Certificado caducado.
    • Error de resolución DNS.
    • Tiempo de espera agotado.
    • Puerto bloqueado.
    • Protocolo TLS incompatible.

    Por tanto:

    La validación comprueba la coherencia de la configuración; la habilitación comprueba si el servicio puede inicializar sus recursos.

    Mensajes de validación

    Los mensajes de validación deben leerse con atención.

    Normalmente incluyen:

    • Nombre de la propiedad.
    • Valor afectado.
    • Motivo del error.
    • Dependencia relacionada.
    • Restricción incumplida.

    Ejemplo:

    'Database Driver Location(s)' is invalid because the specified resource does not exist

    Este mensaje indica tres elementos:

    Elemento Interpretación
    Propiedad Database Driver Location(s)
    Problema El recurso no existe
    Acción Revisar la ruta y el acceso al archivo

    Otro ejemplo:

    'Maximum Total Connections' validated against '0' is invalid because the value must be greater than 0

    La acción adecuada será aumentar el valor:

    Maximum Total Connections = 8

    Cuando un Controller Service permanece inválido, conviene seguir un proceso ordenado.

    El procedimiento recomendado es:

    1. Abrir la configuración del servicio.
    2. Leer todos los mensajes de validación.
    3. Corregir primero las propiedades obligatorias.
    4. Revisar parámetros y valores sensibles.
    5. Verificar las dependencias con otros servicios.
    6. Comprobar rutas y recursos.
    7. Guardar los cambios.
    8. Esperar a que NiFi vuelva a validar.
    9. Repetir el proceso hasta eliminar todos los errores.

    Orden de corrección

    Cuando aparecen varios errores, no siempre deben tratarse como problemas independientes.

    Un único error en un servicio base puede provocar varios errores derivados.

    Por ejemplo:

    flowchart TD
    SSL["SSLContextService inválido"]
    HTTP["HTTP Client Service inválido"]
    PROC1["InvokeHTTP inválido"]
    PROC2["ConsumeHTTP inválido"]

    SSL --> HTTP
    HTTP --> PROC1
    HTTP --> PROC2

    En esta situación no conviene comenzar por los Processors.

    La corrección debe seguir el orden de las dependencias:

    1. SSLContextService.
    2. Servicio cliente HTTP.
    3. Processors consumidores.

    Corregir la causa raíz puede resolver automáticamente varios mensajes secundarios.

    Validación en un clúster

    En un clúster NiFi, la configuración del Controller Service forma parte del flujo compartido, pero los recursos locales pueden variar entre nodos.

    Supongamos un clúster de tres nodos:

    flowchart TD
    SERVICE["DBCPConnectionPool"]
    N1["Nodo 1<br/>Driver disponible"]
    N2["Nodo 2<br/>Driver disponible"]
    N3["Nodo 3<br/>Driver ausente"]

    SERVICE --> N1
    SERVICE --> N2
    SERVICE --> N3

    La configuración puede ser sintácticamente válida, pero el servicio puede fallar en el nodo 3 durante su inicialización.

    Deben comprobarse en todos los nodos:

    • Drivers.
    • Certificados.
    • Archivos.
    • Directorios.
    • Permisos.
    • Resolución DNS.
    • Acceso de red.
    • Variables de entorno.

    Las rutas absolutas deben ser coherentes en toda la infraestructura.

    Validación en Docker

    En Docker, uno de los errores más habituales es configurar una ruta existente en el host, pero inexistente dentro del contenedor.

    Configuración incorrecta:

    C:\nifi\drivers\postgresql.jar

    Esta ruta puede existir en el equipo anfitrión, pero no dentro de un contenedor Linux.

    La ruta debe corresponder al sistema de archivos interno:

    /opt/nifi/drivers/postgresql.jar

    Y el recurso debe montarse mediante volumes:

    services:
  nifi:
    image: apache/nifi:2.10.0
    volumes:
      - ./drivers:/opt/nifi/drivers:ro

    El modificador :ro monta el directorio en modo de solo lectura, una opción adecuada cuando NiFi únicamente debe leer los drivers.

    Cambios en Parameter Contexts

    Cuando se modifica un parámetro utilizado por un Controller Service, NiFi debe actualizar los componentes afectados.

    El cambio puede requerir:

    • Detener Processors.
    • Deshabilitar Controller Services.
    • Aplicar el nuevo valor.
    • Volver a validar.
    • Habilitar los servicios.
    • Reiniciar los componentes consumidores.
    sequenceDiagram
    participant U as Administrador
    participant PC as Parameter Context
    participant CS as Controller Service
    participant P as Processor

    U->>P: Detener Processor
    U->>CS: Deshabilitar servicio
    U->>PC: Modificar parámetro
    PC-->>CS: Nuevo valor
    CS->>CS: Validar configuración
    U->>CS: Habilitar servicio
    U->>P: Iniciar Processor

    Este procedimiento reduce el riesgo de estados inconsistentes durante cambios de configuración.

    Ejemplo de validación de un DBCPConnectionPool

    Supongamos la siguiente configuración inicial:

    Propiedad Valor
    Database Connection URL Vacío
    Database Driver Class Name org.postgresql.Driver
    Database Driver Location(s) /opt/nifi/drivers/postgresql.jar
    Database User nifi_user
    Password Configurada

    El servicio mostrará un error similar a:

    'Database Connection URL' is invalid because it is required

    Después se configura:

    jdbc:postgresql://postgres:5432/nifi

    NiFi vuelve a validar el servicio.

    Si todas las propiedades obligatorias cumplen sus reglas, el servicio dejará de aparecer como inválido.

    Sin embargo, todavía podrían surgir errores al habilitarlo:

    Connection refused

    o:

    FATAL: password authentication failed for user "nifi_user"

    Estos errores no corresponden a la validación estática, sino a la inicialización o conectividad.

    Validación frente a prueba de conexión

    No todos los Controller Services incorporan una acción explícita de prueba de conexión.

    Cuando no existe esta funcionalidad, la comprobación suele realizarse mediante:

    • La habilitación del servicio.
    • Un Processor consumidor.
    • Un flujo de prueba.
    • Los boletines de NiFi.
    • Los registros del sistema.

    Para un DBCPConnectionPool, puede utilizarse un Processor sencillo como ExecuteSQL con una consulta de prueba:

    SELECT 1;

    flowchart LR
    DBCP["DBCPConnectionPool"]

    SUCCESS["Relación success"]
    FAILURE["Boletín o error"]

    DBCP --> SQL
    SQL --> DB
    DB -->|Respuesta correcta| SUCCESS

    Este método permite verificar no solo la configuración, sino también la conectividad y las credenciales.

    Boletines y logs

    Cuando la validación no explica completamente el problema, deben revisarse los boletines y los logs.

    Los boletines aparecen en la interfaz y suelen mostrar errores relacionados con:

    • Inicialización.
    • Dependencias.
    • Conectividad.
    • Carga de clases.
    • Certificados.
    • Acceso a archivos.

    Los registros más relevantes suelen encontrarse en:

    logs/nifi-app.log

    En Docker pueden consultarse mediante:

    docker compose logs -f nifi

    O directamente sobre el contenedor:

    docker logs -f nifi

    Para filtrar errores relacionados con JDBC:

    docker compose logs nifi | grep -i jdbc

    Para localizar errores del driver PostgreSQL:

    docker compose logs nifi | grep -i postgresql

    La validación de la interfaz proporciona una visión resumida, mientras que los logs suelen incluir la excepción completa y su causa interna.

    Buenas prácticas

    Para facilitar la validación de los Controller Services se recomienda:

    • Configurar primero todas las propiedades obligatorias.
    • Utilizar Parameter Contexts.
    • Marcar como sensibles los parámetros confidenciales.
    • Evitar rutas dependientes de un único nodo.
    • Utilizar rutas homogéneas en el clúster.
    • Montar explícitamente los recursos en Docker.
    • Crear y habilitar primero los servicios base.
    • Leer todos los mensajes de validación.
    • Corregir la causa raíz antes que los errores derivados.
    • Revisar los valores predeterminados.
    • Probar la conectividad con un flujo mínimo.
    • Consultar los logs cuando la interfaz no proporcione suficiente detalle.
    • Documentar las dependencias y los requisitos externos.

    Errores frecuentes

    Confundir Invalid con Disabled

    Invalid indica que la configuración no cumple los requisitos.

    Disabled indica que el servicio no está habilitado, aunque puede estar correctamente configurado.

    Un servicio puede encontrarse:

    • Deshabilitado e inválido.
    • Deshabilitado y válido.
    • Habilitado y operativo.

    Pensar que la validación prueba la conectividad

    Una URL puede ser válida sintácticamente aunque el servidor no esté disponible.

    Corregir primero los Processors

    Cuando el problema procede de un Controller Service base, debe resolverse la dependencia antes de revisar los componentes consumidores.

    Ignorar los parámetros sensibles

    Una contraseña puede estar parametrizada, pero el parámetro debe existir y estar correctamente definido.

    Usar rutas del host en Docker

    NiFi valida y utiliza las rutas desde el interior del contenedor.

    No revisar todos los nodos

    Un recurso local puede estar presente en un nodo y ausente en otro.

    Ignorar los mensajes completos

    Leer únicamente la palabra Invalid no proporciona suficiente información. Debe consultarse el detalle de cada causa.

    Habilitación

    Una vez que un Controller Service dispone de una configuración válida, debe habilitarse para que pueda ser utilizado por los Processors y por otros Controller Services.

    La habilitación no consiste únicamente en cambiar el estado visual del componente. Durante este proceso, Apache NiFi ejecuta la lógica de inicialización definida por el servicio y prepara los recursos que este gestionará durante su funcionamiento.

    Dependiendo del tipo de Controller Service, la habilitación puede implicar:

    • Cargar drivers.
    • Crear pools de conexiones.
    • Leer certificados.
    • Inicializar clientes de red.
    • Abrir conexiones.
    • Cargar esquemas.
    • Crear estructuras internas.
    • Validar dependencias.
    • Reservar memoria.
    • Registrar recursos para su reutilización.
    flowchart LR
    VALID["Servicio válido"]
    ENABLE["Solicitud de habilitación"]
    INIT["Inicialización"]
    CHECK["Comprobación de dependencias"]
    RESULT{"¿Inicialización correcta?"}
    ENABLED["Enabled"]
    ERROR["Error de habilitación"]

    VALID --> ENABLE
    ENABLE --> CHECK
    CHECK --> INIT
    INIT --> RESULT
    RESULT -->|Sí| ENABLED
    RESULT -->|No| ERROR

    Un Controller Service únicamente estará disponible para sus consumidores cuando alcance el estado Enabled.

    Estados relacionados con la habilitación

    Durante este proceso pueden aparecer varios estados.

    Estado Significado
    Invalid La configuración contiene errores
    Disabled El servicio está configurado, pero no está activo
    Enabling NiFi está inicializando el servicio
    Enabled El servicio está disponible
    Disabling NiFi está liberando los recursos
    Disabling Failed Se produjo un error al liberar el servicio

    Aunque la interfaz puede simplificar algunos de estos estados, conceptualmente el ciclo completo es el siguiente:

    stateDiagram-v2
    [*] --> Invalid
    Invalid --> Disabled: Corregir configuración
    Disabled --> Enabling: Enable
    Enabling --> Enabled: Inicialización correcta
    Enabling --> Disabled: Error
    Enabled --> Disabling: Disable
    Disabling --> Disabled: Recursos liberados
    Disabled --> Invalid: Configuración incorrecta

    Diferencia entre válido y habilitado

    Un servicio válido no está necesariamente habilitado.

    Esta diferencia es fundamental.

    Un Controller Service puede encontrarse en estado Disabled y tener una configuración perfectamente válida. En este caso, NiFi permite habilitarlo, pero todavía no proporciona ningún recurso.

    Situación Válido Habilitado Utilizable
    Faltan propiedades No No No
    Configurado correctamente Sí No No
    Inicializado correctamente Sí Sí Sí
    Error durante la inicialización Sí No No

    La validación comprueba la coherencia de la configuración.

    La habilitación intenta construir o acceder a los recursos reales.

    Por ejemplo, un DBCPConnectionPool puede ser válido porque contiene:

    • URL JDBC.
    • Clase del driver.
    • Usuario.
    • Contraseña.
    • Tamaño del pool.

    Sin embargo, puede fallar al habilitarse si:

    • El driver no puede cargarse.
    • La base de datos no responde.
    • Las credenciales son incorrectas.
    • El servidor no puede resolverse mediante DNS.
    • El certificado no es válido.
    • La red bloquea el puerto.

    Habilitar desde la interfaz

    Para habilitar un Controller Service desde la interfaz gráfica, el procedimiento habitual es:

    1. Acceder a la configuración del Process Group.
    2. Abrir la pestaña Controller Services.
    3. Localizar el servicio.
    4. Comprobar que no aparece como inválido.
    5. Seleccionar la opción Enable.
    6. Confirmar la operación.
    7. Esperar a que el estado cambie a Enabled.

    PG["Configurar Process Group"]

    CORRECT --> SELECT

    Si el servicio tiene componentes referenciados, la interfaz puede ofrecer opciones adicionales para habilitar también sus dependencias o los componentes consumidores.

    Inicialización del servicio

    Durante la habilitación, NiFi invoca la lógica de inicialización del Controller Service.

    Cada implementación define qué acciones debe ejecutar.

    Por ejemplo:

    Controller Service Inicialización habitual
    DBCPConnectionPool Carga el driver y prepara el pool
    StandardSSLContextService Carga keystore, truststore y contexto TLS
    JsonTreeReader Prepara la lógica de lectura y resolución de esquemas
    CSVReader Inicializa la configuración de análisis CSV
    JsonRecordSetWriter Prepara el escritor de registros
    Servicio Kafka Crea el cliente y carga propiedades
    Lookup Service Inicializa la fuente de búsqueda

    En algunos casos, la inicialización es casi inmediata.

    En otros, puede implicar operaciones costosas o acceso a servicios externos.

    sequenceDiagram
    participant A as Administrador
    participant N as Apache NiFi
    participant C as Controller Service
    participant R as Recurso externo

    A->>N: Enable
    N->>C: Validar dependencias
    C->>C: Inicializar estructuras
    C->>R: Abrir o preparar acceso
    R-->>C: Respuesta
    C-->>N: Inicialización correcta
    N-->>A: Estado Enabled

    Orden de habilitación

    Cuando existen dependencias entre servicios, deben habilitarse en el orden adecuado.

    La regla general es:

    Los recursos base deben habilitarse antes que los componentes que dependen de ellos.

    Supongamos la siguiente arquitectura:

    flowchart TD
    SSL["StandardSSLContextService"]
    CLIENT["Servicio cliente HTTPS"]
    PROCESSOR["Processor consumidor"]

    SSL --> CLIENT
    CLIENT --> PROCESSOR

    El orden correcto es:

    1. Habilitar StandardSSLContextService.
    2. Habilitar el servicio cliente.
    3. Iniciar el Processor.

    El orden contrario puede provocar estados inválidos o errores de inicialización.

    flowchart LR
    BASE["1. Servicio base"]
    DEP["2. Servicio dependiente"]
    PROC["3. Processor"]

    BASE --> DEP
    DEP --> PROC

    Habilitación en cascada

    Apache NiFi puede mostrar los componentes referenciados y permitir operaciones sobre ellos.

    En algunos casos, al habilitar un Controller Service puede ofrecer la posibilidad de habilitar también otros servicios relacionados.

    Sin embargo, esta acción debe utilizarse con precaución.

    Antes de habilitar múltiples componentes conviene revisar:

    • Qué servicios se activarán.
    • Qué Processors comenzarán a utilizar el recurso.
    • Si todos pertenecen al entorno correcto.
    • Si las credenciales están actualizadas.
    • Si el sistema externo está disponible.
    • Si existe una ventana de mantenimiento.

    Una habilitación masiva puede afectar simultáneamente a numerosos flujos.

    Qué sucede al habilitar un DBCPConnectionPool

    En el caso de un DBCPConnectionPool, la habilitación puede incluir los siguientes pasos:

    flowchart TD
    START["Enable"]
    DRIVER["Localizar y cargar driver JDBC"]
    CONFIG["Leer URL y propiedades"]
    POOL["Crear pool de conexiones"]

    DRIVER --> CONFIG
    CONFIG --> POOL
    POOL --> VALIDATION

    Dependiendo de la implementación y de la configuración, las conexiones físicas pueden crearse:

    • Durante la habilitación.
    • De forma perezosa, cuando un Processor solicita la primera conexión.
    • Gradualmente, según aumenta la carga.

    Por ello, un servicio puede llegar a Enabled y fallar posteriormente en el primer uso si la conectividad real no se comprobó durante la inicialización.

    Inicialización perezosa

    Algunos servicios utilizan una estrategia conocida como lazy initialization o inicialización perezosa.

    Esto significa que ciertos recursos no se crean hasta que son realmente necesarios.

    sequenceDiagram
    participant A as Administrador
    participant CS as Controller Service
    participant P as Processor
    participant DB as Base de datos

    A->>CS: Enable
    CS-->>A: Enabled
    Note over CS: Todavía no abre una conexión
    P->>CS: Solicitar conexión
    CS->>DB: Crear conexión
    DB-->>CS: Conexión disponible
    CS-->>P: Entregar conexión

    Este modelo presenta ventajas:

    • Reduce recursos innecesarios.
    • Acelera la habilitación.
    • Evita conexiones sin uso.

    Pero también puede retrasar la aparición de errores.

    Un servicio puede parecer correctamente habilitado hasta que un Processor intenta utilizarlo.

    Errores durante la habilitación

    Cuando la inicialización falla, NiFi suele mantener el servicio deshabilitado y generar un boletín.

    Ejemplos frecuentes:

    Failed to invoke @OnEnabled method

    Cannot load JDBC driver class

    Connection refused

    Unknown host

    Keystore was tampered with, or password was incorrect

    PKIX path building failed

    Permission denied

    No such file or directory

    Estos errores deben analizarse junto con los logs.

    Fallo en métodos de ciclo de vida

    Los Controller Services pueden implementar métodos asociados a eventos de ciclo de vida.

    Conceptualmente, pueden existir acciones equivalentes a:

    • Al habilitar.
    • Al deshabilitar.
    • Al configurar.
    • Al inicializar.

    Cuando falla la lógica ejecutada durante la habilitación, NiFi puede mostrar un error similar a:

    Failed to invoke @OnEnabled method

    Este mensaje indica que la configuración superó la validación, pero la inicialización interna lanzó una excepción.

    La causa real suele aparecer más abajo en el log.

    Ejemplo conceptual:

    Failed to invoke @OnEnabled method
Caused by: java.lang.ClassNotFoundException: org.postgresql.Driver

    En este caso, el problema real no es la habilitación en sí, sino la ausencia del driver.

    Problemas con drivers

    Uno de los errores más habituales en servicios JDBC es la imposibilidad de cargar el driver.

    Ejemplo:

    java.lang.ClassNotFoundException: org.postgresql.Driver

    Las posibles causas son:

    • El archivo JAR no existe.
    • La ruta configurada es incorrecta.
    • El JAR no está accesible.
    • La clase especificada no corresponde al driver.
    • El archivo está corrupto.
    • El driver no está disponible en todos los nodos.

    Debe verificarse:

    ls -l /opt/nifi/drivers/

    En Docker:

    docker compose exec nifi ls -l /opt/nifi/drivers/

    El nombre de clase habitual para PostgreSQL es:

    org.postgresql.Driver

    Para MySQL:

    com.mysql.cj.jdbc.Driver

    Para MariaDB:

    org.mariadb.jdbc.Driver

    Problemas de red

    Si el servicio necesita acceder a un sistema externo, la habilitación puede fallar por problemas de red.

    Errores habituales:

    Connection refused

    Connection timed out

    UnknownHostException

    No route to host

    Debe comprobarse:

    • Nombre DNS.
    • Dirección IP.
    • Puerto.
    • Firewall.
    • Red Docker.
    • Reglas de seguridad.
    • Proxy.
    • Rutas entre subredes.

    Desde un contenedor puede probarse la resolución:

    docker compose exec nifi getent hosts postgres

    Y la conectividad TCP:

    docker compose exec nifi bash -c 'echo > /dev/tcp/postgres/5432'

    También puede utilizarse nc si está disponible:

    nc -zv postgres 5432

    Problemas de autenticación

    Un servicio puede conectarse al servidor y fallar durante la autenticación.

    Ejemplos:

    password authentication failed

    Access denied for user

    Invalid credentials

    Debe revisarse:

    • Usuario.
    • Contraseña.
    • Base de datos.
    • Dominio.
    • Mecanismo de autenticación.
    • Caducidad de credenciales.
    • Permisos del usuario.
    • Parameter Context asociado.

    Cuando se utilizan parámetros, conviene confirmar que el Process Group tiene asociado el contexto correcto.

    Problemas con certificados

    Los servicios TLS pueden fallar durante la habilitación por errores relacionados con certificados.

    Ejemplos:

    Keystore password was incorrect

    Truststore does not contain trusted certificate

    Certificate has expired

    PKIX path building failed

    Habilitación en clúster

    En un clúster NiFi, el Controller Service se habilita para los nodos que forman parte de la plataforma.

    La configuración lógica es común, pero cada nodo inicializa sus propios recursos locales.

    flowchart TD
    CONFIG["Configuración compartida"]
    SERVICE["Controller Service"]
    N1["Nodo 1<br/>Instancia local"]
    N2["Nodo 2<br/>Instancia local"]
    N3["Nodo 3<br/>Instancia local"]

    CONFIG --> SERVICE
    SERVICE --> N1
    SERVICE --> N2
    SERVICE --> N3

    En un pool JDBC, cada nodo puede mantener su propio conjunto de conexiones.

    Por ejemplo, si se configura:

    Maximum Total Connections = 10

    y existen tres nodos, el número máximo teórico agregado puede ser:

    10 conexiones × 3 nodos = 30 conexiones

    Esto debe considerarse al dimensionar la base de datos.

    flowchart TD
    DB["Base de datos"]

    N2["Nodo 2<br/>Pool máximo: 10"]
    N3["Nodo 3<br/>Pool máximo: 10"]

    N1 --> DB
    N2 --> DB
    N3 --> DB

    El límite configurado en el Controller Service suele aplicarse por nodo, no necesariamente a todo el clúster de forma global.

    Impacto sobre sistemas externos

    Habilitar un Controller Service puede provocar actividad inmediata sobre sistemas externos.

    Ejemplos:

    • Apertura de conexiones.
    • Autenticación.
    • Carga de metadatos.
    • Consulta de esquemas.
    • Registro de clientes.
    • Negociación TLS.
    • Reserva de sesiones.

    Por tanto, la habilitación debe planificarse en entornos productivos.

    Especialmente cuando:

    • Existen muchos nodos.
    • Se habilitan varios servicios a la vez.
    • El sistema externo tiene límites de conexión.
    • Las credenciales tienen restricciones.
    • El servicio utiliza recursos costosos.

    Habilitación y Processors detenidos

    Un Controller Service puede habilitarse aunque los Processors consumidores estén detenidos.

    De hecho, este suele ser el procedimiento recomendado durante una puesta en marcha:

    sequenceDiagram
    participant A as Administrador
    participant CS as Controller Service
    participant P as Processor

    A->>P: Mantener detenido
    A->>CS: Habilitar
    CS-->>A: Enabled
    A->>P: Iniciar

    Este orden permite detectar primero los errores de infraestructura y después los errores del flujo.

    Modificación de un servicio habilitado

    La mayoría de las propiedades no pueden modificarse mientras el servicio está habilitado.

    Para cambiar la configuración debe seguirse este proceso:

    1. Detener los Processors consumidores.
    2. Deshabilitar el Controller Service.
    3. Modificar las propiedades.
    4. Guardar.
    5. Validar.
    6. Habilitar de nuevo.
    7. Iniciar los Processors.
    flowchart LR
    STOP["Detener Processors"]
    DISABLE["Deshabilitar servicio"]
    EDIT["Modificar propiedades"]
    VALIDATE["Validar"]
    ENABLE["Habilitar"]
    START["Iniciar Processors"]

    STOP --> DISABLE
    DISABLE --> EDIT
    EDIT --> VALIDATE
    VALIDATE --> ENABLE
    ENABLE --> START

    Este procedimiento evita que los Processors utilicen un recurso mientras su configuración está cambiando.

    CS->>CS: Validar y habilitar
    CS->>DB: Probar conexión
    P->>P: Reiniciar

    Debe coordinarse el momento en que se modifica la credencial en NiFi y en el sistema externo.

    Si se cambia primero en la base de datos, NiFi puede perder conectividad.

    Si se cambia primero en NiFi, el nuevo valor puede no ser aceptado todavía.

    En entornos críticos puede utilizarse una estrategia temporal con credenciales solapadas.

    Deshabilitación

    Aunque este apartado se centra en la habilitación, ambos procesos están estrechamente relacionados.

    Al deshabilitar un Controller Service, NiFi intenta liberar los recursos inicializados.

    Esto puede incluir:

    • Cerrar conexiones.
    • Vaciar pools.
    • Finalizar clientes.
    • Detener hilos internos.
    • Liberar memoria.
    • Cerrar archivos.
    • Desregistrar listeners.
    flowchart LR
    ENABLED["Enabled"]
    DISABLE["Disable"]
    RELEASE["Liberar recursos"]
    DISABLED["Disabled"]

    ENABLED --> DISABLE
    DISABLE --> RELEASE
    RELEASE --> DISABLED

    No debe asumirse que deshabilitar equivale simplemente a ocultar o pausar el servicio. Puede provocar el cierre real de recursos externos.

    Componentes en ejecución

    NiFi normalmente impide deshabilitar un servicio mientras existen componentes en ejecución que dependen de él.

    flowchart TD
    REQUEST["Solicitud de Disable"]
    REFERENCES{"¿Hay consumidores ejecutándose?"}
    BLOCK["Operación bloqueada"]
    RELEASE["Liberar recursos"]
    DISABLED["Disabled"]

    REFERENCES -->|Sí| BLOCK
    REFERENCES -->|No| RELEASE
    RELEASE --> DISABLED

    El orden correcto será:

    1. Detener Processors.
    2. Deshabilitar servicios consumidores.
    3. Deshabilitar el servicio base.

    Deshabilitación en orden inverso

    La habilitación sigue el orden de las dependencias.

    La deshabilitación sigue el orden inverso.

    flowchart LR

    Buenas prácticas

    Durante la habilitación se recomienda:

    • Validar completamente el servicio antes de habilitarlo.
    • Habilitar primero los servicios base.
    • Mantener detenidos los Processors durante la inicialización.
    • Revisar los componentes referenciados.
    • Probar primero en un entorno no productivo.
    • Consultar boletines y logs.
    • Verificar drivers, certificados y rutas.
    • Comprobar la conectividad desde el entorno real de NiFi.
    • Dimensionar los pools considerando todos los nodos.
    • Evitar habilitaciones masivas sin analizar el impacto.
    • Documentar el orden de arranque.
    • Preparar un procedimiento de reversión.
    • Coordinar los cambios de credenciales.
    • Probar el servicio con un flujo mínimo.

    Errores frecuentes

    Confundir validación con habilitación

    Un servicio válido puede fallar durante la inicialización.

    Habilitar los servicios en orden incorrecto

    Los servicios base deben estar disponibles antes que sus dependientes.

    Utilizar localhost en Docker

    localhost se refiere al propio contenedor NiFi.

    No comprobar los recursos en todos los nodos

    Cada nodo inicializa su propia instancia local.

    Ignorar el tamaño agregado del pool

    El máximo configurado puede multiplicarse por el número de nodos.

    Habilitar Processors antes que sus servicios

    Los Processors pueden quedar inválidos o generar boletines.

    Realizar cambios sin detener consumidores

    La modificación debe planificarse para evitar errores y pérdida de datos.

    Revisar solo la interfaz

    Los logs suelen contener la causa raíz.

    Este servicio permite centralizar y reutilizar conexiones JDBC con bases de datos relacionales y constituye un excelente ejemplo para aplicar todos los conceptos estudiados.

    DBCPConnectionPool

    DBCPConnectionPool es uno de los Controller Services más utilizados en Apache NiFi. Su función consiste en proporcionar conexiones JDBC reutilizables a los Processors y servicios que necesitan interactuar con una base de datos relacional.

    En lugar de abrir una conexión nueva para cada consulta o escritura, el servicio mantiene un conjunto de conexiones administradas, denominado pool de conexiones.

    Cuando un Processor necesita acceder a la base de datos:

    1. Solicita una conexión al pool.
    2. Utiliza la conexión.
    3. Devuelve la conexión al pool.
    4. La conexión queda disponible para otro componente.
    sequenceDiagram
    participant P as Processor
    participant D as DBCPConnectionPool
    participant DB as Base de datos

    P->>D: Solicitar conexión
    alt Hay conexión disponible
        D-->>P: Entregar conexión reutilizada
    else No hay conexión disponible
        D->>DB: Crear nueva conexión JDBC
        DB-->>D: Conexión establecida
        D-->>P: Entregar conexión
    end

    P->>DB: Ejecutar operación SQL
    DB-->>P: Resultado
    P->>D: Devolver conexión
    D->>D: Mantener conexión disponible

    La implementación incluida en Apache NiFi 2.10.0 pertenece al bundle nifi-dbcp-service-nar. El servicio proporciona conexiones a través de la interfaz DBCPService y permite que estas sean solicitadas y devueltas al pool después de su utilización.

    Por qué utilizar un pool de conexiones

    Establecer una conexión con una base de datos puede implicar varias operaciones costosas:

    • Resolución DNS.
    • Apertura de una conexión TCP.
    • Negociación TLS.
    • Autenticación.
    • Creación de una sesión.
    • Configuración del contexto de base de datos.
    • Reserva de recursos en el servidor.

    Si cada Processor abriera y cerrara una conexión para cada FlowFile, se produciría una sobrecarga considerable.

    flowchart TD
    subgraph WITHOUT["Sin pool"]
        P1["FlowFile 1"] --> C1["Crear conexión"]
        C1 --> Q1["Ejecutar SQL"]
        Q1 --> X1["Cerrar conexión"]

        P2["FlowFile 2"] --> C2["Crear conexión"]
        C2 --> Q2["Ejecutar SQL"]
        Q2 --> X2["Cerrar conexión"]

        P3["FlowFile 3"] --> C3["Crear conexión"]
        C3 --> Q3["Ejecutar SQL"]
        Q3 --> X3["Cerrar conexión"]
    end

    Con un pool, las conexiones se reutilizan:

    flowchart TD
    POOL["Pool de conexiones"]

    C1["Conexión 1"]
    C2["Conexión 2"]
    C3["Conexión 3"]

    P1["Processor A"]
    P2["Processor B"]
    P3["Processor C"]

    POOL --> C1
    POOL --> C2
    POOL --> C3

    P1 -. "Solicita y devuelve" .-> POOL
    P2 -. "Solicita y devuelve" .-> POOL
    P3 -. "Solicita y devuelve" .-> POOL

    Este modelo proporciona varias ventajas:

    • Menor latencia.
    • Reducción del coste de autenticación.
    • Control del número máximo de conexiones.
    • Reutilización entre Processors.
    • Protección frente a una creación ilimitada de sesiones.
    • Administración centralizada.
    • Mejor aprovechamiento de los recursos.

    DBCPConnectionPool se sitúa entre los Processors de NiFi y el driver JDBC.

    Elemento Responsabilidad

    El Controller Service no ejecuta directamente las consultas del flujo. Su responsabilidad consiste en proporcionar la conexión que utilizará el Processor.

    Propiedades principales

    Apache NiFi 2.10.0 incorpora propiedades para configurar la conexión, el driver, las credenciales y el comportamiento del pool.

    Database Connection URL

    Esta propiedad contiene la URL JDBC utilizada para conectarse a la base de datos.

    Es obligatoria.

    La estructura depende del sistema gestor de bases de datos.

    Sistema Ejemplo de URL JDBC
    PostgreSQL jdbc:postgresql://postgres:5432/clientes
    MariaDB jdbc:mariadb://mariadb:3306/inventario
    MySQL jdbc:mysql://mysql:3306/ventas
    SQL Server jdbc:sqlserver://sqlserver:1433;databaseName=auditoria
    Oracle jdbc:oracle:thin:@oracle:1521/FREEPDB1

    La URL puede incluir:

    • Motor.
    • Host.
    • Puerto.
    • Base de datos.
    • Opciones específicas.
    • Parámetros de conexión.
    • Configuración TLS.

    NiFi 2.10.0 permite en esta propiedad expresiones basadas en variables de entorno definidas a nivel de JVM y propiedades del sistema.

    En un entorno parametrizado puede utilizarse:

    jdbc:postgresql://#{db.host}:#{db.port}/#{db.name}

    Ejemplo de parámetros:

    Parámetro Valor
    db.host postgres
    db.port 5432
    db.name clientes

    Database Driver Class Name

    Define el nombre completo de la clase Java que implementa el driver JDBC.

    Es una propiedad obligatoria.

    Sistema Clase habitual
    PostgreSQL org.postgresql.Driver
    MariaDB org.mariadb.jdbc.Driver
    MySQL com.mysql.cj.jdbc.Driver
    SQL Server com.microsoft.sqlserver.jdbc.SQLServerDriver
    Oracle oracle.jdbc.OracleDriver

    Un error tipográfico provocará normalmente un fallo al habilitar el servicio.

    Ejemplo:

    org.postgresql.Driver

    Error habitual:

    java.lang.ClassNotFoundException: org.postgresql.Driver

    Database Driver Locations

    Esta propiedad permite indicar uno o varios archivos, directorios o URLs que contienen el driver JDBC y sus dependencias.

    No siempre es obligatoria. Puede dejarse vacía cuando el driver ya forma parte del classpath disponible para NiFi.

    Ejemplo:

    /opt/nifi/drivers/postgresql.jar

    También puede contener una lista separada por comas:

    /opt/nifi/drivers/driver.jar,
/opt/nifi/drivers/dependency-1.jar,
/opt/nifi/drivers/dependency-2.jar

    Apache NiFi 2.10.0 documenta esta propiedad como una lista separada por comas de archivos, directorios o URLs que contienen el driver y sus dependencias.

    Recomendación

    En producción es preferible utilizar drivers almacenados localmente y gestionados mediante:

    • Automatización.
    • Imágenes Docker controladas.
    • Volúmenes de solo lectura.
    • Sistemas de configuración.
    • Procedimientos de actualización.

    Contiene el usuario de la base de datos.

    Ejemplo:

    nifi_reader

    o:

    nifi_writer

    • Un usuario administrador.
    • La cuenta personal de un desarrollador.
    • Una cuenta compartida sin trazabilidad.
    • Un usuario con permisos globales innecesarios.

    Configuración del pool

    Max Total Connections

    Define el máximo número de conexiones activas que pueden asignarse simultáneamente desde el pool.

    El valor predeterminado en NiFi 2.10.0 es:

    8

    Un valor negativo indica que no se aplica límite.

    flowchart TD
    POOL["Pool<br/>Máximo: 3"]

    C1["Conexión 1<br/>En uso"]
    C2["Conexión 2<br/>En uso"]
    C3["Conexión 3<br/>En uso"]

    WAIT["Nueva solicitud<br/>Debe esperar"]

    POOL --> C1
    POOL --> C2
    POOL --> C3
    WAIT -. "Sin conexiones disponibles" .-> POOL

    No se recomienda establecer un valor ilimitado en producción.

    Un crecimiento sin control puede:

    • Saturar la base de datos.
    • Agotar memoria.
    • Consumir todos los sockets.
    • Bloquear a otras aplicaciones.
    • Provocar fallos en cascada.

    Dimensionamiento inicial

    Puede utilizarse como aproximación:

    conexiones_por_nodo ≈ concurrencia_JDBC_esperada + margen

    Por ejemplo:

    Processors JDBC concurrentes: 6
Margen operativo: 2
Max Total Connections: 8

    Sin embargo, no siempre cada tarea concurrente mantiene una conexión durante todo su tiempo de ejecución.

    El dimensionamiento debe basarse en observación real.

    Max Wait Time

    Define cuánto tiempo esperará una solicitud cuando no haya conexiones disponibles.

    El valor predeterminado en NiFi 2.10.0 es:

    500 millis

    El valor -1 permite esperar indefinidamente.

    sequenceDiagram
    participant P as Processor
    participant D as Pool
    participant C as Conexiones

    P->>D: Solicitar conexión
    D->>C: ¿Hay alguna libre?
    C-->>D: No
    D->>D: Esperar Max Wait Time

    alt Se libera una conexión
        C-->>D: Conexión disponible
        D-->>P: Entregar conexión
    else Se supera el tiempo
        D-->>P: Error de timeout
    end

    Un tiempo demasiado corto puede generar errores durante picos breves.

    Un tiempo demasiado largo puede mantener hilos bloqueados y ocultar una saturación del pool.

    Ejemplo equilibrado

    Max Total Connections = 20
Max Wait Time = 5 sec

    La configuración adecuada depende de:

    • Duración de las consultas.
    • Número de tareas concurrentes.
    • Latencia de la base de datos.
    • Capacidad del servidor.
    • Política de reintentos.
    • Requisitos de tiempo de respuesta.

    Minimum Idle Connections

    Define el número mínimo de conexiones inactivas que el pool intentará conservar.

    El valor predeterminado es:

    0

    Con 0, el pool no necesita mantener conexiones inactivas adicionales.

    Un valor superior puede reducir la latencia inicial, porque existen conexiones preparadas.

    flowchart LR
    POOL["Pool"]

    ACTIVE["Activas: 4"]
    IDLE["Inactivas mínimas: 2"]
    CREATE["Crear conexiones adicionales"]

    POOL --> ACTIVE
    POOL --> IDLE
    IDLE -. "Si baja del mínimo" .-> CREATE

    Mantener demasiadas conexiones inactivas puede desperdiciar recursos de la base de datos.

    Maximum Idle Connections

    Define el número máximo de conexiones que pueden permanecer inactivas.

    El valor predeterminado es:

    8

    Un valor negativo permite un número ilimitado de conexiones inactivas.

    Si el número de conexiones inactivas supera este límite, las sobrantes pueden cerrarse.

    Ejemplo:

    Max Total Connections = 20
Maximum Idle Connections = 8
Minimum Idle Connections = 2

    Interpretación:

    • Como máximo puede haber 20 conexiones activas.
    • El pool intentará conservar al menos 2 inactivas.
    • No conservará más de 8 inactivas.

    Maximum Connection Lifetime

    Define la vida máxima de una conexión.

    Cuando se supera ese tiempo, la conexión puede descartarse durante su siguiente activación, devolución o validación.

    Un valor igual o inferior a cero representa una duración ilimitada.

    El valor predeterminado en NiFi 2.10.0 es:

    -1

    flowchart TD
    CREATED["Conexión creada"]
    USED["Utilizada varias veces"]
    AGE{"¿Supera la vida máxima?"}
    RETURN["Volver al pool"]
    CLOSE["Cerrar conexión"]
    NEW["Crear otra cuando sea necesario"]

    CREATED --> USED
    USED --> AGE
    AGE -->|No| RETURN
    AGE -->|Sí| CLOSE
    CLOSE --> NEW

    Configurar una vida máxima puede ser útil cuando:

    • El firewall elimina sesiones antiguas.
    • La base de datos limita la duración.
    • Se rotan credenciales.
    • Se desea renovar periódicamente las conexiones.
    • Existen proxies o balanceadores intermedios.

    Time Between Eviction Runs

    Define el intervalo entre ejecuciones del hilo que revisa conexiones inactivas.

    Cuando el valor es igual o inferior a cero, no se ejecuta el hilo de expulsión periódica.

    El valor predeterminado es:

    -1

    sequenceDiagram
    participant E as Evictor
    participant P as Pool
    participant C as Conexiones inactivas

    loop Cada intervalo configurado
        E->>P: Ejecutar revisión
        P->>C: Comprobar tiempo inactivo
        C-->>P: Lista de candidatas
        P->>P: Cerrar conexiones expulsables
    end

    Para que las políticas de expulsión periódica actúen, debe configurarse un intervalo positivo.

    Ejemplo:

    Time Between Eviction Runs = 5 min

    Minimum Evictable Idle Time

    Define cuánto tiempo debe permanecer inactiva una conexión antes de ser candidata a expulsión.

    El valor predeterminado es:

    30 mins

    Ejemplo:

    Time Between Eviction Runs = 5 min
Minimum Evictable Idle Time = 30 min

    Cada cinco minutos se revisará el pool. Las conexiones que lleven al menos treinta minutos inactivas podrán cerrarse.

    flowchart LR
    IDLE["Conexión inactiva"]
    TIMER["Tiempo inactiva"]
    THRESHOLD{"¿Al menos 30 min?"}
    KEEP["Mantener"]
    EVICT["Expulsar"]

    IDLE --> TIMER
    TIMER --> THRESHOLD
    THRESHOLD -->|No| KEEP
    THRESHOLD -->|Sí| EVICT

    Soft Minimum Evictable Idle Time

    Define un tiempo mínimo de inactividad similar al anterior, pero respeta el número mínimo de conexiones inactivas.

    Una conexión podrá expulsarse cuando:

    • Haya superado el tiempo configurado.
    • Su eliminación no reduzca el pool por debajo de Minimum Idle Connections.

    El valor predeterminado es:

    -1

    flowchart TD
    CONN["Conexión inactiva"]
    TIME{"¿Supera tiempo soft?"}
    MIN{"¿Quedarán suficientes conexiones mínimas?"}
    KEEP["Mantener"]
    EVICT["Expulsar"]

    CONN --> TIME
    TIME -->|No| KEEP
    TIME -->|Sí| MIN
    MIN -->|No| KEEP
    MIN -->|Sí| EVICT

    La diferencia principal es:

    Propiedad Respeta Minimum Idle Connections
    Minimum Evictable Idle Time No necesariamente
    Soft Minimum Evictable Idle Time Sí

    Validation Query

    Permite definir una consulta que se ejecutará para validar las conexiones antes de entregarlas.

    Si la conexión no supera la validación, se descarta y se intenta obtener otra.

    Apache NiFi advierte de que esta validación puede introducir una penalización de rendimiento.

    Ejemplos:

    PostgreSQL

    SELECT 1;

    MariaDB y MySQL

    SELECT 1;

    SQL Server

    SELECT 1;

    Oracle

    SELECT 1 FROM DUAL;

    sequenceDiagram
    participant P as Processor
    participant D as Pool
    participant DB as Base de datos

    P->>D: Solicitar conexión
    D->>DB: Ejecutar Validation Query

    alt Conexión válida
        DB-->>D: Resultado correcto
        D-->>P: Entregar conexión
    else Conexión inválida
        DB-->>D: Error
        D->>D: Descartar conexión
        D->>DB: Crear o seleccionar otra
        D-->>P: Entregar conexión válida
    end

    Cuándo utilizarla

    Resulta especialmente útil cuando:

    • La red elimina conexiones inactivas.
    • La base de datos reinicia sesiones.
    • Existen firewalls con timeout.
    • El pool conserva conexiones durante mucho tiempo.
    • Se observan errores de conexiones cerradas.

    Coste

    Si cada solicitud ejecuta una consulta adicional, aumenta:

    • El número de operaciones.
    • La latencia.
    • La carga de la base de datos.
    • El tráfico de red.

    Debe utilizarse una consulta mínima y sin efectos secundarios.

    Transacciones

    Los Processors que utilizan el pool son responsables de gestionar correctamente las conexiones y las transacciones según su implementación.

    Una conexión puede incluir:

    • Inicio de transacción.
    • Ejecución de sentencias.
    • commit.
    • rollback.
    • Devolución al pool.
    sequenceDiagram
    participant P as Processor
    participant D as DBCPConnectionPool
    participant DB as Base de datos

    P->>D: Obtener conexión
    D-->>P: Conexión
    P->>DB: BEGIN
    P->>DB: Ejecutar sentencias

    alt Operación correcta
        P->>DB: COMMIT
    else Error
        P->>DB: ROLLBACK
    end

    P->>D: Devolver conexión

    No debe confundirse el pool con un coordinador global de transacciones.

    El pool entrega conexiones; la lógica transaccional depende del Processor y del driver.

    Seguridad

    Principio de mínimo privilegio

    El usuario de NiFi debe disponer únicamente de los permisos necesarios.

    Usuario de lectura

    GRANT CONNECT ON DATABASE clientes TO nifi_reader;
GRANT USAGE ON SCHEMA public TO nifi_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO nifi_reader;

    Usuario de escritura controlada

    GRANT CONNECT ON DATABASE clientes TO nifi_writer;
GRANT USAGE ON SCHEMA public TO nifi_writer;
GRANT SELECT, INSERT, UPDATE ON TABLE public.pedidos TO nifi_writer;

    No debe concederse indiscriminadamente:

    GRANT ALL PRIVILEGES ON DATABASE clientes TO nifi_user;

    Es recomendable utilizar distintos pools:

    DBCP-POSTGRESQL-CLIENTES-READ

    Debe utilizarse el nombre del servicio:

    jdbc:postgresql://postgres:5432/clientes

    Crear un pool para cada Processor

    Esto elimina gran parte de las ventajas de reutilización.

    Debe compartirse un pool cuando:

    • El destino es el mismo.
    • Las credenciales son las mismas.
    • La política de conexiones es la misma.
    • El ámbito de seguridad es compatible.

    Compartir un único pool para todo

    El extremo contrario tampoco es recomendable.

    No deberían compartir el mismo pool:

    • Aplicaciones con permisos distintos.
    • Bases de datos diferentes.
    • Entornos diferentes.
    • Lecturas y escrituras con cuentas separadas.
    • Dominios de seguridad independientes.

    Configurar conexiones ilimitadas

    Un valor negativo puede eliminar el límite.

    Esto puede provocar una saturación grave.

    Ignorar el número de nodos

    El límite suele aplicarse por nodo.

    15 conexiones × 5 nodos = 75 conexiones

    Aumentar el pool sin analizar las consultas

    Más conexiones pueden aumentar:

    • Contención.
    • Bloqueos.
    • Consumo de memoria.
    • Cambios de contexto.
    • Esperas de disco.

    No validar conexiones obsoletas

    Las conexiones inactivas pueden ser cerradas por:

    • Firewall.
    • Proxy.
    • Balanceador.
    • Base de datos.
    • Políticas de red.

    No controlar la versión del driver

    Un driver nuevo puede cambiar:

    • Valores predeterminados.
    • Protocolos TLS.
    • Compatibilidad.
    • Formato de URLs.
    • Tipos de datos.
    • Comportamiento de transacciones.

    Laboratorio 9. Seguridad y mínimo privilegio

    Objetivo

    Separar usuarios de lectura y escritura.

    Paso 1. Crear usuarios

    Entrar en PostgreSQL como administrador.

    docker compose exec postgres \
psql -U nifi_user -d clientes_db

    Para un entorno real, estas operaciones deberían ejecutarse con una cuenta administrativa distinta.

    Crear usuarios:

    CREATE USER nifi_reader WITH PASSWORD 'reader_password';
CREATE USER nifi_writer WITH PASSWORD 'writer_password';

    Paso 2. Permisos de lectura

    GRANT CONNECT ON DATABASE clientes_db TO nifi_reader;
GRANT USAGE ON SCHEMA public TO nifi_reader;
GRANT SELECT ON TABLE clientes TO nifi_reader;

    Paso 3. Permisos de escritura

    GRANT CONNECT ON DATABASE clientes_db TO nifi_writer;
GRANT USAGE ON SCHEMA public TO nifi_writer;

GRANT SELECT, INSERT, UPDATE
ON TABLE clientes
TO nifi_writer;

GRANT USAGE, SELECT
ON SEQUENCE clientes_id_seq
TO nifi_writer;

    Paso 4. Crear parámetros sensibles

    Añadir:

    db.reader.user
db.reader.password
db.writer.user
db.writer.password

    Marcar las contraseñas como sensibles.

    Paso 5. Crear dos pools

    Pool de lectura

    DBCP-POSTGRESQL-CLIENTES-READ

    Usuario:

    #{db.reader.user}

    Contraseña:

    #{db.reader.password}

    Pool de escritura

    DBCP-POSTGRESQL-CLIENTES-WRITE

    Usuario:

    #{db.writer.user}

    Contraseña:

    #{db.writer.password}

    Arquitectura

    flowchart TD
    READPROC["ExecuteSQLRecord"]
    WRITEPROC["PutDatabaseRecord"]

    READPOOL["DBCP READ"]
    WRITEPOOL["DBCP WRITE"]

    READER["nifi_reader"]

    WRITEPROC --> WRITEPOOL

    READPOOL --> READER
    WRITEPOOL --> WRITER

    Laboratorio 13. Análisis en clúster

    Objetivo

    Calcular el impacto agregado de los pools.

    Escenario

    Un clúster tiene:

    4 nodos NiFi

    Cada nodo configura:

    Max Total Connections = 12

    La base de datos admite:

    100 conexiones

    Otras aplicaciones consumen:

    45 conexiones

    Cálculo

    Conexiones máximas de NiFi:

    4 × 12 = 48

    Total potencial:

    48 + 45 = 93

    Margen:

    100 - 93 = 7

    El margen es demasiado bajo para:

    • Conexiones administrativas.
    • Procesos internos.
    • Picos.
    • Mantenimiento.
    • Recuperación.

    Propuesta

    Reducir a:

    Max Total Connections = 9

    Nuevo máximo:

    4 × 9 = 36

    Total:

    36 + 45 = 81

    Margen:

    100 - 81 = 19

    Diagrama

    flowchart TD
    DB["Base de datos<br/>Máximo 100"]

    OTHERS["Otras aplicaciones<br/>45"]
    N1["Nodo 1<br/>9"]
    N2["Nodo 2<br/>9"]
    N3["Nodo 3<br/>9"]
    N4["Nodo 4<br/>9"]
    FREE["Margen<br/>19"]

    OTHERS --> DB
    N1 --> DB
    N2 --> DB
    N3 --> DB
    N4 --> DB
    FREE -. "Reserva" .-> DB

    Preguntas

    1. ¿Por qué el límite del pool debe multiplicarse por el número de nodos?
    2. ¿Qué sucedería si se configuraran conexiones ilimitadas?
    3. ¿Por qué debe reservarse margen?
    4. ¿Qué impacto tendría añadir un quinto nodo?
    5. ¿Cómo afectaría aumentar las tareas concurrentes?

    Los aprendizajes principales son:

    1. El Controller Service debe crearse en el ámbito adecuado.
    2. Las propiedades deben configurarse de forma coherente.
    3. La validación detecta errores antes de la ejecución.
    4. La habilitación inicializa los recursos reales.
    5. DBCPConnectionPool centraliza las conexiones JDBC.
    6. Los drivers deben estar disponibles en el entorno de NiFi.
    7. En Docker deben utilizarse nombres internos de servicio.
